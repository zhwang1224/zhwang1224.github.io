TurboBus：把空闲 PCIe 借给 GPU 内存卸载

发表于 2026-09-28 分类于 人工智能系统 ， 计算机网络 阅读时长 ≈ 7 分钟
SIGCOMM 2026 阅读笔记。TurboBus 用节点内特权守护进程和 NVLink 中继，让共置作业借用彼此空闲的 PCIe，服务按需加载、KV 缓存卸载和 ZeRO-Offload。

SIGCOMM 2026 的 TurboBus：GPU 内存卸载的瓶颈是 PCIe 上，而这些链路大部分时间是空的。TurboBus 用纵向扩展互连把邻居的空闲 PCIe 借过来，并用一个特权守护进程保持作业之间的隔离。

按需加载的首 token 时延最多降 40%，KV 缓存卸载的吞吐最高到 1.6×，ZeRO-Offload 的迭代快 4%–7%。借出链路的共置作业开销不到 1%。

TurboBus：把空闲 PCIe 借给 GPU 内存卸载

解决的矛盾

卸载把权重、优化器状态或 KV 缓存放到主机内存。FlexGen 把 90% 的时间花在 PCIe 上，ZeRO-Offload 的数据移动占 24%。链路容量却没用起来：在 16 GB/s 的 PCIe 3.0 x16 上，平均利用率不到 27%，超过 60% 的时间带宽不超过 2 GB/s。

原因是每张 GPU 只能走自己的 PCIe。作业内部，各 rank 的传输互相错开；作业之间，一张卡的 PCIe 带宽可能会充分使用，但邻居 GPU 可能有大量空闲时间。且 Scale-up 网络中提供较高的互连带宽：GPU 之间的 NVLink、Infinity Fabric 或 UALink。V100 上单向 NVLink 是 50 GB/s，PCIe 是 16 GB/s。数据可以先跳到邻居，再从邻居的 PCIe 进主机。

图 1 左：一张卡的 PCIe 忙，其余链路空闲。右：经纵向扩展互连中继后，多条 PCIe 一起传。

已有工作。DeepPlan 和 Torpor 只在同一作业里聚合主机到设备（H2D）的模型加载。memHarvester 靠页错误在 GPU 和主机之间换页，面向的是会反复访问的数据。三者都是存储转发，也不调度跨作业的双向传输。

TurboBus

TurboBus 是每节点一个特权守护进程，外加一个 Python 库。作业只向守护进程提交传输。直连 PCIe 和中继路径放在同一个池里分配。

图 5 守护进程分三块：核心负责跨作业隔离，执行器负责中继，调度器负责双向和公平性。

分块流水中继，而不是整包存储转发。 传输切成固定大小的块。中继 GPU 接收完一块就从 PCIe 送出，同时经 NVLink 收下一块。NVLink 更快，这一跳被藏在 PCIe 时间里。中继缓冲与传输大小无关：两个方向各两块，V100 上是 4 × 16MB = 64MB。块大小按硬件选，V100 和 RTX 3090 为 16MB，H800 为 32MB。小于半块的传输（V100 上 8MB）直接走 cudaMemcpy，不进流水线。

按块填路径，而不是把一条路径锁给一次传输。 一次传输的最后几块填不满所有路径。分配器每一轮把空闲路径交给别的传输里已经就绪的块。微基准里，这比传输级分配最高多 20% 吞吐。

双向流量调度，大传输分片+token门控。 中继只用一跳 NVLink，每个 PCIe 方向同时只有一个请求，所以一条 NVLink 上最多叠两个 PCIe 速率的流。NVLink 超过 PCIe 的两倍，两边都能跑满 PCIe。两个方向若各起一个线程独立同步，CUDA 运行时的锁会让吞吐最多掉 40%；作者改成一个控制线程，按块时间对齐同步。同一方向上，大传输切成片，并且一次只放行一个大传输，避免队头阻塞，也避免两个大传输互相把带宽拆半。分片把完成时间减少 27%，令牌门控减少 15%。

图 6 (a) 同一对 GPU 上，D2H 和 H2D 的直连与中继正好相反。(b) 固定块流水线去掉气泡，并让两个方向对齐。(c) 传输级分配会留下空路径，块级分配把下一次传输的块填进去。

原型大约 3,900 行：C++ 守护进程约 2,500 行，C++ 客户端约 1,100 行，Python 前端约 300 行。主机内存走 /dev/shm，GPU 内存走 CUDA IPC，控制面只走 UNIX 套接字。启动时用 nvidia-smi topo -m 把 NVLink 连通的 GPU 收成可池化的链路组；只共享 PCIe 交换机上行的 GPU 另成一组，因为中继不会多出带宽。守护进程不可用时，请求退回该卡自己的 cudaMemcpy。

实验结果

主测试台是 DGX V100：四块 32GB GPU，两条独立 PCIe 交换机，每个方向两条可池化的 PCIe 3.0 x16（各 16 GB/s）。微基准也跑了 RTX 3090（PCIe 4.0）和八卡 H800（PCIe 5.0）。在剖析出的块大小上，两链路中继吞吐距两条链路的理想值，H2D 约在 5% 以内，D2H 约在 6% 以内。

按需加载。 对照是原生传输（Vanilla）和 PipeSwitch 的逐层流水加上 DeepPlan 的作业内中继（PS+DP）。四张卡各自一条泊松请求流（每卡 请求/秒），模型用 Llama-3-8B，提示长 19、216 或 823 token。TurboBus 能跨这四份作业借链路，PS+DP 不能。中位 TTFT 降 17%–25%；P99 最多比 PS+DP 高 10%，作者把它归因于高峰时争用中继。没有干扰、只用一条专用中继把两条 PCIe 合在一起时，Llama-3-8B 的 TTFT 降 24%–36%，Llama-2-13B 降 22%–40%，最多 40%，与 减半的解析上界相差不超过 5%。

图 9 (a) H800 上中继在本地 NUMA 内扩展，跨 UPI 后聚合吞吐下降。(b)(c) 隔离条件下，TurboBus 的 TTFT 接近两条链路的解析最优。

KV 缓存卸载。 FlexGen 把 90% 的 KV 放在 CPU，权重留在 GPU；批大小 32，输入 512 token，输出 32 token。两份 FlexGen 互为中继时，超过 80% 的迭代快于原版，吞吐最多高 50%，其余迭代最多慢 3 tokens/s。旁边是计算型训练或内存型推理时，FlexGen 吞吐最高到 1.6×，邻居的开销不到 1%。

内存受限训练。 ZeRO-Offload 以 DP=4 跑 GPT-J、Llama-2-7B 和 Phi-3-mini，有效批大小 32。中继和 NVLink 上的全归约同时存在，迭代仍快 4%–7%。PCIe 只占迭代时间的 22%–30%，传输快一倍也最多带来 12%–17% 的端到端加速；4%–7% 大约是这个上界的 33%–41%。

图 10 (a)(b) 两份 FlexGen 互相中继。(c)(d) 与训练或推理共置，FlexGen 变快，邻居几乎不变。(e) ZeRO-Offload 迭代时间略降。

结论

中继要划算，GPU 之间的带宽至少要超过 PCIe；超过两倍以后，双向传输也不会把 NVLink 变成瓶颈。

卸载 GPU 内存的工作负载受 PCIe 带宽瓶颈制约，却让大部分链路容量空闲。这一矛盾植根于按 GPU 独占链路。TurboBus 通过 NVLink 中继，在共置作业之间池化 PCIe 带宽，从而解决这一问题；它保持进程隔离，只需要极少的代码改动，并提供显式的流调度。评估表明，按需模型加载的 TTFT 最多降低 40%（与解析最优值相差不超过 5%），卸载 KV 缓存的推理吞吐量最高达到 1.6×，内存受限训练最多加速 7%，对共置工作负载造成的开销不到 1%。
