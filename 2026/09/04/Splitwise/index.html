Splitwise：拆分 Prefill 与 Decode 的高效大模型推理系统

发表于 2026-09-04 分类于 人工智能系统 ， 计算机体系结构 阅读时长 ≈ 19 分钟
解读 Splitwise 如何依据大模型推理两个阶段的资源差异，拆分机器池、优化 KV Cache 传输，并在延迟 SLO 下改善吞吐、成本与功耗。

一次生成式大模型推理，看起来只是模型连续执行多轮前向计算，内部却包含两种几乎相反的工作负载：处理输入提示的 Prompt/Prefill 阶段计算密集，逐个生成后续 Token 的 Token Generation/Decode 阶段则更受显存容量和带宽约束。如果把两者始终混在同一批昂贵 GPU 上执行，硬件配置只能迁就二者，批处理还会让首 Token 延迟与 Token 间延迟相互干扰。

ISCA 2024 论文《Splitwise: Efficient Generative LLM Inference Using Phase Splitting》提出了一条直接但并不简单的路径：将两个阶段放入独立机器池，为各自选择合适的 GPU、功耗上限和批处理策略，再通过高速互连传递 KV Cache。在经实机数据校准的集群模拟中，论文报告 Splitwise 集群在满足延迟 SLO 的前提下，可实现最高 1.4× 的吞吐提升并将成本降低 20%；或者在成本和功耗预算不变时获得 2.35× 的吞吐。

这篇文章从“为什么值得拆”出发，依次分析 Splitwise 的调度、KV Cache 传输、集群配置和评估边界。

Splitwise：拆分 Prefill 与 Decode 的高效大模型推理系统

一、为什么同一台 GPU 很难同时服务好两个阶段

1.1 先分清四个指标

一条请求进入生成式 LLM 后，Prompt 中的全部输入 Token 可以并行完成一次前向计算，得到第一个输出 Token，并生成各层的 KV Cache。此后模型每轮只接收上一个 Token，同时读取此前累积的 KV Cache，串行地产生下一个 Token。

因此，推理服务不能只看“每秒生成多少 Token”，至少需要同时关注四个指标：

指标 含义 用户感知
E2E latency 从提交请求到完整响应结束 总等待时间
TTFT（Time to First Token） 请求到达至首 Token 返回 多快开始响应
TBT（Time Between Tokens） 连续两个输出 Token 的平均间隔 流式输出是否顺畅
Throughput 单位时间完成的请求数 系统容量与成本

Prompt 阶段直接决定 TTFT，Decode 阶段的每次迭代决定 TBT；由于输出 Token 是串行生成的，哪怕单次 Decode 不慢，它仍可能占据大部分端到端时间。论文的一个典型观测是：对 BLOOM-176B 而言，处理 1500 个输入 Token 的 Prompt 阶段，耗时只相当于生成 6 个输出 Token；即便代码补全请求的输出很短，E2E 仍主要消耗在 Decode 上。

1.2 真实请求并不天然形成理想大 Batch

作者使用 2023 年 11 月 11 日采集的两段 Azure 生产轨迹，每段持续 20 分钟，分别代表代码补全与对话服务。受隐私要求限制，实验不读取提示内容，而是按真实轨迹的到达时间、输入长度和输出长度构造请求。主要模型是 Llama 2 70B 与 BLOOM-176B，默认在一台配备 8 张 H100 的机器上以 vLLM 运行。

两类服务的请求形态差异很大：

  • 代码补全的输入长度中位数为 1500 Token，输出仅 13 Token；
  • 对话服务的输入长度中位数为 1020 Token，输出中位数为 129 Token，且输出长度近似呈双峰分布。

即使采用能够把 Prompt 与 Decode 放入同一批次的 mixed continuous batching，机器也没有持续获得理想的大 Batch。对话轨迹中，60%–70% 的时间只运行了不超过 20 个活跃 Token；代码轨迹由于输出短，超过 20% 的时间实际上只有一个 Token 在运行。

1.3 两个阶段对 Batch 的反应正好相反

Prompt 的算术强度高，增加输入 Token 可以更充分地使用 GPU 计算单元，但超过某一点后，吞吐反而下降。论文在两种模型上都观察到：Prompt 的批量 Token 数超过 2048 后，吞吐开始降低。以生产轨迹的输入中位数换算，这甚至对应不到两个请求。

Decode 则不同。单步只处理每条请求最新的一个 Token，扩大 Batch 能把更多请求的矩阵—向量操作合并起来，吞吐一直增长到 Batch Size 64，随后才因显存不足而停止。与此同时，Batch Size 从 1 增至 64 时，TBT 只增长约 2×。

图 1（原论文图 6）：Prompt 吞吐在批量 Token 数较小时见顶，Decode 吞吐则随 Batch 扩大而持续上升，直到显存容量成为限制。

这意味着统一的批处理策略无法两全：Prompt 应限制批量以保护 TTFT 和吞吐，Decode 却应该尽可能聚合更多请求。

1.4 计算、显存和功耗也不对称

Prompt 同时计算大量输入 Token，表现为计算受限；Decode 每轮都要读取模型权重和不断增长的 KV Cache，更容易受显存容量与带宽限制。两者的功耗曲线也印证了这一点：Prompt 功耗随 Batch 增大而逼近 GPU 的 TDP，Decode 即使扩大 Batch，功耗仍大致停留在 TDP 的一半附近。

图 2（原论文图 8）：Prompt 的功耗随批量增长并接近 TDP，Decode 的平均与峰值功耗对 Batch 大小都不敏感。

论文进一步把 H100 GPU 的功耗上限从 700 W 降至 350 W：Prompt 延迟显著恶化，Decode 延迟却几乎不变。硬件代际的作用也不同。与 A100 相比，H100 的计算能力提升 3.43×，但 HBM 带宽只提升 1.64×、容量仍为 80 GB；实测 H100 对 TTFT 的改善明显大于对 TBT 的改善。因此，最新、计算能力最强的 GPU 应优先承担 Prompt，Decode 则有机会使用旧一代 GPU 或较低功耗配置。

到这里，Splitwise 的出发点已经清楚：它不是把一条相同的计算简单切成两半，而是让计算密集阶段与内存密集阶段分别接受合适的资源管理。

二、Splitwise 的总体架构

Splitwise 将预装同一模型的机器组织为三个池：

  • Prompt Pool：执行 Prompt，生成首 Token 与 KV Cache；
  • Token Pool：接收 KV Cache，继续执行 Decode；
  • Mixed Pool：在负载升高或两侧不平衡时临时承接另一阶段，减少静态分池造成的资源碎片。

一条新请求到达后，集群级调度器会同时选择一台 Prompt 机器和一台 Token 机器。Prompt 机器完成各层计算并把 KV Cache 发往目标机器，Token 机器随后生成余下输出。三个池不是不可变的物理分区：负载高时，调度器可以把相反角色的任务送入 mixed pool；待混合任务排空后，机器回到原来的角色。若负载分布长期偏离部署假设，系统再以较粗粒度重新划分 Prompt Pool 与 Token Pool。

图 3（原论文图 10）：集群级调度器管理 Prompt、Token 与动态 Mixed Pool；机器级调度器负责本机队列、显存和批处理，阶段间通过 InfiniBand 传递 KV Cache。

2.1 两级调度各管一层问题

**集群级调度器（Cluster-Level Scheduler，CLS）**负责机器池管理和请求路由。它使用 Join-the-Shortest-Queue（JSQ）策略，队列长度按待处理 Token 数定义，而非简单按请求数计算。机器会周期性上报剩余显存和等待队列，但不必在每轮模型迭代后都与 CLS 通信。

CLS 同时分配 Prompt 与 Token 机器还有一个重要原因：系统可以提前知道 KV Cache 的目的地，从而把传输与 Prompt 计算重叠起来。当目标池队列超过阈值时，CLS 先寻找 mixed pool；若仍无容量，才让对侧机器暂时处理另一种任务。

**机器级调度器（Machine-Level Scheduler，MLS）**根据阶段采用不同策略：

  • Prompt 机器按 FCFS 调度，并把一个批次的 Prompt Token 总数限制在 2048 以内；这是论文实验平台上的经验阈值，不是跨模型、跨硬件不变的常数。
  • Token 机器同样按 FCFS 调度，但在显存允许时尽量扩大 Batch，接近容量上限后才让新 Token 排队。
  • Mixed 机器为满足 TTFT SLO，会优先调度新 Prompt，必要时抢占 Decode；系统又会随等待时间提高 Decode 的优先级，并限制单个请求可被抢占的次数，以避免饥饿。

这种设计的关键价值，是将“全局分池与路由”和“局部 Batch 与显存控制”拆开：CLS 不需要介入每次模型迭代，MLS 也不需要理解整个集群的负载。

三、真正的难点：如何搬运 KV Cache

阶段拆分会引入基线系统不存在的关键开销：Prompt 机器生成的 KV Cache 必须先到达 Token 机器，Decode 才能继续。

KV Cache 大小与 Prompt Token 数近似成正比。最直接的做法，是等整个 Prompt 阶段结束后再一次性传输；但这会把通信完整地串在首 Token 与第二个 Token 之间，直接拉高第二个 Token 的延迟、TBT 和 E2E。Splitwise 因而采用两种自适应路径：

  1. 小 Prompt 使用串行传输。 数据量小时，同步与并发传输本身的额外开销可能得不偿失；论文的 H100 实现对小于 512 个批量 Token 的 Prompt 采用这一路径。
  2. 大 Prompt 使用逐层异步传输。 某一 Transformer 层计算完成后，该层 KV Cache 已经就绪，系统立刻异步发送它，同时 Prompt 机器继续计算下一层，从而把大部分通信隐藏在计算之后。

作者在 vLLM 上实现该机制，并使用 MSCCL++ 的零拷贝、单边 put 原语通过 InfiniBand 发送数据。每个请求使用独立信号量通知 Token 机器；vLLM 的 KV Block 会尽量按连续内存合并，以减少传输次数。这种逐层流水需要细粒度同步，可能干扰较短 Prompt 的计算，也正是系统没有对所有请求一律启用它的原因。

图 4（原论文图 14）：串行传输开销随 Prompt 增长，逐层传输把未被计算隐藏的延迟稳定在 A100 约 8 ms、H100 约 5 ms。

在两台机器的无 Batch 实验中，传输相对 Prompt 计算的开销低于 7%。对代码轨迹，串行传输在大 Prompt 下最多增加约 3% 的 E2E，而 Splitwise 的自适应方案把 E2E 开销压到 0.8%。从流式体验看，Splitwise 让第二个 Token 的延迟增加 16.5%，串行传输则会增加 64%。

这些数字不是说通信已经“免费”。它们依赖高速后端网络：实验中的 A100 与 H100 环境分别使用 200 Gbps 和 400 Gbps InfiniBand。更准确的结论是：只要在层粒度暴露数据就绪时机，阶段拆分新增的数据搬运就可以从完整串行停顿变成多数可隐藏的流水开销。

四、硬件不是只有一种拆法

Splitwise 用两个字母表示 Prompt 与 Token 机器的类型，并评估四种部署：

配置 Prompt Pool Token Pool 设计意图
Splitwise-AA DGX-A100 DGX-A100 复用成本较低、供给更充足的旧一代 GPU
Splitwise-HH DGX-H100 DGX-H100 保持硬件同构，只改变阶段管理方式
Splitwise-HA DGX-H100 DGX-A100 Prompt 用更强计算，Decode 用更高性价比硬件
Splitwise-HHcap DGX-H100 限功耗 DGX-H100 同构部署下回收 Decode 用不到的功耗预算

HHcap 并不是把整机简单减半：论文将 Token 机器的每张 H100 GPU 限制在额定功耗的 50%，折算后 Token 机器的整机供电约为未限功耗 H100 机器的 70%。

机器数量同样不能凭阶段耗时比例直接推算。作者构建事件驱动的 SplitwiseSim，以真实硬件上不同输入、输出和 Batch 大小的 profiling 数据建立分段线性性能模型。模型在 80:20 的训练/测试划分上平均绝对百分比误差低于 3%，模拟器还使用生产负载进行了超过 50K 次迭代的端到端交叉验证。

给定请求轨迹、目标模型、硬件性能模型、TTFT/TBT/E2E SLO、吞吐约束和成本或功耗目标后，模拟器搜索 Prompt 与 Token 机器数量。例如，论文针对代码负载和 70 RPS 峰值搜索 Splitwise-HH 时，最低成本的可行配置是 27 台 Prompt 机器与 3 台 Token 机器。这个 27:3 不是通用比例，而是特定模型、轨迹、SLO 和硬件下的搜索结果。

五、评估结果应该怎样读

论文评估的集群级结果主要来自 SplitwiseSim，但其性能模型与 KV Cache 通信模型建立在 A100/H100 实机测量之上。基线集群同样使用 mixed continuous batching；所有设计都必须同时满足 TTFT、TBT 和 E2E 的 P50、P90 与 P99 共九项 SLO。因此，下列收益不能理解成脱离延迟约束的裸吞吐峰值。

5.1 同功耗：把闲置算力换成吞吐

在同功耗、吞吐优先的对话服务配置中，基准功耗等于 40 台 DGX-H100，或 70 台 DGX-A100。与 Baseline-A100 相比：

  • Splitwise-AA 在相同功耗与成本下达到 2.15× 吞吐；
  • Splitwise-HA 在相同功耗下达到 1.18× 吞吐，同时成本低 10%。

这里 AA 能获益，不是因为 A100 单卡突然比 H100 快，而是阶段分池让 Decode 更容易形成大 Batch，也避免大 Prompt 混入后持续扰动 TBT。到高负载时，mixed pool 会接管更多跨阶段任务，批量分布逐渐接近基线，从而减少固定分池带来的碎片。

图 5（原论文图 18）：左图比较同功耗设计的机器数、吞吐与成本，右图比较同成本设计的机器数、吞吐与功耗，均以 Baseline-A100 归一化。

5.2 同成本：旧 GPU 可以用更多空间换吞吐

在成本相同的配置中，Splitwise-AA 相比 Baseline-H100 获得 1.4× 吞吐，但代价是功耗增加 25%、机架空间达到 2×。这更适合不受供电与空间约束、又希望使用较易获得的 A100 的客户；对已经触及数据中心功耗墙的云服务商，它未必是最佳点。

5.3 同吞吐：分别优化功耗或成本

当目标改为保持与 Baseline-H100 相同的吞吐时：

  • 功耗优化的 Splitwise-HHcap 在成本与空间相同的情况下，将功耗降低 25%；
  • 成本优化的 Splitwise-AA 将成本降低 25%，但会占用更多机器。

图 6（原论文图 19）：左图按最低功耗配置同吞吐集群，右图按最低成本配置；不同目标会选择不同的 Prompt/Token 机器组合。

这也解释了为什么论文不给出唯一的“最佳 Splitwise 集群”。吞吐、租用成本、供电和机架空间互相制约；阶段拆分的价值是扩大可选设计空间，而不是让一个固定配置在所有维度同时占优。

5.4 对负载变化的适应能力

作者还把对话轨迹放到为代码轨迹配置的集群上，并把 Llama 2 70B 放到为 BLOOM-176B 配置的集群上。AA 和 HH 可以依靠 mixed pool 基本吸收轨迹变化；HA 与 HHcap 因两个池的硬件能力或功耗配置不对称，相比专门为对话优化的配置出现 7% 吞吐下降，但仍优于两种基线。

这说明 mixed pool 不只是低负载下的“备用池”，还是 Splitwise 面对输入/输出长度变化时的重要安全阀。不过，它只能缓解阶段比例的波动，不能消除长期错误配置；持续偏移仍需要重新规划机器池。

六、Splitwise 的边界与代价

6.1 它最适合受交互延迟约束的在线服务

对于没有严格 TTFT/TBT SLO、可以把集群压到极高负载的离线批任务，所有机器最终都会进入 mixed pool。此时 Splitwise 退化为按机器数相同的混合批处理基线，阶段拆分优势基本消失。论文报告，重压下 Baseline-A100 与 Splitwise-AA 的吞吐成本比同为 0.89 RPS/$，Baseline-H100 与 Splitwise-HH 同为 0.75 RPS/$。

6.2 高速互连是重要前提

论文假设 Prompt 与 Token 机器之间有 InfiniBand。H100 与 A100 跨代直连虽然技术上可行，却不是云数据中心普遍提供的标准拓扑，这使 Splitwise-HA 的落地比同构方案更复杂。作者认为即使网络带宽降低 10×，优化后的传输仍可能有收益，并提出通过 RoCE 或压缩 KV Cache 进一步降低要求；但这些属于讨论和未来方向，并没有在本文中完成等价验证。

6.3 故障恢复与调度扩展性仍待完善

当前设计在 Prompt 或 Token 机器故障时会从头重启请求，与当时的常见推理系统相似。定期把 KV Cache 写入内存数据库可以减少重算，但安全、高效的恢复协议不在论文范围内。另一方面，单个 CLS 在超大规模集群中可能成为瓶颈，未来需要借鉴分区或复制式集群调度器。

6.4 对话状态复用会改变数据流

论文按当时的 Chat API 形态假设每轮请求携带完整上下文，并出于安全隔离考虑，不跨请求复用 KV Cache。如果未来服务长期保存会话状态，Prompt 的显存特征会变化；为了处理下一轮对话，系统还可能需要把更新后的 KV Cache 从 Token 机器传回 Prompt 侧。此时单向的阶段流水需要扩展。

6.5 结论受模型与硬件年代约束

评估对象是 Llama 2 70B、BLOOM-176B、A100 与 H100。论文的核心方法依赖自回归模型普遍存在的 Prompt/Decode 两阶段，而不是某个特定模型结构；但 2048 Token 的 Prompt 批量阈值、512 Token 的传输策略切换点以及具体机器比例，都来自这套软硬件与轨迹，迁移到新模型、新 GPU 或 MoE 时必须重新 profiling 和规划。

七、总结与启示

Splitwise 最值得记住的并不是“Prefill/Decode 分离”这六个字，而是它把这一观察落实成了完整系统：

  1. 用生产轨迹证明两个阶段在 Batch、延迟、显存和功耗上的需求确实不同；
  2. 用 Prompt、Token 与动态 Mixed Pool 同时获得专业化和负载适应性；
  3. 用 CLS/MLS 两级调度分别处理集群路由与机器内批处理；
  4. 用逐层异步传输把 KV Cache 搬运隐藏在 Prompt 计算之后；
  5. 最后以实机 profiling 驱动的模拟器搜索机器类型、数量、成本与功耗，而不是预设一种固定集群。

它揭示了一个更一般的系统设计原则：当同一请求的不同阶段受不同资源约束时，统一硬件与统一调度未必真的通用；只要状态交接的成本可以被控制，按阶段专门化就可能同时改善利用率和用户体验。

Splitwise 也没有回避这条路线的代价。高速网络、额外调度层、机器池碎片、异构运维与故障恢复都会增加复杂度。它给出的答案不是“拆分一定更快”，而是更严谨的条件句：对于必须满足 TTFT、TBT 与 E2E 尾延迟的在线自回归推理，阶段拆分提供了一个值得搜索的新设计空间。
