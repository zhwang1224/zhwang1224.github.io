NVLink 01｜为什么需要 NVLink

发表于 2026-09-19 分类于 人工智能系统 ， 高性能互连 阅读时长 ≈ 10 分钟
从异构计算与多 GPU 节点的发展出发，理解 NVLink 如何缓解通信瓶颈、改善应用扩展性，并与 Unified Memory 配合简化编程。

GPU 的计算能力不断提高，把更多 GPU 放进一台服务器，也就成为提升性能的自然选择。但多张 GPU 只有及时交换数据，才能共同推进一个任务。计算能力越强，数据传输跟不上的问题就越容易暴露出来。

NVLink 正是在这样的背景下提出的。理解它，需要把处理器、互连和编程模型放在一起看：CPU 与 GPU 如何分工，多 GPU 为什么受到通信限制，更快的互连又能给应用带来什么。

本文沿着 Mark Harris 于 2014 年发表的 How NVLink Will Enable Faster, Easier Multi-GPU Computing 展开，并补充简单的性能分析。

1. 异构节点：为什么需要 CPU 和 GPU 协作

CPU 和 GPU 的设计侧重点不同。CPU 适合处理复杂控制流和串行依赖较强的工作；GPU 则利用大量并行线程提高吞吐量。异构计算把同一个应用中的不同部分交给合适的处理器，因而需要同时考虑计算分工与数据传输。CUDA Best Practices Guide

可以用一个迭代计算任务理解这种分工：CPU 准备输入、决定执行流程，GPU 对大量数据执行相同或相近的操作，然后 CPU 根据结果决定下一步。如果一次传输之后，数据能够在 GPU 上被反复使用，那么传输成本就可以由后续计算平摊。

这里的关键是“反复使用”。假设把一组数据传给 GPU 需要 1 ms，此后可以执行 100 ms 的计算，那么传输占比很小。若每次只计算 0.1 ms 就要返回 CPU，计算加速带来的收益便很容易被往返传输抵消。这两个数字只是说明比例关系，与具体硬件无关。

因此，异构节点的性能不仅取决于 CPU 和 GPU 各自有多快，还取决于任务如何切分，以及切分边界上要搬运多少数据。

2014 年官方文章以 Titan 以及当时规划中的 Summit、Sierra 为背景，提出了更紧密的 CPU–GPU 节点集成需求。随着每个 CPU 配置的 GPU 数量增加，节点内互连的重要性随之上升。原文：异构节点与多 GPU 趋势

2. 更多 GPU，为什么未必带来等比例加速

把四个彼此独立的任务分给四张 GPU，通常比较容易利用新增算力。把同一个任务拆给四张 GPU，则需要处理子任务之间的依赖。

继续增加 GPU，单卡负责的网格区域会变小，计算时间随之下降；通信量却未必按同样比例下降。以正方形子区域为例，边长为 m 时，内部计算量大致随 m² 增长，边界交换量随 m 增长。子区域越小，边界相对于内部的比例越高。

这就是固定问题规模下的强扩展容易遇到的限制：GPU 越多，每张卡计算得越少，但通信在总时间中的比例可能越来越大。

一种优化办法是让内部计算与边界交换重叠。它要求两者之间没有数据依赖，也要求执行资源允许并发。如果独立计算已经很短，仍有一部分通信只能表现为等待。CUDA 的异步传输和并发执行机制可以帮助隐藏传输开销，但重叠程度取决于实际工作负载。CUDA Best Practices Guide：异步传输与重叠

3. NVLink：为节点内的数据交换提供更快的通道

PCIe 已经可以连接 CPU、GPU 和其他设备。在受支持的拓扑上，GPU 还可以通过 PCIe P2P 直接访问另一张 GPU 的内存，不必先把数据放进主机内存。因此，“GPU 之间能不能直接通信”和“通信通道是否足够快”是两个问题。CUDA 多 GPU 编程指南

当多 GPU 的通信需求增加时，已有路径的带宽和共享关系就成为系统约束。提高计算吞吐量，并不会自动提高这条路径的吞吐量。

NVLink 为此增加了高带宽互连。原文同时讨论了 GPU–GPU 连接，以及受支持 CPU 与 GPU 之间的连接；它并不是只为 GPU 之间交换数据而提出的。原文：NVLink 高速互连

图 1 不同 GPU 数量下的连接示例。绿色为 NVLink，灰色为 PCIe。图中的带宽标注属于 2014 年的设计示例。图片来源：NVIDIA 原文图 4。

这张图值得从“路径”而不是“数字”来读。CPU 仍通过灰色的 PCIe 路径连接 GPU，GPU 之间另外增加绿色通道。主机通信与 GPU 间的数据交换可以使用不同的连接。

另一个要点是链路分配。同样数量的端口可以集中连接一个对端，也可以分配给多个对端。因而评估多 GPU 系统时，既要看每张 GPU 总共有多少互连带宽，也要看具体通信对象之间分到了多少带宽。

这可以类比为一组待安排的传输任务：若所有数据都发给同一个邻居，集中链路可能更有利；若不同 GPU 之间都需要交换，覆盖更多通信对又变得重要。拓扑与应用的数据交换模式应当一起考虑。

至于通过什么接口使用这些路径，CUDA 提供 peer 拷贝和 peer 内存访问等机制。能否直接访问对端显存，需要结合设备与 PCIe/NVLink 拓扑判断。应用仍然需要正确划分数据、安排计算并处理同步，更快的互连不会自动完成这些工作。CUDA 多 GPU 编程指南

它解释了为什么不同应用对互连升级的反应差异很大。若绝大部分时间都在计算，压缩少量通信只能带来有限收益；若通信已经占据主要时间，提高带宽就可能显著缩短执行过程。

NVIDIA 原文用数据交换、排序、3D FFT 等工作负载展示了这种收益，并报告了部分应用接近或超过两倍的预测加速。这些结果来自当时的模型系统比较，不能当作任意程序或今天硬件的实测结论。原文：应用性能预测

对应用设计而言，更快的互连还有一个作用：扩大值得使用多 GPU 的问题范围。

假设某个问题在两张 GPU 上运行时，节省的计算时间还不够抵消新增通信，那么使用多 GPU 没有收益。缩短通信后，同一个问题可能跨过这一临界点。互连改善的不仅是已有多 GPU 任务的速度，也可能是多 GPU 并行本身的适用范围。

5. 更容易编程：NVLink 与 Unified Memory 的配合

CPU 与 GPU 拥有不同的物理内存时，显式内存管理通常需要分别分配空间，再安排输入和结果的拷贝。程序还必须跟踪哪一份数据已经更新、何时可以交给另一侧使用。

Unified Memory 为 CPU 和 GPU 提供可通过同一个指针访问的托管分配，由系统管理数据迁移，减少应用中显式维护两套数据的负担。它与统一虚拟寻址（UVA）不同：统一地址空间本身并不负责把数据迁移到使用它的处理器附近。Unified Memory in CUDA 6

可以把两层作用分开理解：

层次 负责什么
Unified Memory 简化内存使用方式，并由系统管理数据的位置与迁移
NVLink 在具备相应连接的处理器之间，提高数据传输能力

自动管理不会消除物理数据移动。即使代码中没有显式拷贝，处理器访问所需数据时，仍可能发生迁移或远程访问。相应路径越快，完成这些操作的成本就越低。

这里需要区分 CPU–GPU 和 GPU–GPU 的物理连接。如果系统只有 GPU 之间连接了 NVLink，CPU 仍经 PCIe 访问 GPU，就不能据此认为 CPU–GPU 的数据迁移也获得了 NVLink 带宽。

编程简化也不意味着无需考虑局部性。假设 CPU 和 GPU 每做一点工作就交替访问同一批数据，频繁的数据移动仍可能很昂贵。将连续的 GPU 工作组织在一起、增加本地数据复用，依然有意义。NVIDIA 的 Unified Memory 介绍也指出，经过精细安排的显式异步拷贝可能获得更好的性能。Unified Memory 的便利性与性能边界

由此看，NVLink 参与解决的是异构计算中的一个基础矛盾：处理器各自擅长的工作不同，但共同完成应用又要求它们不断交换数据。更快的连接降低了协作成本，让计算分工和内存管理拥有更大的选择空间。
