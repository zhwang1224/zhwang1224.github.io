InfiniBand RDMA 编程入门

1. RDMA 体系结构

  • RDMA 是一种通信能力：远程直接内存访问 (RDMA) 允许从一台主机（存储或计算主机）的内存直接访问另一台主机的内存，而无需远程操作系统和 CPU 的参与，从而降低延迟、减少 CPU 负载并提高带宽，进而提升网络和主机性能。相比之下，TCP/IP 通信通常需要复制操作，这会增加延迟并消耗大量 CPU 和内存资源。
  • InfiniBand（IB） 是一种高速、低延迟、低 CPU 开销、高效且可扩展的服务器与存储互连技术。其关键能力之一是原生支持 RDMA。IB 可在服务器之间、服务器与存储之间传输数据，而主机 CPU 不参与数据路径。IB 使用 I/O 通道通信（每主机最多约 1600 万条），每条通道提供虚拟化 NIC/HCA 的语义。
  • Virtual Protocol Interconnect（VPI） 架构在网卡与交换机之间提供高性能、低延迟且可靠的通信手段，并同时支持 InfiniBand 与以太网语义。VPI 适配器或交换机可以按端口配置为提供 InfiniBand 或以太网语义。
  • RoCE 是 IBTA 定义的“以太网上的 RDMA”标准。它为以太网提供真正的 RDMA 语义，不需要 iWARP 那种复杂且性能较低的 TCP 传输。RoCE 是目前最高效的低延迟以太网方案。它所需的 CPU 开销非常低，并利用数据中心桥接以太网（Data Center Bridging Ethernet）中的优先级流控（Priority Flow Control）实现无损连接。
  • Verbs 是面向 RDMA 设备的编程抽象。Linux 用户态通常通过 libibverbs 使用它；rdma-core 中的 provider 再把通用 Verbs 映射到具体 HCA 驱动。

目前支持 RDMA 的技术主要有三种：InfiniBand、以太网 RoCE，以及以太网 iWARP。这三项技术可共用同一套用户 API，但物理层和链路层不同。就以太网方案而言，RoCE 相对 iWARP 具有明显的性能优势——无论是延迟、吞吐还是 CPU 开销。许多主流方案都支持 RoCE，并且它已被纳入 Windows Server 软件（InfiniBand 同样如此）。

RDMA 结构中的主要硬件/管理组件：

  • 主机通道适配器（HCA / Network Adapter） ：HCA 是 IB 终端节点（例如服务器）接入 IB 网络的连接点。它们相当于以太网网卡（NIC）。
  • 距离延伸器（Range Extenders） ：用于延长 IB 链路距离。
  • 子网管理器（Subnet Manager） ：发现拓扑、分配本地标识符 LID、计算并下发路由、管理交换机转发表。
  • 交换机（Switches） ：按 SM 编程的转发表转发报文，支持 VL 等 QoS 能力。许多交换机内置子网管理器。

2. RDMA 为什么快

Socket（套接字）是操作系统提供的网络通信抽象。程序通过 Socket 使用 TCP、UDP 等协议收发数据，而不需要直接操作网卡、IP 数据包或 TCP 状态机。在 Linux 中，Socket 是一种内核对象，由内核维护的网络对象，应用程序通过文件描述符访问它。

传统 Socket 路径通常需要协议栈处理、内核缓冲、系统调用和数据复制。RDMA 的稳定数据面让应用提前创建队列、注册缓冲区，随后通过用户态队列向 HCA 提交工作。它减少的是每条消息的 CPU 与软件路径开销。

TCP/IP 的每一次操作都需要操作系统介入，并且线路两端都包含缓冲拷贝。当应用想发送一个分组时，操作系统把这些字节放入属于操作系统的、主存中的匿名缓冲；字节传输完成后，操作系统再把其缓冲中的数据拷贝到应用的接收缓冲。每当有分组到达，这一过程就会重复，直到整段字节流收完。因拥塞而丢失的分组，由 TCP 负责重传。

在 InfiniBand 中，一条完整消息会直接投递给应用。一旦应用请求传输一次 RDMA Read 或 Write，InfiniBand 硬件会按需要把出站消息分段成多个分组，分组大小由结构路径的最大传输单元（path MTU）决定。这些分组经 InfiniBand 网络传输，并直接写入接收应用的虚拟缓冲，在那里被重新组装成完整消息。整条消息接收完成后，才会通知接收应用。因此，在整条消息被投递进接收应用的缓冲之前，发送方和接收方应用都不必介入。

3. Verbs 的资源模型

Verbs 编程需要理解资源之间的关系。可以先把它们分成三层：

  • 设备层：打开 RDMA 设备，得到操作设备所需的 Context；
  • 资源层：在 Context 下创建 PD、CQ，并在 PD 中注册 MR、创建 QP；
  • 请求层：应用把 WR 提交到 QP，HCA 执行后再通过 CQ 返回完成结果。

它们之间的依赖关系如下：

flowchart LR
    DEV[ibv_device] --> CTX[ibv_context]
    CTX --> PD[Protection Domain]
    CTX --> CQ[Completion Queue]
    PD --> MR[Memory Region]
    PD --> QP[Queue Pair]
    QP --> SQ[Send Queue]
    QP --> RQ[Receive Queue]
    SQ -. completion .-> CQ
    RQ -. completion .-> CQ
    MR -. local access: lkey .-> QP
    RQP[Remote QP] -. remote access: addr + rkey .-> MR

其中，PD 决定“哪些 QP 可以访问哪些 MR”，QP 负责接收工作请求，CQ 负责报告完成结果。理解这三者的分工，基本就掌握了 Verbs 的资源模型。

3.1 Device 与 Context

ibv_device 表示系统中可用的 RDMA 设备。应用先通过 ibv_get_device_list() 枚举设备，再调用 ibv_open_device() 打开其中一个设备，得到 ibv_context。

Context 是应用操作该设备的入口。后续查询端口、分配 PD、创建 CQ 等操作，都需要使用这个 Context。它只代表本地设备上下文。

3.2 Protection Domain（PD）

Protection Domain（保护域）是本地资源之间的隔离边界，通过 ibv_alloc_pd() 创建。MR 注册到某个 PD，QP 也隶属于某个 PD；QP 只能使用同一 PD 中 MR 的 lkey。

因此，PD 本身不传输数据，也不分配缓冲区。它的作用更像一个“权限容器”：把可以协同工作的 QP 和 MR 归为一组，防止 QP 误用其他保护域中的内存。

3.3 Memory Region（MR）

应用不能把一段普通虚拟地址直接交给 HCA 或远端访问。使用缓冲区前，需要通过 ibv_reg_mr() 将它注册为 Memory Region。注册过程把地址范围、所属 PD 和访问权限告知 HCA，并返回三个关键信息：

  • addr 与 length：MR 覆盖的本地虚拟地址范围；
  • lkey：本地 WR 在 SGE 中引用该内存时使用；
  • rkey：远端执行 RDMA Read、Write 或 Atomic 时使用。

lkey 供本地 HCA 校验内存访问，不能发送给对端代替 rkey。rkey 则应视为一种访问凭据，只应通过可信的控制面提供给确实需要访问该 MR 的对端。

MR 始终允许本地 HCA 读取；其他能力由注册时的访问标志决定：

标志 含义
IBV_ACCESS_LOCAL_WRITE HCA 可写本地 MR；Receive 缓冲区和 RDMA Read 的本地目标都需要它
IBV_ACCESS_REMOTE_WRITE 允许远端向该 MR 执行 RDMA Write
IBV_ACCESS_REMOTE_READ 允许远端从该 MR 执行 RDMA Read
IBV_ACCESS_REMOTE_ATOMIC 允许远端原子操作，且设备必须支持

若设置 REMOTE_WRITE 或 REMOTE_ATOMIC，还必须设置 LOCAL_WRITE。

3.4 Queue Pair（QP）

Queue Pair 是数据面工作的核心。每个 QP 由两条队列组成：

  • Send Queue（SQ）：接收 Send、RDMA Read、RDMA Write、Atomic 等发送侧 WR 工作请求；
  • Receive Queue（RQ）：接收 Receive WR，为到来的 Send 消息预先准备缓冲区。

创建 QP 时，需要指定：

  • 传输类型，如 RC、UC 或 UD；
  • Send CQ 与 Receive CQ；两者可以是同一个 CQ；
  • 最大 Send/Receive WR 数与每个 WR 的最大 SGE 数；
  • 是否让所有 Send WR 自动产生 Completion。

常见的 QP 传输类型对比如下：

类型 连接方式 可靠性与顺序 支持的主要操作
RC（Reliable Connection） 一对一 可靠、按序，传输层负责重传 Send/Recv、RDMA Read/Write、Atomic
UC（Unreliable Connection） 一对一 不提供可靠重传 Send/Recv、RDMA Write
UD（Unreliable Datagram） 一对多 不保证送达或按序 Send/Recv；消息不能超过路径 MTU

本教程后续使用 RC。它的功能最完整，也最适合用来理解连接建立、双边消息和单边内存访问。

3.5 Completion Queue（CQ）

Completion Queue 用于报告工作请求的完成状态。HCA 生成的底层记录称为 CQE（Completion Queue Entry）；应用调用 ibv_poll_cq() 后，得到的是 ibv_wc（Work Completion）。

一个 CQ 可以被多个 QP 共用，Send Queue 和 Receive Queue 也可以绑定同一个 CQ。应用通常通过 WC 中的以下字段判断完成的是哪项工作：

  • wr_id：提交 WR 时由应用填写的 64 位标识，完成时原样返回；
  • status：操作成功或失败的状态；
  • opcode：完成的操作类型；
  • byte_len：接收等操作实际完成的字节数。

不是每个成功的 Send WR 都必须产生 CQE。当 sq_sig_all=0 时，应用可以只为需要完成通知的 WR 设置 IBV_SEND_SIGNALED，从而减少 CQ 压力；被实际消耗的 Receive WR 则会产生完成通知。

需要特别注意：CQ 的容量有限，应用必须及时轮询。若 CQ 发生 overrun，通常会触发 IBV_EVENT_CQ_ERR，该 CQ 将无法继续正常使用。

3.6 WR、WQE、SGE 与 WC

这四个缩写描述了一次请求从提交到完成的不同阶段：

名称 所在阶段 作用
WR（Work Request） 提交前 应用构造的工作请求，描述要执行的操作
SGE（Scatter/Gather Element） WR 内部 用addr + length + lkey 描述一段本地缓冲区；一个 WR 可包含多个 SGE
WQE（Work Queue Element） 提交后 WR 被放入 SQ 或 RQ 后，在工作队列中的表示
WC（Work Completion） 完成后 应用从 CQ 取出的完成结果

一次典型操作可以概括为：

  1. 应用准备数据缓冲区，并将其注册为 MR；
  2. 用一个或多个 SGE 描述缓冲区，再构造 WR；
  3. 调用 ibv_post_send() 或 ibv_post_recv()，把 WR 提交为 WQE；
  4. HCA 取出并执行 WQE；
  5. 需要通知时，HCA 向 CQ 写入 CQE，应用通过 ibv_poll_cq() 得到 WC。

ibv_post_send() 或 ibv_post_recv() 返回 0，只说明 WR 已成功提交，不代表数据传输已经完成。调用返回后，栈上的 WR 和 SGE 描述符可以销毁，但它们引用的数据缓冲区仍必须保持注册且不可被不安全地复用，直到对应操作完成。

IBV_SEND_INLINE 是一个例外：HCA 会在提交时把待发送数据复制到 WQE 中，因此 ibv_post_send() 成功返回后，应用即可复用源缓冲区。不过，QP 队列空间等资源仍要等该 WR 完成后才能回收。

4. 四类数据操作：消息语义与内存语义

操作 需要远端预投 Receive 需要远端地址 / rkey 远端通常有 CQE
Send / Receive 是 否 是，IBV_WC_RECV
RDMA Write 否 是 否
RDMA Write with Immediate 是，用于通知 是 是，带 immediate data
RDMA Read 否 是 否
Atomic 否 是 否

4.1 Send/Recv：双边消息语义

接收端先执行 ibv_post_recv()，把本地缓冲区交给 RQ；发送端以 IBV_WR_SEND 提交 Send WR。消息到达时，HCA 从 RQ 取出一个 Receive WQE，把 payload scatter 到它的 SGE 中，并在接收 CQ 生成 WC。

Send/Recv 不暴露接收缓冲区地址给发送端，也不需要交换 MR 的 rkey。发送端只知道自己连接的是哪条远端 QP。若远端没有可用 Receive，RC 会收到 RNR NAK 并按 rnr_retry 重试；重试耗尽后得到 IBV_WC_RNR_RETRY_EXC_ERR。

4.2 RDMA Write：单边写

发起端提供本地 SGE，以及远端 remote_addr + rkey。远端 HCA 校验权限和边界后把数据直接放到目标 MR，不消耗普通 Receive WQE，也默认不在远端产生 CQE。

远端仍要事先注册并授权内存，通过控制面安全地发布地址与 rkey，还要知道何时数据完整可见、何时可以复用或撤销缓冲区。常见做法是在同一 RC QP 上使用 Write with Immediate，或在 Write 后再发一个 Send 作为通知。

Write with Immediate 的 payload 仍写入 remote_addr 指向的 MR；被消耗的 Receive WQE 用于生成远端通知，而不是承载这段 RDMA payload。Immediate Data 只有 32 位，并按网络字节序传输。

4.3 RDMA Read 与 Atomic

RDMA Read 把远端 MR 的内容拉到发起端本地 SGE。远端需开放 REMOTE_READ，发起端本地目标需允许本地写。操作完成只在发起端产生 WC；远端应用默认不会得到通知。并发 Read/Atomic 数还受两端 max_rd_atomic 与 max_dest_rd_atomic 约束。

RC 的 Compare-and-Swap 和 Fetch-and-Add 要求目标 MR 开放 REMOTE_ATOMIC，设备能力、对齐和操作宽度也必须满足要求。Verbs Atomic 只保证规定宽度上的设备级原子性，不会自动把更大的应用对象或持久化更新变成事务。

5. 一个 RC 连接的完整生命周期

收发两端通常先用 TCP 等带外通道交换连接参数，再把 QP 从 RESET 依次推进到 INIT、RTR 和 RTS：

sequenceDiagram
    participant A as 主机 A
    participant C as TCP / RDMA CM 控制面
    participant B as 主机 B
    A->>A: Context、PD、MR、CQ、QP
    B->>B: Context、PD、MR、CQ、QP
    A->>A: RESET → INIT，预投 Receive
    B->>B: RESET → INIT，预投 Receive
    A->>C: LID/GID、QPN、PSN、MTU
    B->>C: LID/GID、QPN、PSN、MTU
    C-->>A: B 的连接参数
    C-->>B: A 的连接参数
    A->>A: INIT → RTR → RTS
    B->>B: INIT → RTR → RTS
    A->>C: Ready
    B->>C: Ready
    A->>B: RDMA 数据面开始

6.1 创建本地资源

典型顺序是：

  1. ibv_get_device_list()、ibv_open_device()；
  2. ibv_query_port() 检查端口；
  3. ibv_alloc_pd()；
  4. 分配缓冲区并 ibv_reg_mr()；
  5. ibv_create_cq()；
  6. ibv_create_qp()；
  7. 把 QP 修改到 INIT；
  8. 在对端可能发送前预投足够的 Receive；
  9. 交换连接参数并进入 RTR、RTS。

6.2 建连究竟要交换什么

原生 IB 同一子网的最小 RC 路径通常需要：

  • 对端端口 LID；
  • 对端 QP Number；
  • 对端初始 Packet Sequence Number（PSN）；
  • 双方一致且不超过链路能力的 Path MTU。

只有 RDMA Read/Write/Atomic 才需要额外发布远端虚拟地址、长度和 rkey；Send/Recv 不需要。控制消息应使用固定宽度整数、明确版本和网络字节序。

6.6 TCP 控制面

TCP 在示例中承担三件事：交换连接参数、等待双方 QP 都进入 RTS、在退出前协调生命周期。RC 的可靠性只覆盖已经建立的数据路径，不负责服务发现、身份认证或密钥发布。

生产程序可用 librdmacm 把地址解析、路由解析、连接请求/接受和 QP 建连组织为事件流程。它能同时服务 InfiniBand、RoCE 和 iWARP，避免应用手工拼接 LID/GID 路径；建连完成后，数据操作仍然使用相同的 Verbs 对象和 WR。
