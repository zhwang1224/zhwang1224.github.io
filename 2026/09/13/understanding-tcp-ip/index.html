深入理解 TCP/IP

理解 TCP/IP 的关键，不是背下“七层模型”“三次握手”和“四次挥手”，而是回答三个问题：

  1. 数据在每一层以什么形式存在？
  2. 哪一层保证了什么，又明确不保证什么？
  3. 丢包、乱序、拥塞和连接中断发生时，系统如何恢复？

本文以一次 TCP 传输为主线，解释从应用写入字节，到路由器逐跳转发，再到接收端按序交付的完整过程。协议语义以 IETF 标准为准，工程行为则结合 Cloudflare 与 APNIC 的公开实践说明。

一、先纠正一个名字：TCP/IP 不是两个协议

TCP/IP 通常指 Internet Protocol Suite（互联网协议族），不是“TCP 加 IP”这两个协议的简单组合。它还包括 UDP、ICMP、ARP、IPv6 Neighbor Discovery、DNS、HTTP 等大量协议。

RFC 1122 将互联网主机的通信体系划分为应用层、传输层、互联网层和链路层。物理传输有时被单独列出，因此教材中也常见五层模型。OSI 七层模型有助于教学，但互联网实际协议并不要求与它逐层严格对应。

层次 主要问题 典型协议或技术 数据单位
应用层 数据的业务含义与交互规则 HTTP、TLS、DNS、SSH 消息或字节
传输层 进程到进程的通信 TCP、UDP、QUIC TCP 段、UDP 数据报、QUIC 分组
互联网层 跨网络寻址与路由 IPv4、IPv6、ICMP IP 数据报/分组
链路层 在一条本地链路上交付 Ethernet、Wi-Fi、ARP、IPv6 ND 帧
物理层 传输比特 电、光、无线电 比特

分层不是说上层完全不知道下层，而是划定责任边界：IP 尽力转发独立数据报；TCP 在端系统中提供可靠、有序的字节流；HTTP 决定字节代表请求、响应还是正文。

二、分层的真正价值：让每一层只解决一类问题

假设应用调用 write() 写入一段数据。发送端协议栈逐层增加首部，接收端再逐层去除：

flowchart LR
    A[应用数据] --> B[TCP 首部 + 数据<br/>TCP 段]
    B --> C[IP 首部 + TCP 段<br/>IP 分组]
    C --> D[链路层首尾 + IP 分组<br/>Ethernet 或 Wi-Fi 帧]
    D --> E[比特流]

这个过程称为封装。每一层只解释自己的首部：

  • 交换机主要依据链路层地址转发帧；
  • 路由器主要依据目的 IP 地址转发分组；
  • 目的主机依据 IP 首部中的协议号把负载交给 TCP，再依据端口交给相应 socket；
  • 应用最终解释收到的字节。

封装也解释了为什么“TCP 包”不是严谨的统一单位。TCP 产生的是 segment，IP 承载它形成 packet/datagram，Ethernet 再把 IP 分组装入 frame。日常交流可以笼统说“包”，分析问题时应指出所在层次。

三、一个 TCP 报文如何穿过互联网

以客户端通过 TCP 访问一台服务器为例，省略代理、负载均衡和隧道：

  1. 解析名称。 应用通常先通过 DNS 获得服务器 IP 地址。DNS 可能使用 UDP、TCP，或者运行在 TLS/HTTPS 之上；域名本身不参与 IP 路由。
  2. 选择端点。 操作系统选择源 IP 和临时源端口，应用给出目的 IP 与目的端口。
  3. 查路由表。 内核根据目的地址选择最具体的匹配路由、出接口和下一跳。若目的地不在本地子网，下一跳通常是默认网关。
  4. 解析下一跳的链路地址。 IPv4 Ethernet 常使用 ARP；IPv6 使用 Neighbor Discovery。这里解析的是下一跳，不是远端服务器的 MAC 地址。
  5. 建立 TCP 连接。 两端交换 SYN、SYN-ACK、ACK，同步初始序列号并协商只能在 SYN 中出现的选项。
  6. 发送数据。 TCP 把字节流组织成段，IP 为每个段选择路径，链路层把 IP 分组交给下一跳。
  7. 逐跳转发。 每台路由器移除收到的链路层封装，递减 TTL 或 Hop Limit，查询转发表，再为下一条链路重新封装。
  8. 接收与交付。 目的主机校验首部与校验和，TCP 去重、排序并确认数据，只有连续字节才按序交给应用。

因此，一次端到端传输同时包含两种范围不同的通信：

  • IP 地址和 TCP 状态主要是端到端的；
  • MAC 地址与链路层帧只在当前一跳有效，经过路由器通常会改变。

NAT、防火墙、隧道和负载均衡可能改写地址、端口或增加外层封装，但没有改变上述基本分工。

四、IP：只负责把数据报送向目的地

1. 地址、子网与路由

IP 提供的是无连接、尽力而为的数据报服务。它不保证分组一定到达，也不保证只到达一次、按发送顺序到达或在固定时间内到达。RFC 1122 明确把可靠性与流量控制放在端系统的传输层或应用层。

前缀 192.0.2.0/24 表示前 24 位是网络前缀。转发时，一个目的地址可能匹配多条路由，路由器通常采用最长前缀匹配，即选择最具体的条目。例如 192.0.2.128/25 比 192.0.2.0/24 更具体，默认路由 0.0.0.0/0 则只在没有更具体路由时兜底。APNIC 的最长前缀匹配介绍进一步说明了 FIB 与硬件查表过程。

IP 地址不是永久设备身份。它标识一个 IP 接口在当前网络拓扑中的位置；设备移动、DHCP 续租、NAT 或多网卡都会使“设备”和“地址”不再一一对应。

2. 转发是逐跳的

IPv4 的 TTL 与 IPv6 的 Hop Limit 每经过一台路由器至少减 1，减到 0 时分组被丢弃，路由器通常返回 ICMP Time Exceeded。这防止路由环路中的分组永远存在，也是 traceroute 能逐跳发现路径的基础。

路由器独立处理每个 IP 数据报。不同分组可能走不同路径，路径也可能在连接期间改变。传统 IP 路由器不需要维护 TCP 的连接状态；可靠性状态由通信端点保存。这正是互联网能够跨越大量异构链路并在部分路径故障时继续工作的基础设计。

需要区分三种完整性检查：

  • Ethernet FCS 检测一条链路上的帧错误，每一跳重新计算；
  • IPv4 首部校验和只保护 IPv4 首部，路由器修改 TTL 后需要更新；IPv6 基本首部没有首部校验和；
  • TCP 校验和覆盖 TCP 首部、数据和由 IP 地址等组成的伪首部，用于差错检测，但它不是加密，也不能抵抗恶意篡改。

3. MTU、MSS 与分片

MTU 是一条链路能够承载的最大 IP 分组大小，Path MTU 是端到端路径上各链路 MTU 的最小值。常见 Ethernet MTU 是 1500 字节，但它既不是互联网常量，也不包含 Ethernet 帧本身的全部开销。

IPv4 路由器可以对未设置 DF 的过大分组分片；IPv6 路由器不进行分片，源主机只能在收到 ICMPv6 Packet Too Big 后调整大小，必要时由源端使用 Fragment 扩展首部。RFC 8201 定义了 IPv6 Path MTU Discovery。实践中通常应避免 IP 分片：任一分片丢失都会使整个原始数据报无法重组，而且过滤必要的 ICMP 报文会造成 PMTU black hole。APNIC 对 MTU 与 MSS 不匹配 的案例展示了这类故障的实际表现。

五、TCP：在不可靠 IP 之上构造可靠字节流

RFC 9293 是 TCP 的现行基础规范，取代了 1981 年的 RFC 793 及其若干更新。TCP 的核心能力是面向连接、双向、可靠、有序的字节流；它不负责加密，也不理解应用消息。

1. TCP 是字节流，不是消息队列

应用连续调用两次 write()，接收端可能用一次 read() 读出；应用一次写入 100 KiB，接收端也可能分多次读取。TCP 不保留应用写入边界，只保证字节顺序。

因此，应用协议必须自行定义消息边界，常见方法包括：

  • 固定长度；
  • 长度字段加正文；
  • 分隔符；
  • 自描述编码；
  • 关闭连接表示消息结束。

“粘包”不是 TCP 把两个包错误地粘在一起，而是应用误把字节流当成了消息队列。

3. 三次握手究竟建立了什么

sequenceDiagram
    participant C as 客户端
    participant S as 服务器
    C->>S: SYN, seq=x, TCP options
    S->>C: SYN + ACK, seq=y, ack=x+1, TCP options
    C->>S: ACK, seq=x+1, ack=y+1（可携带数据）

握手完成了四件事：

  1. 同步双方各自的初始序列号；
  2. 证明握手报文可以在两个方向传递；
  3. 让双方建立并确认连接所需状态；具体实现可以延迟分配部分资源；
  4. 交换 MSS、Window Scale、SACK Permitted、Timestamp 等 TCP 选项。

为什么不是两次？服务器发出自己的 SYN 后，需要第三个报文确认客户端已经收到服务器的初始序列号。没有这个确认，服务器无法区分“客户端能够双向通信”和“一个延迟或伪造的旧 SYN”。

SYN 与 FIN 虽不携带普通应用字节，各自仍占用一个序列号。第三个 ACK 可以同时携带数据；同时打开、TCP Fast Open 等机制也会呈现不同报文形态。因此“三次握手”是正常主动打开的基本过程，不是所有抓包都必须出现的僵硬模板。

4. 序列号、确认与重传

TCP 给字节编号，而不是给报文编号。假设某段从 seq=1001 开始，携带 500 字节，接收端连续收到后返回 ack=1501，含义是：“1501 之前的字节已经连续收到，下一个期望字节是 1501。”这是累计确认。

如果中间一段丢失而后续段先到，接收端不能把缺口之后的数据作为连续字节交付给应用，通常会重复确认当前期望序列号。发送端可以通过以下信号判断丢失：

  • 重传超时 RTO： 根据平滑 RTT 与 RTT 波动动态计算；连续超时采用指数退避，RFC 6298 给出标准算法；
  • 重复 ACK： 经典 TCP 在收到 3 个重复 ACK 后执行快速重传；
  • SACK： 接收端报告已经收到的非连续区间，使发送端只重传缺失部分，RFC 2018 定义该选项。

TCP 的可靠意味着：只要连接最终没有失败，交给接收应用的字节是无重复且有序的。它不意味着等待时间无限、连接永不失败，更不意味着对端业务已经处理或持久化数据。TCP ACK 通常只表明对端 TCP 已接收相应字节；需要“订单已入库”之类保证时，应用协议必须另行确认。

5. 流量控制与拥塞控制不是一回事

两者都限制发送量，但保护的对象不同：

接收应用读取太慢时，接收端缩小 rwnd，极端情况下通告零窗口；这与网络拥塞无关。反过来，即使接收端有大量空闲内存，发送端也不能无视 cwnd 把数据倾倒进网络。

RFC 5681 描述了经典慢启动、拥塞避免、快速重传与快速恢复。慢启动的“慢”是相对直接以链路速率发送而言：在理想 ACK 行为下，cwnd 可大致每个 RTT 翻倍；进入拥塞避免后增长更保守，检测到拥塞则回退。现代实现还可能使用 CUBIC、BBR 等算法，但都必须承担不造成拥塞崩溃的责任。Cloudflare 对 CUBIC 与 HyStart++ 的实验展示了慢启动过冲、丢包与窗口回退。

6. 关闭连接为什么常见四个报文

TCP 是全双工的，两个方向可以独立关闭。A 发送 FIN 只表示“A 不再发送数据”，B 仍可继续向 A 发送。因此正常关闭常见如下过程：

它不是永远严格四个报文：B 可以把 ACK 与自己的 FIN 合并，双方也可能同时关闭。主动关闭的一方通常进入 TIME-WAIT，等待 2×MSL，以便旧的重复报文从网络中消失，并在对端重传 FIN 时再次发送最终 ACK。

RST 表示异常复位，不等价于优雅关闭。访问未监听端口、协议状态不匹配或应用执行 abortive close 等情况都可能出现 RST。仅仅长时间没有报文也不能证明连接仍然可用；TCP 本身没有即时存活检测能力。Cloudflare 的连接超时分析展示了 SYN 重传、keepalive、TCP_USER_TIMEOUT 和应用超时之间的区别。

七、从 HTTP 看 TCP 的边界

以 HTTPS 为例：

TCP 只保证 TLS 收到有序字节，不认识 HTTP 请求、响应或 HTTP/2 stream。若一个 TCP 段丢失，缺口后的字节即使已经到达，也必须等待重传后才能按序交给 TLS。这是 TCP 字节流层面的队头阻塞；当多个 HTTP/2 stream 复用一条 TCP 连接时，一个丢失可能同时拖延多个逻辑流。

HTTP/3 使用 QUIC，QUIC 通常运行在 UDP 之上，并在用户态实现可靠性、拥塞控制、加密和多路流。某个 QUIC stream 丢失数据不必阻塞其他 stream 的有序交付，但共享路径仍受连接级拥塞控制约束。Cloudflare 的 QUIC 演进介绍 给出了 TCP、TLS 与 QUIC 握手的直观对比。

这也提醒我们：TCP/IP 是协议族的历史名称，现代互联网并非所有可靠传输都必须经过 TCP。

八、八个常见误解

  1. “TCP 有连接，所以网络中存在一条固定通路。” 连接状态主要保存在端主机；IP 分组仍可能独立选择路径。
  2. “一次 send 对应一次 recv。” TCP 只提供字节流，读取边界由缓冲、分段和调度共同决定。
  3. “收到 ACK 就说明服务端处理成功。” ACK 是传输层确认，不是业务事务确认。
  4. “三次握手只是在确认服务器在线。” 它还同步两个方向的序列空间并交换 TCP 选项。
  5. “断开连接一定是四次挥手。” ACK 与 FIN 可以合并，也可能同时关闭或直接 RST。
  6. “丢包一定等于网络拥塞。” 经典丢包型拥塞控制常把丢包当作拥塞信号，但无线误码、链路故障和策略丢弃也会丢包。
  7. “能 ping 通就能访问服务，ping 不通就是主机离线。” ping 使用 ICMP；防火墙可能分别处理 ICMP 与 TCP 端口。
  8. “TCP 校验和保证数据安全。” 它只做非加密差错检测；机密性、身份认证和抗篡改应由 TLS、IPsec 等机制提供。

十、最终心智模型

可以把 TCP/IP 浓缩为四句话：

  • 链路层解决下一跳交付，IP 解决跨网络逐跳转发。
  • IP 是无连接、尽力而为的；可靠性不是路由器承诺的。
  • TCP 在端主机上利用序列号、ACK、计时器和重传构造可靠有序字节流。
  • rwnd 保护接收端，cwnd 保护网络，真正性能由窗口、RTT、丢包和应用行为共同决定。

当遇到网络问题时，也应按层定位：先确认名称解析，再确认路由与邻居解析，然后观察 TCP 状态、重传和窗口，最后检查 TLS 与应用协议。不要用某一层的单一现象替代整条因果链。
