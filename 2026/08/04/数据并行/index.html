数据并行

数据并行（Data Parallelism，DP）是分布式深度学习中最基础、应用最广泛的并行策略。它在多个计算设备上保留逻辑上相同的模型副本，将训练数据切分给不同的设备并行计算，再同步各副本产生的梯度，使所有副本在每次参数更新后继续保持一致。

数据并行解决的首要问题是训练吞吐量：当模型能够放入单个加速器、但单卡处理数据的速度不足时，可以通过增加数据并行 Rank 同时处理更多样本。然而，传统数据并行会在每个 Rank 上重复保存参数、梯度和优化器状态；随着模型规模增长，这些冗余状态又会成为显存瓶颈。DeepSpeed ZeRO 和 PyTorch FSDP 等技术正是从这一问题出发，将数据并行从“完整复制”推进到“状态分片”。

本文从数据并行的数学语义出发，先厘清广义数据并行、参数服务器架构、PyTorch DataParallel（DP）和 DistributedDataParallel（DDP）的关系，再介绍 Ring AllReduce、混合精度训练中的显存构成，以及 DeepSpeed ZeRO-1、ZeRO-2 和 ZeRO-3 的工作机制。

2. 从单卡训练到数据并行

单卡训练的一次迭代通常包含以下步骤：

  1. 从数据集中读取一个批次；
  2. 执行前向传播并计算损失；
  3. 执行反向传播，得到参数梯度；
  4. 优化器根据梯度及其内部状态更新参数；
  5. 清空梯度并进入下一次迭代。

同步数据并行在此基础上增加了两个关键环节：

  • 数据分片：每个 Rank 只处理全局批次的一部分；
  • 梯度同步：在优化器更新参数之前，对各 Rank 的局部梯度执行集合通信。

注意，数据并行切分的是输入批次，而不是模型中的层或张量。标准 DDP 的每个 Rank 仍需容纳完整的模型及一次局部前向、反向计算所需的状态。因此，增加 DDP Rank 可以提升吞吐量，但不能让一个原本无法放入单卡显存的模型自动变得可训练。

3. 数据并行、参数服务器与 PyTorch DP 和 DDP

“DP”“参数服务器”和“DDP”经常被放在一起比较，但它们并不处于同一个概念层次。数据并行是一种并行策略；参数服务器是一种分布式状态管理与通信架构；DataParallel 和 DistributedDataParallel 则是 PyTorch 提供的两种具体实现。

3.1 四个概念的层次

名称 概念层次 核心含义
数据并行（Data Parallelism） 通用并行策略 多个计算单元使用逻辑上相同的模型处理不同数据，并协调梯度或参数
参数服务器（Parameter Server） 分布式系统架构 Worker 负责计算，Server 集中或分片维护参数、聚合更新，并向 Worker 提供最新状态
PyTorch DataParallel 单机多卡 API 实现 单进程内复制模型、分发输入，并在主设备上汇集输出和梯度
PyTorch DistributedDataParallel 同步数据并行 API 实现 通常一进程一 GPU，各 Rank 通过集合通信同步梯度，再独立执行相同更新

因此，本文用“数据并行”或“广义 DP”表示并行策略本身；用代码形式的 DataParallel 表示 PyTorch 的具体类。参数服务器可以实现数据并行，但它不等同于数据并行，更不等同于 PyTorch DataParallel。

3.2 参数服务器

参数服务器架构通常包含两类逻辑角色：

  • Worker：读取训练数据，执行前向传播和反向传播，产生梯度；
  • Server：维护全部或部分模型参数，接收 Worker 的梯度并完成聚合或参数更新，再向 Worker 返回更新后的参数。

Worker 和 Server 描述的是逻辑角色，并不等同于某块 GPU。一个 Worker 可以管理一张或多张 GPU；Server 可以运行在 CPU 节点或 GPU 节点上，也可以由某个 Worker 兼任。大规模系统还可以设置多个 Server，对参数进行分片，避免所有状态都集中在单个节点。

经典训练流程可以概括为 Pull → Compute → Push：Worker 从 Server 拉取参数，在本地批次上计算梯度，再把梯度推送给 Server。系统既可以采用同步更新——等待参与本轮的所有 Worker 提交梯度后再统一更新，也可以采用异步更新——收到某个 Worker 的梯度后立即更新。异步方式可以减少慢 Worker 带来的等待，但会让部分梯度基于过期参数计算，产生梯度陈旧（Stale Gradient）问题。

具体实现并不只有一种：Server 可以同时负责梯度聚合和全量参数更新；也可以只负责聚合梯度，再把聚合结果发回各 Worker，由它们执行一致的本地更新。无论采用哪种形式，都必须保证参数版本、更新规则和容错语义与训练算法相匹配。

若一个中心 Server 与 个 Worker 交换大小为 的梯度或参数，单个 Worker 每轮的通信量通常为 ，但中心 Server 需要汇聚并下发来自所有 Worker 的数据，其通信压力约为 。因此，增加 Worker 时，中心节点容易成为带宽、计算和容错瓶颈。参数分片、多 Server、分层聚合和通信压缩可以缓解这一问题，但也会增加系统复杂度。

参数服务器并非只适用于单机，也并非已经被 AllReduce 完全取代。它仍适合需要异步训练、稀疏参数访问、超大嵌入表或中心化参数管理的场景；而在稠密梯度的同步 GPU 训练中，集合通信通常更容易获得均衡的带宽利用率。

3.3 PyTorch DataParallel

DataParallel 采用单进程、多线程模式，基本流程为：

  1. 在主设备上保存原始模型；
  2. 每次前向计算时将模型复制到其他设备；
  3. 沿批次维度将输入分发（Scatter）到各设备；
  4. 各设备并行执行前向计算，输出汇集（Gather）回主设备；
  5. 在主设备上计算损失并反向传播，各设备的梯度规约累加到原始模型；
  6. 在主设备上执行参数更新。

这种实现带有明显的集中式特征：梯度最终累加到主设备上的原始模块，优化器也更新这份主副本。因此，它与单 Server 聚合存在相似的“中心热点”，但它是 PyTorch 单进程内部的多 GPU 数据并行封装，不是独立的参数服务器系统，也不存在经典参数服务器所强调的远程 Push/Pull、参数分片和异步一致性机制。

DataParallel 易于使用，但存在 Python GIL、多线程调度、每轮模型复制、输入分发、输出汇集，以及主设备负载和显存不均衡等开销。它只能用于单机，因此更适合教学或快速验证，不是现代多 GPU 训练的首选。

3.4 PyTorch DistributedDataParallel

DDP 通常采用“一进程一 GPU”的多进程架构。每个进程持有独立且长期存在的模型副本，反向传播时通过通信后端同步梯度。NVIDIA GPU 训练一般使用 NCCL（单机与多机均适用），CPU 训练常使用 Gloo；多机训练还需要完成跨节点的进程发现和通信域初始化。

DDP 的关键机制包括：

  • 构造 DDP 模型时同步初始模型状态；
  • 为需要梯度的参数注册自动微分钩子；
  • 将多个参数的梯度组织成通信桶（Bucket）；
  • 当一个桶中的梯度就绪时，异步发起 AllReduce；
  • 尽可能让较早产生的梯度通信与后续反向计算重叠；
  • backward() 返回时，参数的 .grad 已经是同步后的梯度。

DDP 不会自动切分输入数据。使用者仍需通过 DistributedSampler 或等价机制，让不同 Rank 读取不同的数据分片。

DDP 的典型实现不设置中心 Server。每个 Rank 同时承担计算和模型状态维护职责，并通过 AllReduce 等集合操作得到相同的规约梯度，随后独立执行相同的优化器更新。以 Ring AllReduce 为例，大小为 的缓冲区在每个 Rank 上的单向发送量为 ，当 增大时趋近 ；通信负载不会集中在某一个 Rank 上。

这里的“单 Rank 通信量趋近常数”不代表扩展 GPU 数量没有代价：全系统总流量仍随 Rank 数增加，Ring 的通信轮数为 ，跨节点链路、启动延迟、网络争用和慢 Rank 都可能降低扩展效率。因此，DDP 能够跨机器运行，不仅因为流量更均衡，还依赖通信后端、网络拓扑与分层算法的共同支持。

4. 梯度同步与 Ring AllReduce

DDP 的语义是对梯度执行 AllReduce，但 AllReduce 是通信原语，不等同于某一种固定算法。通信库可根据 Rank 数、消息大小、硬件拓扑和链路特性，在 Ring、Tree、CollNet 或分层算法之间选择。关于通信原语和通信库，可进一步阅读集合通信与集合通信库。

Bucket 过小会产生大量小消息，增加启动延迟；Bucket 过大又会推迟第一次通信，降低重叠比例。最优大小取决于模型结构、网络带宽、延迟和计算速度，应通过性能分析工具测量，而不是机械地使用同一组参数。

4.2.1 Bucket 是什么

神经网络通常包含大量参数张量。反向传播不会在同一时刻产生所有梯度，而是沿计算图逐步进行：靠近输出端的参数梯度通常先就绪，靠近输入端的参数梯度随后就绪。Bucket 就是若干参数梯度对应的连续通信缓冲区，它通常包含多个参数张量，而不一定与某一层一一对应。

DDP 根据容量上限和参数大小把参数映射到不同 Bucket，并把同一 Bucket 中的梯度打包为连续的一维缓冲区。这样做同时服务于两个目标：

  • 合并小消息：避免每个小参数都单独调用一次集合通信，减少固定启动开销；
  • 提前启动通信：不必等待全部梯度完成，只要一个 Bucket 凑齐就可以开始同步。

初始映射通常依据参数注册顺序的逆序近似构造，因为反向传播中的梯度就绪顺序往往与前向参数使用顺序相反。部分实现会在观察到实际就绪顺序后重建 Bucket。需要注意，这只是性能优化假设：带分支的计算图、参数共享、激活检查点或动态控制流都可能让真实顺序与该假设不同。

4.2.2 一个 Bucket 何时可以开始通信

DDP 在构造时为参数注册 autograd hook。某个参数的梯度计算完成后，对应 hook 会通知 Reducer：这个梯度已经就绪。随后经历以下过程：

  1. 梯度被写入或关联到所属 Bucket 的连续缓冲区；
  2. Reducer 记录该 Bucket 中已经就绪的参数；
  3. 只有当 Bucket 内的所有梯度都就绪后，该 Bucket 才具备通信条件；
  4. Reducer 按一致的 Bucket 索引顺序发起异步 AllReduce；
  5. 规约完成后，各 Rank 获得相同的 Bucket 梯度，再写回或映射到各参数的 .grad。

所有 Rank 必须以相同顺序参与集合操作。即使某个后续 Bucket 在本 Rank 上更早就绪，也不能让不同 Rank 任意改变 AllReduce 顺序，否则可能造成集合操作错配、结果错误或训练挂起。因此，Bucket 的参数组成和就绪顺序会直接影响流水线能否及时启动。

4.2.3 通信如何与反向传播重叠

当 Bucket 3 的梯度全部就绪时，DDP 可以在通信流上启动 Bucket 3 的 AllReduce；与此同时，计算流继续计算 Bucket 2、Bucket 1 和 Bucket 0 对应的梯度。后续 Bucket 依次形成“计算完成一个、通信启动一个”的流水线。

这里的“异步”只表示通信操作可以与当前反向计算并发，并不代表不同 Rank 可以使用不同版本的参数继续训练。backward() 返回前，DDP 仍需等待本轮所有 Bucket 的规约完成；只有同步后的梯度全部可用，才能安全执行 optimizer.step()。因此 DDP 仍属于同步数据并行。

经过重叠后，训练步骤感知到的不是全部通信时间，而是没有被反向计算遮蔽的“暴露通信时间”：

图中最后一个 Bucket 的 AllReduce 超出反向计算终点的部分，就是典型的通信尾部（Communication Tail）。如果网络足够快且流水线安排合理，大部分通信可以被计算掩盖；如果通信明显慢于反向计算，多个 AllReduce 会在通信流中排队，尾部仍然可能很长。

4.2.4 Bucket 大小为什么需要权衡

Bucket 设置 优点 代价与典型现象
较小 梯度更早凑齐，可以更早启动第一次 AllReduce 集合通信调用数量增多，小消息更受启动延迟影响，带宽利用率可能较低
较大 消息数量更少，大消息通常更容易利用链路带宽 必须等待更多梯度就绪，第一次通信启动更晚，最后可能留下更长的通信尾部

Bucket 容量只是一个上限，并不能单独决定重叠效果。某个计算很慢的参数如果与多个早已就绪的梯度位于同一 Bucket，会阻塞整个 Bucket；多个 Rank 的输入形状或执行路径不一致，也会造成就绪时间偏差。真正需要优化的是“Bucket 何时就绪、通信何时结束”，而不只是 Bucket 有多少 MB。

4.2.5 如何判断是否需要调优

可以使用 PyTorch Profiler、Nsight Systems 等工具同时观察反向计算内核与 NCCL 集合通信：

  1. 查看第一次 AllReduce 是否在反向传播早期启动；
  2. 查看 AllReduce 是否与后续反向计算在时间线上重叠；
  3. 查看多个小 AllReduce 是否被固定启动延迟支配；
  4. 查看最后一次 AllReduce 在反向传播结束后还延伸了多长时间；
  5. 对比不同 Bucket 容量下的单步时间、吞吐量和显存，而不是只比较通信持续时间。

如果时间线上存在大量细碎通信，可适当增大 Bucket；如果第一次通信启动很晚、反向传播结束后仍有较长尾部，则可以尝试减小 Bucket，或调整参数分组与执行顺序。最优配置取决于模型结构、消息规模、计算速度、网络带宽与延迟，也可能受到 torch.compile 图切分方式影响，应以实际时间线测量为准。

5. 标准数据并行的显存冗余

DDP 虽然避免了 DataParallel 的主设备汇集瓶颈，但每个 Rank 仍完整保存模型状态。训练显存大致由以下部分组成：

  • 模型参数（Parameters）；
  • 参数梯度（Gradients）；
  • 优化器状态（Optimizer States）；
  • 前向激活值（Activations）；
  • 临时缓冲区、通信缓冲区和内存碎片。

6. DeepSpeed ZeRO：零冗余优化

ZeRO（Zero Redundancy Optimizer）的核心思想是：在保持数据并行计算方式的同时，把原本在所有 Rank 上重复保存的模型状态分片，使每个 Rank 只长期持有其中一部分，并在计算需要时通过集合通信临时重建所需数据。

方案 分片对象 每个 Rank 的理想化状态显存
DDP 无
ZeRO-1 优化器状态
ZeRO-2 优化器状态、梯度
ZeRO-3 优化器状态、梯度、参数

以上只计算模型状态，不包含激活值、通信临时缓冲区、对齐填充和内存碎片，也没有考虑为了提高性能而保留的参数缓存。

仍以 70 亿参数、8 路数据并行为例：

方案 理想化模型状态显存 / Rank
DDP 112 GB
ZeRO-1 38.5 GB
ZeRO-2 26.25 GB
ZeRO-3 14 GB

6.1 ZeRO-1：分片优化器状态

ZeRO-1 在所有 Rank 上保留完整的低精度参数和梯度，但把 FP32 主参数、Adam 一阶矩和二阶矩等优化器状态分片。

梯度仍按 DDP 的方式做 AllReduce，但每个 Rank 只负责更新自己拥有的那部分参数。更新完成后，再通过 AllGather 把各 Rank 的新参数分片收集起来，使所有 Rank 重新获得一致的完整参数。与标准 DDP 相比，ZeRO-1 主要减少优化器状态冗余，通常不会改变前向和反向计算的模型副本形态。

适用场景：模型参数和梯度能够放入单卡，但 Adam 等优化器状态占用过高。

6.2 ZeRO-2：进一步分片梯度

ZeRO-2 在 ZeRO-1 基础上继续分片梯度。反向传播产生梯度后，可以通过 ReduceScatter 让每个 Rank 只保留与其优化器分片对应的已规约梯度；各 Rank 更新自己负责的参数后，再通过 AllGather 恢复一致的完整参数。

从通信数据量的数量级看，ZeRO-1/2 可以用 ReduceScatter + AllGather 替代 DDP 的 AllReduce，因此在理想情况下并不必然增加总通信量；实际吞吐量仍会受到消息切分、调度、通信重叠和网络拓扑影响。

适用场景：完整参数仍能放入单卡，但梯度和优化器状态共同造成显存压力。ZeRO-2 往往是显存节省、通信复杂度和训练吞吐量之间较均衡的选择。

6.3 ZeRO-3：进一步分片模型参数

ZeRO-3 将低精度模型参数也切分到不同 Rank。单个 Rank 不再长期持有完整模型参数；执行某个模块的前向或反向计算前，系统通过 AllGather 收集该模块当前需要的参数，使用后再释放或重新分片。梯度则通过 ReduceScatter 交给相应的参数所有者。

这让模型状态显存随数据并行度近似按 缩小，使数据并行组本身具备了承载超出单卡显存模型的能力。但参数需要按计算进度动态收集，ZeRO-3 对通信带宽、预取策略、模块粒度和执行顺序更敏感。相比 ZeRO-2，它通常会引入更多参数通信和更复杂的运行时调度。

适用场景：完整模型参数已经无法放入单卡，或者需要尽可能降低每个 Rank 的模型状态显存。

6.4 ZeRO-Offload 与 ZeRO-Infinity

状态分片仍然受整个 GPU 集群总显存限制。DeepSpeed 还可以把部分状态和优化器计算卸载到 CPU，或进一步卸载到 NVMe：

  • ZeRO-Offload：主要利用 CPU 内存和 CPU 计算承载优化器相关状态与计算；
  • ZeRO-Infinity：在 ZeRO-3 基础上扩展到参数等模型状态，并可利用 CPU 和 NVMe 的分层存储。

Offload 用更低速、更大容量的存储换取 GPU 显存空间，并不意味着没有代价。PCIe 传输、CPU 算力和 NVMe 吞吐量都可能成为瓶颈，需要通过预取、固定页内存、计算通信重叠以及合理的分片粒度缓解。

7. ZeRO、FSDP 与其他并行策略

7.1 ZeRO 仍属于数据并行体系

ZeRO 不会像张量并行那样，把同一个矩阵乘法拆给多个 Rank 协作计算；各 Rank 仍处理不同的数据样本，并执行逻辑上完整的模型计算。它改变的是模型状态的存储方式和按需通信方式，因此常被称为分片数据并行（Sharded Data Parallelism）。

7.2 ZeRO-3 与 FSDP

PyTorch Fully Sharded Data Parallel（FSDP）的核心语义与 ZeRO-3 相近：参数、梯度和优化器状态在数据并行 Rank 间分片，并通过 AllGather、ReduceScatter 等集合通信按需参与计算。二者的 API、运行时实现、模块包装方式、状态字典和生态集成不同，不能简单视为同一个软件，但可以把它们放在同一类“全分片数据并行”方案中理解。

7.3 数据并行不是万能方案

当单个算子或单层权重无法在一个设备上计算，或者仅靠参数动态收集无法获得理想性能时，还需要组合其他并行维度：

  • 张量并行（TP）：切分层内张量和算子计算；
  • 流水线并行（PP）：把不同层放到不同流水线阶段；
  • 序列/上下文并行（SP/CP）：切分长序列相关计算与激活；
  • 专家并行（EP）：在 MoE 模型中切分专家。

大模型训练通常采用多维并行：在节点内使用高带宽互连完成张量并行，在节点间组织数据并行或流水线并行，并让各通信组映射到最合适的物理拓扑。

11. 方案选择

训练条件 优先考虑的方案 原因
单机多卡，模型和训练状态均能轻松放入单卡 DDP 实现成熟，通常吞吐量最高、调试简单
参数与梯度可放入单卡，优化器状态过大 ZeRO-1 以较低复杂度消除优化器状态冗余
完整参数可放入单卡，梯度和优化器状态造成压力 ZeRO-2 显存节省和通信开销较均衡
完整参数无法放入单卡 ZeRO-3 或 FSDP 对参数、梯度和优化器状态进行全分片
模型状态能放下，但激活值过大 激活检查点、序列并行等 ZeRO 不直接消除主要激活值占用
CPU/NVMe 容量充足但 GPU 显存不足 ZeRO-Offload / ZeRO-Infinity 用传输与主机计算开销换取 GPU 显存
单层或单算子无法在单卡计算 张量并行，必要时组合 PP/DP 仅做状态分片未必解决算子计算约束

一般而言，应从满足显存约束的最低复杂度方案开始：能用 DDP 就先用 DDP；DDP 放不下时依次评估 ZeRO-1、ZeRO-2 和 ZeRO-3。更高的 ZeRO Stage 并不天然更快，它首先解决的是容量问题。

小结

数据并行通过“逻辑上相同的模型、不同的数据分片、协调后的参数更新”扩展训练吞吐量。参数服务器通过 Worker/Server 角色管理和交换参数状态，既可用于同步训练，也可用于异步或稀疏参数场景；PyTorch DataParallel 使用单进程多线程和主设备汇集，使用简单但扩展性有限；DDP 采用多进程架构，通过梯度分桶与集合通信实现高效同步，是常规稠密多 GPU 同步训练的首选。

Ring AllReduce 可以分解为 ReduceScatter 和 AllGather，具有较高的大消息带宽利用率，但真实通信库会根据拓扑和消息规模选择算法。标准 DDP 的主要容量限制，是每个 Rank 都重复保存完整的参数、梯度和优化器状态。DeepSpeed ZeRO 通过三个阶段依次分片优化器状态、梯度和参数，在保留数据并行语义的同时显著降低单 Rank 的模型状态显存；代价则是更复杂的集合通信、状态管理和性能调优。

理解数据并行时，最重要的是同时把握三条主线：数学语义是否等价、模型状态如何分布、通信能否被计算有效掩盖。只有三者都正确，增加设备数量才会转化为可靠的训练能力。
