使用 MRC 与 SRv6 构建具备韧性的 AI 超级计算机网络

论文：Resilient AI Supercomputer Networking using MRC and SRv6，arXiv:2605.04333v1。作者来自 OpenAI、Microsoft、AMD、Broadcom 与 NVIDIA。

大规模同步预训练对网络提出的首要要求，并不只是较高的平均吞吐量，而是稳定的尾部性能。在一次 collective 中，只要有一个传输因流碰撞、incast 或链路故障而显著变慢，所有同步 GPU 都可能等待这一离群值。随着训练规模扩展到数万乃至十万块 GPU，低概率事件会转化为持续发生的系统事件，依赖作业重启或路由协议收敛来恢复已经难以接受。

本文的核心贡献是一套由三个部分构成的协同设计：将一张 800 Gb/s 物理端口拆分成多个较低速 lane，构成高基数的多平面两层 Clos；在端侧使用 Multipath Reliable Connection（MRC）对每个 Queue Pair（QP）执行逐包多路径传输；再通过静态 SRv6 源路由，使每个 MRC 熵值精确对应一条物理路径。其关键并非单独提出一种负载均衡算法，而是重新划分了网络职责：交换机只执行简单、静态的转发，端系统同时负责负载均衡、拥塞反馈和故障绕行。

论文报告称，这套系统已经部署于 OpenAI 和 Microsoft 的多个大规模训练集群，并用于前沿模型训练。其生产结果表明，过去足以终止训练的部分链路和交换机故障，在 MRC 网络中通常只表现为短暂吞吐波动或与剩余容量相匹配的性能下降。

1. 问题：规模放大了尾延迟与故障

同步预训练会组合数据并行、张量并行、流水线并行和专家并行等策略。每个训练 step 中，计算与通信交替执行；系统希望尽可能重叠二者，并让关键路径以计算为主。然而，一轮通信的完成时间由最慢的传输决定。当参与者数量增加时，即使单条路径发生异常的概率很低，某个参与者遭遇异常的概率也会迅速上升。

论文将网络必须解决的问题归纳为三项：

  1. 在大量等价路径间均匀分配流量，避免低熵大流造成 ECMP 哈希碰撞；
  2. 处理同步 collective 常见的 incast，同时避免产生新的尾延迟离群值；
  3. 在链路、端口或交换机发生故障时继续推进训练，而不是使整个作业失败。

还有一个容易被忽略的约束：数千台交换机组成的多座 AI 超级计算机，需要由规模相对较小的团队运维。系统不能要求操作人员实时诊断每次链路抖动，也不应依赖复杂控制面在每次故障后重算全网路径。因此，论文把“低运维负担”与性能、韧性并列为设计目标。

2. 核心思路：拓扑、传输与路由协同设计

三部分机制的分工如下。

层次 机制 主要作用
物理拓扑 多平面两层 Clos 以高端口基数缩短路径，并把单次故障细化为较小的容量损失
端到端传输 MRC 逐包喷洒、主动负载均衡、乱序放置、选择性重传与故障路径淘汰
网络转发 静态 SRv6 源路由 建立 EV 到物理路径的确定性映射，避免动态路由与端侧自适应相互干扰

这三者存在明确的依赖关系。多平面网络提供大量独立路径，但传统单路径 RoCE 无法稳定利用这些路径；MRC 能够使用路径多样性，但若底层 ECMP 映射和动态路由持续变化，端侧观察到的路径状态便难以解释；SRv6 固定了 EV 与物理路径之间的关系，使 MRC 可以对单条路径维护状态，并让监控系统精确定位故障。

因此，论文所谓的“韧性”不是依靠某一个冗余组件实现，而是让拓扑提供冗余、传输层快速选择冗余、静态路由保持路径身份稳定。

3. 多平面两层 Clos 拓扑

论文以 100,000 块 GPU、每块 GPU 配备一张 800 Gb/s NIC 为例。51.2 Tb/s 交换芯片可提供 64 个 800 Gb/s 端口。若构造传统无超售 Clos，每台 T0 使用 32 个端口连接 NIC、32 个端口连接 T1，一个 pod 只能容纳 1024 张 NIC；再增加 T2 后，网络规模约为 64K NIC。要达到 100K GPU，需要继续增加层级、引入超售，或构造多个独立 rail。

论文采用的方案是把 800 Gb/s NIC 按 lane 拆分为 8×100 Gb/s，并用同一类 51.2 Tb/s 芯片构造八个相互独立的 Clos 平面。此时一台交换机可提供 512 个 100 Gb/s 端口：T0 向下连接 256 个 NIC 端口、向上连接 256 台 T1；T1 再连接 512 台 T0。最终只需两层交换机便可连接 131,072 块 GPU，并保持全二分带宽。

多平面拓扑带来四项直接收益：

  • 最长路径只经过三台交换机，而三层单平面网络需要经过五台或七台交换机；
  • T0 一跳范围从 32 个节点扩大到 256 个节点，更容易利用作业放置的局部性；
  • 在相同全二分带宽目标下，光模块数量约为三层网络的 2/3，交换机数量约为 3/5；
  • 故障粒度显著减小。论文估算，一条 T0–T1 链路故障在 800 Gb/s 单平面中会使相关节点损失约 3% 容量，在 100 Gb/s 平面中则约为 0.4%。NIC–T0 链路故障也只损失一个平面的 1/8 带宽。

需要强调的是，lane 拆分不会增加 NIC 的总带宽。它用较低的单链路速率换取更高的交换端口基数、更短的拓扑和更细的故障粒度。代价在于每条 100 Gb/s 链路更容易被单个大流压满，而且系统必须同时均匀使用所有平面。MRC 正是为这一约束设计的传输层。

4. MRC：面向多路径的可靠 RDMA 传输

MRC 是对 RoCEv2 Reliable Connection（RC）的最小化扩展。它保留普通 RoCE verbs 接口和 QP 抽象，但在本文实现中只支持训练负载所需的 write 与 write-with-immediate 操作。MRC 借鉴了 Ultra Ethernet Transport（UET）的若干设计，包括逐包喷洒、乱序内存放置、选择性重传和数据包裁剪。

4.1 逐包喷洒与乱序放置

每个 MRC 数据包都携带 RDMA 虚拟地址与 remote key。因此，即使同一 QP 的数据包经不同路径乱序到达，接收 NIC 仍可立即把数据写入正确位置，无需先恢复按序数据流。

每个数据包还携带一个 32 位 Entropy Value（EV）。EV 分布编码在 UDP 源端口与 IPv6 flow label 中。在传统 ECMP 网络中，不同 EV 会被哈希到不同路径；在本文的 SRv6 网络中，EV 则通过确定性算法映射到一条明确的源路由路径。

QP 建立时，发送端通常生成包含 128～256 个条目的 EV 集合，并在所有网络平面之间均匀分配这些 EV。此后，每发送一个数据包便轮换选择新的 EV。于是，一个 QP 无需应用感知，即可把数据包条带化地分布到所有平面及每个平面中的多条路径上。传统 RoCE 的多 QP 扩展仍以流为基本单位，而 MRC 把负载均衡粒度下沉到了数据包。

4.2 拥塞、丢包与路径状态

逐包喷洒很难与 Priority Flow Control（PFC）共存：同一个 QP 的数据包可能沿数百条路径汇聚到最后一跳，PFC 还会在不同 collective 之间造成队头阻塞。MRC 因此关闭 PFC，在尽力而为的有损以太网上运行，并通过更快、更精确的丢包恢复来维持 RC 语义。

MRC 为每个 EV 保存少量路径健康状态，并针对不同信号采取不同动作：

  • **内部拥塞：**交换机正常执行随机 ECN 标记，但通往接收端的最后一跳关闭 ECN。在全二分网络中，除最后一跳 incast 外，网络内部原则上不应持续拥塞。因此，内部 ECN 可被解释为路径负载不均。接收端回显 ECN 后，发送端临时避开对应 EV，使不同发送端未经协调产生的轻微不均得到平滑。
  • **拥塞丢包：**交换机可对本应丢弃的数据包执行 packet trimming，移除 payload，并以高优先级把头部送到目的端。接收 NIC 随即返回 NACK，触发快速重传。裁剪包还使发送端能够区分拥塞丢包与路径故障。
  • **普通丢包：**若数据包未被裁剪却直接丢失，MRC 假定路径已经失效，立即停止使用对应 EV，并在其他路径上选择性重传。SACK 会精确报告已到达的数据包，避免传统 RC 从丢失点开始进行粗粒度恢复。
  • **路径恢复：**一次丢包也可能源于比特错误，而非永久故障。MRC 会在后台探测被移除的路径；当足够多的探测成功后，对应 EV 会重新进入活动集合。

论文称，MRC 能在数十微秒内发现并绕过路径故障。这里的“路径故障”应与 NIC 端口失效区分：若一个 NIC 端口整体掉线，CX-8 实现还需要重映射大量活跃 QP 的 EV，并通过 SACK 中的端口状态位图通知远端；这一过程通常需要数秒，但 QP 本身仍可在剩余平面上继续工作。

4.3 保持平面间负载相等

当一个 EV 被移出活动集合时，MRC 使用同一平面中的另一个 EV 替换它。这个不变量保证所有 NIC 端口正常时，各平面上的负载严格相等，从而避免多个流在目的端形成“伪 incast”。它也使运维判断更简单：当 MRC 已经绕过坏路径后，健康平面的统计特征通常应当近似一致，异常平面会较为醒目。

这一选择同时构成了系统边界。如果后端网络中混入单路径流量，MRC 会受最拥塞平面限制；如果某一平面损失了过多 T0–T1 链路，该平面也可能成为全局瓶颈。论文称生产环境中尚未观察到后一种情况。

5. SRv6：以静态源路由取代动态路由

5.1 为什么关闭动态路由

在 512 端口的高基数 T0 上，一个目的端最多对应 256 个 ECMP 下一跳。故障发生后，经部分 T1 可能无法到达特定目的端，交换机不得不维护大量因目的端而异的 ECMP 集合，其数量可能接近 T0 交换机总数。这不仅增加转发表与控制面的压力，也使大规模路由问题难以诊断。

更重要的是，MRC 和动态路由都是自适应机制，但二者反应时间不同。MRC 首先检测丢包并移除故障路径；随后动态路由收敛又会改变 ECMP 映射，使原有 EV 的物理含义发生变化，并扰乱刚刚稳定的负载分配。论文由此作出一个看似反直觉的选择：既然 MRC 已能在冗余拓扑上快速绕过故障，就关闭交换机动态路由，让路径保持静态。

5.2 从 EV 生成 SRv6 路径

系统采用 SRv6 micro-segment ID（uSID）格式。外层 IPv6 目的地址由 32 位 locator 和一系列 16 位 uSID 组成，每个 uSID 显式指定路径上的一台交换机。交换机匹配地址前 48 位中的 locator 与自身 uSID，随后把 uSID 序列左移 16 位，再依据静态 /48 路由表转发。论文所使用的交换机均可在线速下完成这种 uN 风格转发。

MRC 数据包使用 IPv6-in-IPv6 封装：外层目的地址表达 SRv6 路径，内层目的地址保留目标 NIC 地址，供接收 NIC 解封装后送入 RDMA 流水线。

为避免同时保存 EV 状态和完整 SRv6 地址，系统在二者之间建立算法映射。QP 启动时，NIC 根据目的端所在 T0 group 读取一个通用 SRv6 地址模板，再从目的 IP 填入最后一跳下行链路编号。实际发送数据包时，NIC 从活动 EV 集合中选择一个 EV，将其中的平面编号复制到各 uSID，并把 T0 上行链路编号写入 T1 uSID，生成该数据包的最终外层地址。

EV 本身仍保留在 UDP 源端口和 IPv6 flow label 中。原因是 SRv6 地址会在逐跳移位过程中消失，而接收端必须在 SACK 或 NACK 中回显 EV，发送端才能更新对应路径的拥塞与健康状态。

5.3 反向路径

MRC 的累积 ACK、SACK 与 NACK 也需要一条可用反向路径。双向通信可以直接从对端的活动 EV 集合中选路，但许多 collective QP 在某一时刻是单向的，而且前向 SRv6 路径未必能够简单反转。

论文为控制包维护一个较小的反向 EV 集合，并保证每个平面至少有一个 EV。当 QP 只有入站活动时，接收端每个 RTT 使用随机 EV 发出探测；得到确认后，该 EV 被设为对应平面的反向路径。如果同时存在出站数据，则直接利用数据 SACK 更新反向 EV。由此，控制包始终从近期验证可用的路径集合中选路。

6. 故障处理与运维

静态源路由把每个 EV 固定到唯一物理路径后，故障遥测也变得确定。论文实现的 Clustermapper 由所有节点上的 agent 组成，它们共同以每毫秒覆盖一次全网链路的频率执行源路由探测：节点探测直接连接的 T0，并让数据包返回自身；同时各节点分担对 T1 的探测，使所有 T0–T1 链路都被高频覆盖。

这种探测得到的是数据面的真实状态，而不是控制面宣告的链路状态。如果 T0 自探测正常、经过 T1 的探测失败，系统便可把问题定位到 T0–T1 链路。对于“控制面和链路均显示在线，但交换机已经停止转发”这类灰色故障，Clustermapper 仍能直接发现问题。SRv6 还保证探测包与对应 MRC 数据包经过相同路径，不存在 ECMP 哈希带来的路径歧义。

MRC 支持 denylist，因而可以在 QP 建立时避开已知故障路径。不过，对于长生命周期的预训练 QP，论文发现无需预先屏蔽失效的 T0–T1 链路：QP 可以先从 100 多个 EV 和备用 EV 集合开始运行，再由 MRC 很快淘汰不可用路径。在一个 75K GPU 作业的启动过程中，即使没有预填 denylist，第一分钟内每个 QP 丢失的数据包仍少于 5 个，数分钟后总体丢包率便降至很低水平。

这也改变了维修策略。T0–T1 链路抖动通常不再需要紧急处理，甚至维修过程中也可以保持链路在线：链路不可用时 MRC 自动排除路径，探测持续成功后再恢复使用。T1 交换机异常时，运维系统可以直接重启交换机，而无需等待路由收敛或与运行中的训练作业协调。相比之下，NIC–T0 链路与 T0 交换机故障会直接减少节点可用平面，仍会造成可测量的容量下降，因而需要更谨慎处理。

7. 实验结果

论文给出了四种平台。Cluster A、B、C 是两层多平面网络，Cluster D 是用于对照实验的两层单平面小型测试床。

集群 GPU / NIC 交换机 拓扑
A NVIDIA GB200 + CX-8，800 Gb/s NVIDIA Spectrum-4、Broadcom TH5 4×200 Gb/s 多平面
B NVIDIA GB200 + CX-8，800 Gb/s NVIDIA Spectrum-5 8×100 Gb/s 多平面

D NVIDIA RTX 6000 + Broadcom Thor Ultra Broadcom TH5 400 Gb/s 单平面

7.1 基础性能

在 Cluster B 上，MRC 的 T0-local 与 cross-T1 32 KB RDMA write 均达到约 770 Gb/s，即 800 Gb/s 理论峰值的 96%。2 字节 write 的近似单向延迟分别为 5.09 μs 和 6.54 μs；跨 T1 的额外交换机跳数增加了小消息延迟，但没有限制大消息稳态吞吐量。

在 42K GPU 的 NCCL sendrecv 微基准中，大消息的每 NIC 吞吐量最高达到 92 GBytes/s。这个结果说明逐包喷洒和 SRv6 封装没有阻止 MRC 在数万 GPU 范围内接近 NIC 线速，但该微基准并不等价于完整训练 step 的端到端效率。

7.2 生产训练中的故障

在 Cluster A 的一个 50K GPU 生产预训练作业中，一台 T0 的光收发器异常导致四条 200 Gb/s 链路快速连续抖动，其中三条连接到作业中的活跃节点。由于同步训练由最慢节点决定，作业吞吐量在持续约一分钟的抖动期间下降约 25%，之后立即恢复全速。作业没有崩溃，没有 QP 失败，也无需移除受影响节点。

在另一个 75K GPU 预训练作业中，论文记录了四次 T1 交换机必须重启的事件。图中所示的一次故障里，交换机虽然仍在线，却停止了数据包转发；约四分之一 QP 受到影响，共丢失约 580K 个数据包。吞吐量在故障发生时短暂下降，但 QP 很快排除了坏路径。自动化系统在 t=0 重启交换机、约两分钟后恢复转发，而重启动作本身没有进一步影响作业吞吐量。

7.3 与 RoCE 的比较

论文在包含 64 块 GPU 的 Cluster C 上进行主要对比。RoCE 使用 400 Gb/s 单平面、ECMP、PFC 与 DCQCN；MRC 使用 4×100 Gb/s 多平面、SRv6，并关闭 PFC。两种配置使用相同的 GPU、NIC、交换机与聚合带宽，但各自运行在其偏好的网络环境中。因此，这一结果比较的是两套完整系统设计，而不是只隔离传输协议变量。

在 64 路 ring all-reduce 中，单 QP RoCE 在大消息下受 ECMP 碰撞影响，通常只能达到可用吞吐量的一半。把 RoCE 扩展到 16 个 QP 可以改善结果，但超过 8 个 QP 后收益已经很小；一个把数据包喷洒到 256 条路径的 MRC QP 仍然更快。在 0.1% 随机丢包下，MRC 对大消息的吞吐影响很小；在 1% 持续随机丢包下，RoCE 基本不可用，MRC 也只剩约三分之一目标吞吐量，说明 MRC 面向的是瞬态故障而非长期严重丢包。

在 all-to-all 中，同时活动的 QP 更多，RoCE 的负载均衡问题相对减弱，增加 QP 反而没有收益。MRC 在所有消息大小下仍优于 RoCE，带宽受限区间的差距更明显。

论文还构造了 7-to-1 incast，并在同一机架中运行一条目的端不同的“受害者”流。RoCEv2 即使使用 DCQCN，单 QP 下受害者流平均吞吐量仍下降约 25%；多 QP 下还出现持续 1 秒、吞吐量降至约 100 Gb/s 的区间。MRC 则近似均匀地共享 incast 瓶颈，同时让受害者流保持接近 400 Gb/s。这一结果体现了关闭 PFC、使用端到端恢复的重要性：拥塞不再通过暂停帧扩散到无关 collective。

8. 适用边界与局限

论文的结果表明 MRC 能显著提高训练网络的韧性，但它并不消除故障，也不是无需约束的通用 RoCE 替代方案。

首先，本文 MRC 只实现 write 与 write-with-immediate，覆盖的是 AI collective 所需的 RC 子集。系统还要求 NIC 实现新的逐包路径状态、乱序放置和选择性重传机制，交换机支持所需的 SRv6 转发；数据包裁剪则进一步依赖网络设备能力。虽然论文已经在 NVIDIA、AMD 与 Broadcom NIC，以及多种交换芯片和网络操作系统上完成实现，但部署仍属于软硬件协同升级。

其次，多平面设计缩小了故障影响，却没有消除全部单点。论文使用一个 800 Gb/s NIC 光模块承载 4×200 Gb/s 链路；若单条 lane 抖动，MRC 可以绕过它，若整个 NIC 收发器抖动，则所有平面同时丢失，QP 仍会失败。部分失效但未完全掉线的 NIC–T0 链路也不能仅由 MRC 可靠判断故障位于本端还是远端，需要 Clustermapper 检测后通过 denylist 避开该平面。

最后，大规模生产数据主要证明了 MRC 系统在真实故障下能够继续训练；MRC 与 RoCE 的直接、可控对比则来自 64 GPU 等小型测试床。论文没有在同一座数万 GPU 集群上给出两种协议的完整训练效率对照。因而，实验有力支持“故障韧性与负载均衡得到改善”，但不应被解读为对所有模型、collective 和网络配置都给出了统一加速比例。

9. 总结

这项工作的核心判断是：在超大规模同步训练中，依靠交换机控制面收敛来恢复故障已经太慢，也过于复杂；端系统既然能够以逐包粒度观察路径，就应当同时承担负载均衡和故障绕行职责。

多平面 Clos 把 100K+ GPU 网络压缩为两层，并提供细粒度物理冗余；MRC 将每个 QP 喷洒到全部平面和大量路径上，利用 ECN、SACK/NACK、packet trimming 与探测维护路径状态；静态 SRv6 则赋予每个 EV 稳定、可解释的物理路径身份。三者结合后，链路抖动和 T1 交换机故障不再必然触发作业失败，交换机重启也不再要求路由收敛或训练侧协调。

因此，论文真正提供的不是一个孤立的 RDMA 优化，而是一种面向 AI 超级计算机的职责重构：用简单、确定的网络核心暴露路径多样性，用具有快速反馈的端侧传输消费这些路径，并把故障从“必须立即修复的作业事件”转化为“可以在剩余容量上继续运行的运维事件”。
