Splitwise：按推理阶段拆分机器，面向成本与功耗设计集群

发表于 2026-11-23 分类于 人工智能系统 阅读时长 ≈ 14 分钟
ISCA 2024 论文 Splitwise 阅读笔记。论文基于 Azure 生产 trace 刻画 Prompt 与 Token 两个阶段在批处理、显存、功耗和硬件敏感度上的差异，提出把两个阶段拆分到不同机器，并据此设计同构与异构集群，在吞吐、成本、功耗三个目标之间取舍。

Splitwise（ISCA 2024，华盛顿大学与微软）与 DistServe 是同期提出 PD 分离的两篇工作，但视角不同。DistServe 从 SLO 出发，讨论每张 GPU 能承载多少请求；Splitwise 从 云厂商的集群建设 出发，讨论同样的功耗和成本预算下应当采购和部署什么样的机器。

论文先用 Azure 的生产 trace 做了一组特征刻画，得到的核心结论是：Token 生成阶段并不需要最新 GPU 的算力。它受显存容量和带宽限制，功耗上限降低 50% 几乎不影响延迟，在 A100 上运行的性价比不低于 H100。基于这一点，Splitwise 把 Prompt 阶段和 Token 阶段拆到不同机器上，并为两个阶段分别选择硬件。

Splitwise：按推理阶段拆分机器，面向成本与功耗设计集群

项目 内容
标题 Splitwise: Efficient Generative LLM Inference Using Phase Splitting
作者 Pratyush Patel、Esha Choukse、Chaojie Zhang、Aashaka Shah、Íñigo Goiri、Saeed Maleki、Ricardo Bianchini
机构 University of Washington、Microsoft
会议 ISCA 2024
原文 arXiv:2311.18677

术语对应：论文中的 Prompt 阶段 即 Prefill，Token 阶段 即 Decode，TBT（time between tokens）对应 DistServe 中的 TPOT。本文沿用论文的叫法。

1. 背景：算力增长快于显存

论文的出发点是 GPU 代际之间的不均衡。DGX-H100 相对 DGX-A100：

指标 A100 H100 比值
算力（TFLOPs） 19.5 66.9 3.43×
HBM 容量 80 GB 80 GB 1.00×
HBM 带宽 2039 GBps 3352 GBps 1.64×
功耗 400 W 700 W 1.75×
整机价格 17.6 美元/小时 38 美元/小时 2.16×

算力提高到 3.43×，显存带宽只有 1.64×，容量没有变化，价格和功耗则分别是 2.16× 和 1.75×。同时，云厂商新建数据中心已经受到供电能力的限制。

一次推理请求包含两个阶段：Prompt 阶段并行处理全部输入 token，是计算密集的；Token 阶段逐个生成输出 token，每一步都要访问完整的 KV Cache，受显存带宽和容量限制。如果两个阶段对硬件的需求不同，那么全部使用最新 GPU 就未必合理。

2. 动机：生产 trace 上的七条观察

论文使用 2023 年 11 月 11 日 Azure 两个 LLM 推理服务（coding 和 conversation）的生产 trace，在 8 × H100 的机器上用 vLLM 运行 BLOOM-176B 和 Llama2-70B，得到七条 insight：

# 观察 关键数据
I 不同服务的输入输出分布差别很大 coding：prompt 中位数 1500 token，输出中位数 13 token；conversation：1020 / 129
II 混合连续批处理下，机器大部分时间只在处理很少的 token conversation 有 60–70% 的时间活跃 token 不超过 20 个；coding 有 20% 以上的时间只处理 1 个 token
III 端到端时间主要花在 Token 阶段 BLOOM-176B 上，1500 个输入 token 的 Prompt 阶段耗时只相当于生成 6 个输出 token
IV Prompt 阶段的 batch 应当受限，Token 阶段的 batch 越大越好 Prompt 吞吐在 2048 token 之后下降；Token 吞吐持续增长到 batch 64，此时显存耗尽
V Prompt 阶段受算力限制，Token 阶段受显存容量限制 —
VI Prompt 阶段充分使用了功耗预算，Token 阶段没有 功耗上限从 700 W 降到 350 W，Token 阶段延迟几乎不变
VII Token 阶段可以运行在算力较弱的硬件上 A100 上 TTFT 约为 H100 的 2 倍，TBT 只慢约 1.4 倍，单请求成本和能耗不高于 H100

图 4：混合连续批处理下，机器在各活跃 token 数上花费时间的累积分布。conversation 负载大部分时间只有极少的活跃 token。

图 6：左为 Prompt 阶段，右为 Token 阶段。Prompt 吞吐在 2048 token 后下降，Token 吞吐随 batch 增大持续上升。

图 9：左为 Prompt 阶段的 TTFT，右为 Token 阶段的 TBT。Token 阶段在功耗上限降至 350 W 之前延迟基本不变。

这七条观察可以归纳为两点：

  • 混合部署下 Token 阶段的 GPU 利用率很低（II、IV）。Token 阶段需要大 batch 才能有效利用 GPU，但与 Prompt 阶段共用机器时很难形成大 batch。
  • Token 阶段对算力和功耗不敏感（V、VI、VII）。这为它使用旧型号 GPU 或限制功耗提供了依据。Llama-70B 上，H100 的单请求成本是 A100 的 1.24×（coding）和 1.5×（conversation），能耗是 1× 和 1.2×。

3. 设计

3.1 三个机器池与两级调度

图 10：集群级调度器（CLS）管理 Prompt 池、Token 池和 Mixed 池；每台机器上的机器级调度器（MLS）管理等待队列和 batch；KV Cache 通过 InfiniBand 传输。

所有机器都预先加载模型。请求到达后，CLS 同时为它分配一台 Prompt 机器和一台 Token 机器。Prompt 机器完成输入处理并生成第一个 token，然后把 KV Cache 传给 Token 机器继续生成。

集群级调度（CLS）

  • 路由采用 Join the Shortest Queue，队列长度按待处理的 token 数计算。
  • Mixed 池 用于处理负载波动。某一类队列超过阈值时，CLS 先在 Mixed 池中寻找机器；Mixed 池也满时，从另一个池借一台机器放入 Mixed 池。Mixed 池中的机器按普通的混合连续批处理运行，队列清空后回到原来的池。
  • 如果负载分布长期偏离预期，再做粗粒度的机器角色重新划分。

机器级调度（MLS）

  • Prompt 机器：FCFS，一个 batch 的 prompt token 总数限制在 2048 以内（依据 insight IV）。
  • Token 机器：FCFS，尽可能增大 batch，显存接近耗尽时开始排队。
  • Mixed 机器：优先调度 Prompt 以满足 TTFT，必要时抢占 Token；通过随等待时间提高优先级、限制单个请求被抢占的次数来避免饥饿。

3.2 KV Cache 逐层传输

KV Cache 传输是分离引入的主要开销。朴素做法是 Prompt 阶段结束后串行传输，这段时间直接计入第二个 token 的延迟，并且随 prompt 长度线性增长。

图 11：左为串行传输，右为逐层传输。逐层传输与 Prompt 计算重叠进行。

Splitwise 的做法是 逐层异步传输：Prompt 机器每计算完一层，就立即异步发送该层的 KV Cache，同时继续计算下一层。传输时间大部分与 Prompt 计算重叠。因为 CLS 在调度时已经确定了 Token 机器，传输可以在 Prompt 计算过程中开始。

逐层传输需要每层同步，对短 prompt 可能反而增加 TTFT。短 prompt 的 KV Cache 本身很小，所以 Splitwise 对短 prompt（H100 上小于 512 token）使用串行传输，对长 prompt 使用逐层传输。实现上使用 MSCCL++ 的零拷贝单边 put 原语。

3.3 集群配置

Splitwise 提出四种集群设计，命名中第一个字母表示 Prompt 机器，第二个表示 Token 机器：

设计 Prompt 机器 Token 机器 说明
Splitwise-AA DGX-A100 DGX-A100 同构
Splitwise-HH DGX-H100 DGX-H100 同构
Splitwise-HA DGX-H100 DGX-A100 异构，依据 insight VII
Splitwise-HHcap DGX-H100 限功耗的 DGX-H100 Token 机器每张 GPU 功耗上限降低 50%，整机降至额定功耗的 70%，依据 insight VI

两个池各配置多少台机器，由一个事件驱动的集群模拟器搜索得到。输入包括集群设计、性能模型、trace、SLO、约束（如吞吐）和优化目标（如成本最低）。例如 coding 负载、目标 70 RPS 时，Splitwise-HH 成本最优的配置是 27 台 Prompt 机器加 3 台 Token 机器。

优化目标有三个：吞吐、成本、功耗。论文指出用户和云厂商的关注点不同，用户关注成本，云厂商更关注功耗和空间。

4. 实验结果

设置。KV Cache 传输机制在 vLLM 上实现，并在 Azure 上的两台 DGX-A100 和两台 DGX-H100 虚拟机上实测。集群规模的结果全部来自模拟器：性能模型为分段线性模型，平均绝对百分比误差小于 3%。SLO 以 DGX-A100 无竞争时的延迟为基准，要求 TTFT、TBT、E2E 的 P50/P90/P99 共九项全部满足（例如 TTFT 的 P50/P90/P99 分别不超过 2×/3×/6×，TBT 和 E2E 不超过 1.25×/1.5×/5×）。基线 Baseline-A100 和 Baseline-H100 是全部使用混合连续批处理的同构集群。

4.1 KV Cache 传输开销

图 14：串行传输的延迟随 prompt 长度线性增长；逐层传输中未被重叠的部分基本恒定。

  • 逐层传输后，未被重叠的传输时间约为 8 ms（A100，200 Gbps）和 5 ms（H100，400 Gbps），相对 Prompt 计算时间的开销小于 7%。
  • 对端到端延迟的影响为 0.8%，串行传输最高为 3%。
  • 用户能感知到的只有第二个 token 的延迟：Splitwise 增加 16.5%，串行传输增加 64%。

4.2 等功耗下的吞吐

以 40 台 DGX-H100 的功耗为预算，同样的功耗可以部署 70 台 DGX-A100。

图 16：上为 coding trace，下为 conversation trace。各子图为归一化的 P50/P90/P99 TTFT、TBT、E2E，红色虚线为 SLO。图例括号内为 Prompt 机器数（P）和 Token 机器数（T）。

  • 机器配比反映了负载特征：Splitwise-HH 在 coding 负载下为 35P + 5T，在 conversation 负载下为 25P + 15T。
  • coding 负载下，Baseline-H100 随负载升高出现 TBT 过高的问题，原因是长 prompt 与 Token 阶段混合批处理。
  • Splitwise-AA 吞吐高，但 TTFT 始终偏高；Splitwise-HA 在高吞吐下同时保持了较低的 TTFT 和 E2E。
  • conversation 负载下 Splitwise-HHcap 在各项指标上都最好，因为它的 Token 阶段运行时间长，Token 机器受益更多。
  • 低负载（70 RPS）时，Baseline-H100 的 40 台机器有 70% 的时间只在处理不超过 15 个 token；Splitwise 的 Token 机器形成的 batch 更大。

4.3 不同优化目标下的集群设计

图 18：conversation trace。左为等功耗，右为等成本，数值均相对 Baseline-A100 归一化。

图 19：左为功耗最优，右为成本最优。

场景 结果
等功耗，吞吐最优 Splitwise-AA 相对 Baseline-A100，在相同功耗和成本下吞吐为 2.15×
等成本，吞吐最优 Splitwise-AA 相对 Baseline-H100 吞吐高 1.4×，但功耗高 25%，占用空间为 2×
等吞吐，功耗最优 Splitwise-HHcap 相对 Baseline-H100 功耗低 25%，成本和空间相同
等吞吐，成本最优 Splitwise-AA 相对 Baseline-H100 成本低 25%

没有一种设计在所有目标上都最优。对用户而言，Splitwise-AA 用更容易获得的旧 GPU 取得了更高的吞吐；对云厂商而言，Splitwise-HHcap 在不增加成本和空间的前提下降低了 25% 的功耗。

论文摘要和结论给出的总体数字是“吞吐高 1.4× 且成本低 20%”“相同功耗和成本下吞吐为 2.35×”，结论部分还有“1.76× 吞吐、功耗低 15%”。这些数字与第 VI 节正文的逐项结果不完全一一对应，上表采用正文数据。

4.4 负载变化与离线任务

  • 负载变化：在为 coding 设计的集群上运行 conversation trace，同构的 Splitwise-AA 和 Splitwise-HH 依靠 Mixed 池调整，吞吐和延迟没有损失；Splitwise-HA 和 Splitwise-HHcap 因两个池的机器类型不同，吞吐下降 7%，但仍优于基线。
  • 离线任务：不考虑延迟 SLO、把负载加到很高时，所有机器都进入 Mixed 池，Splitwise 退化为同等规模的基线。Splitwise-AA 与 Baseline-A100 同为 0.89 RPS/美元，Splitwise-HH 与 Baseline-H100 同为 0.75 RPS/美元。

5. 局限

  • 评估主要依赖模拟：真实硬件上只验证了两台机器之间的 KV Cache 传输，集群规模的吞吐、成本、功耗结论来自模拟器。
  • 异构集群的互连：论文假设 Prompt 与 Token 机器之间都有 InfiniBand。作者承认 H100 与 A100 之间的 InfiniBand 连接在现实中并不常见，把数据中心按 GPU 类型分割也会给云厂商带来运维问题。
  • 容错：任一台机器故障后请求从头重新执行，KV Cache 检查点只作为设想提出。
  • 多轮对话：论文假设每次请求都携带完整上下文、不跨请求复用 KV Cache。如果服务端缓存上下文，Prompt 阶段的显存使用特征会改变，KV Cache 还需要传回 Prompt 机器。
  • CLS 的可扩展性：集中式的集群调度器在大规模集群下可能成为瓶颈。

6. 总结与思考

1. 分离的价值在于两个阶段可以使用不同的硬件。 DistServe 论证了分离可以消除干扰、独立配置并行策略；Splitwise 进一步指出两个阶段对算力、显存、功耗的敏感度不同，因此可以分别选型。Token 阶段可以使用旧 GPU 或限制功耗，这是混合部署无法做到的。

2. 优化目标由谁来定义，决定了最优设计。 同一套机制下，用户关注成本时最优的是 Splitwise-AA，云厂商关注功耗时最优的是 Splitwise-HHcap。论文把功耗和空间作为一等指标，这是它与多数推理系统论文的主要区别，也反映了数据中心供电受限的现实。

3. 两篇论文对传输开销的处理互为补充。 DistServe 通过部署约束把传输限制在节点内的 NVLink 上；Splitwise 做的是机器级的拆分，传输必须跨节点，因此用逐层异步传输把传输时间与 Prompt 计算重叠起来。前者依赖节点内带宽，后者依赖 InfiniBand，适用的集群条件不同。

4. Mixed 池是分离架构对负载波动的回退机制。 静态划分两个池会在负载变化时造成资源碎片。Splitwise 允许机器临时回到混合批处理模式，高负载下整个系统退化为基线。这意味着分离的收益主要出现在有延迟 SLO、负载未饱和的在线场景；对离线吞吐任务没有收益，这一点与 DistServe 的结论一致。

5. 异构设计的灵活性较低。 负载变化实验中，同构设计没有损失，异构设计吞吐下降 7%。异构硬件带来的成本和功耗收益，需要与负载变化时的适应能力以及运维复杂度一起权衡。
