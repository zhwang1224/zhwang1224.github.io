DistServe：把 Prefill 和 Decode 拆到不同 GPU 上

发表于 2026-11-23 分类于 人工智能系统 阅读时长 ≈ 12 分钟
OSDI 2024 论文 DistServe 阅读笔记。论文指出 Prefill 与 Decode 混部会带来相互干扰和资源耦合，提出 PD 分离并以 per-GPU goodput 为目标自动搜索两阶段的并行策略与部署方案，在三类应用上相对 vLLM 最高支撑 7.4× 请求速率或 12.6× 更严格的 SLO。

DistServe（OSDI 2024，北京大学、阶跃星辰、UCSD）是 PD 分离（Prefill-Decode Disaggregation）方向的代表性工作。它的出发点是：LLM 服务真正要优化的是 在 TTFT 和 TPOT 两个 SLO 约束下，每张 GPU 能承载的最大请求速率（per-GPU goodput），总吞吐只是一个间接指标。

在这个目标下，把 Prefill 和 Decode 放在同一批 GPU 上做 continuous batching 会同时拖慢两个阶段。DistServe 把两个阶段拆到不同的 GPU 实例上，分别配置资源与并行策略，再用一个基于模拟器的搜索算法自动找部署方案。最终相对现有系统可以多服务 7.4× 的请求，或支撑 12.6× 更严格的 SLO。

DistServe：把 Prefill 和 Decode 拆到不同 GPU 上

项目 内容
标题 DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving
作者 Yinmin Zhong、Shengyu Liu、Junda Chen、Jianbo Hu、Yibo Zhu、Xuanzhe Liu、Xin Jin、Hao Zhang
机构 北京大学、StepFun、UC San Diego
会议 OSDI 2024
原文 arXiv:2401.09670

1. 背景：两个阶段，两个指标

一次 LLM 请求分两个阶段：

  • Prefill：一次性并行处理整个 prompt，产生第一个 token。对应指标是 TTFT（time to first token）。
  • Decode：逐 token 自回归生成，每步只处理一个新 token。对应指标是 TPOT（time per output token）。

两个阶段的计算特征差别很大。以 13B 模型为例，一条 512 token 的 prompt 就能让 A100 接近 compute-bound，再往 batch 里加请求只会等比例拉长执行时间；Decode 每步只算一个 token，却要读一遍模型权重和 KV Cache，受显存带宽限制，必须靠大 batch 才能把 GPU 利用率提高。

图 3：左为 Prefill，右为 Decode。Prefill 的吞吐很快饱和，Decode 的吞吐随 batch size 持续增长。

不同应用对两个指标的要求也不同：聊天机器人要求 TTFT 低，TPOT 只需快过人的阅读速度；文档摘要可以容忍较长的 TTFT，但要求 TPOT 低。论文据此定义优化目标 per-GPU goodput：在给定 SLO 达标率（如 90%）下，每张 GPU 能承载的最大请求速率。它直接决定单次请求的成本。

2. 动机：混合部署的两个问题

现有系统（vLLM 等）把两个阶段放在同一批 GPU 上，用 continuous batching 最大化总吞吐。论文用一个实验说明这种做法在 SLO 约束下的代价：

图 1：输入长度 512、输出长度 64 的合成负载。蓝线为现有混部系统，橙线和绿线分别是只跑 Prefill、只跑 Decode 的系统。

混部时单卡 goodput 约为 1.6 rps；单独跑 Prefill 可达 5.6 rps，单独跑 Decode 可达 10 rps。按 2 张 GPU 做 Prefill、1 张做 Decode 来配比，整体可达 10 rps，即每卡 3.3 rps，是混部的 2.1×。差距来自两方面。

2.1 Prefill 与 Decode 相互干扰

图 2：13B 模型，对比纯 Decode batch 与加入一个 Prefill 任务后的 batch 执行时间。输入越长（右图），Decode 被拖慢得越严重。

一个 Prefill step 远比一个 Decode step 长。放进同一个 batch，Decode 要等 Prefill 算完，TPOT 上升；Decode 任务也会拉长 Prefill 的时间。即使不合并 batch、改为分开调度，两者仍然竞争同一张 GPU，优先任何一方都会损害另一方。

Chunked prefill（SARATHI、DeepSpeed-MII）把长 Prefill 切块后和 Decode 拼在一起，可以缓解干扰但无法消除，并且有额外代价：chunk 小了 Prefill 吃不满 GPU，chunk 大了留给 Decode 的空位很少；每个 chunk 都要重新加载之前所有 chunk 的 KV Cache，切成 N 块时 KV Cache 的加载量从 变成 。

2.2 资源与并行策略被耦合

共置部署意味着两个阶段共用同一套 GPU 数量和并行配置。Prefill 是 compute-bound 的，希望用 intra-op 并行压低执行时间来满足 TTFT；Decode 的最优配置取决于 batch size。系统只能按更严格的那个 SLO 来配置，另一个阶段的资源就被过度供给。

消融实验印证了这一点：给 vLLM 枚举所有并行策略后选最优（vLLM++），结果和默认配置完全一样。只要干扰还在，调整并行策略就没有收益。

结论是 低速率或 TTFT SLO 很紧时用 intra-op，高速率时用 inter-op，分界点还取决于 。

Decode 实例。关键是 batch 要大。混部时 Prefill 抢占 GPU 时间，Decode 的 batch 做不大；分离后可以让多个 Prefill 实例对应一个 Decode 实例，在专用 GPU 上合并出大 batch。并行方面，intra-op 降低延迟但收益递减，inter-op 几乎线性提升吞吐，所以 TPOT SLO 紧时先用 intra-op 满足延迟，其余用 inter-op 扩大吞吐。

KV Cache 传输是分离引入的新开销。OPT-66B 上一条 512 token 请求的 KV Cache 约 1.13 GB，10 rps 时需要约 90 Gbps 带宽。有 InfiniBand 的集群可以直接承受；跨节点带宽不足时，需要让传输走节点内的 NVLink，这会约束部署方式。

3.2 Placement 搜索算法

输入模型、负载特征、SLO 和达标率目标，输出一个 placement：两类实例各自的并行策略、各自的数量、在集群上的摆放方式。

SLO 达标率没有解析公式，所以论文构建了一个 模拟器：从历史 trace 拟合到达过程和输入输出长度分布，重采样后用延迟模型估计达标率，再用二分查找找出每个配置的最大 goodput。

  • 算法 1（高节点亲和性，跨节点带宽充足）：Prefill 和 Decode 可以放在任意节点。分别枚举两类实例的 (inter-op, intra-op) 配置，各自取 per-GPU goodput 最高的，再按目标流量复制。复杂度 。
  • 算法 2（低节点亲和性，跨节点带宽有限）：KV Cache 只在 Prefill 和 Decode 的 对应层 之间传输。因此用 inter-op 把模型按层切成 stage，把两类实例中同一 stage 的 segment 放在同一节点内，KV Cache 就只经过 NVLink。在这个约束下联合枚举节点内的配置。

算法 2 解决了大模型的部署问题：OPT-175B 权重 350 GB，一个 8 × 80 GB 的节点放不下一对完整的 Prefill 和 Decode 实例，但按 stage 切开后可以。

3.3 运行时

图 6：Controller 以 FCFS 把请求分发到队列最短的 Prefill 实例，完成后再交给负载最低的 Decode 实例。

三个在线优化：

  • 减少流水线空泡：prompt 长度不一会让 inter-op 流水线出现空泡。Prefill 侧按总长度接近 来组 batch，使各 batch 执行时间接近。
  • 应对突发：KV Cache 由 Decode 实例按需 pull，Prefill 实例的显存充当排队缓冲，避免突发流量压垮 Decode 实例的显存。
  • 重规划：监控负载特征，变化显著时重新运行 placement 算法。算法运行时间最多为分钟级，重新加载权重也是分钟级，远短于负载变化的小时级周期。

系统实现为推理引擎之上的编排层，Python 6.5K 行，C++/CUDA 8.1K 行。跨节点传输用 NCCL，节点内用异步 CudaMemcpy。

4. 实验结果

设置：4 节点 × 8 张 A100-80GB，节点内 NVLink，跨节点仅 25 Gbps，因此主要使用算法 2。模型为 OPT-13B/66B/175B（选 OPT 是因为它使用标准 MHA，KV Cache 大，对传输压力最大）。基线为 vLLM 和支持 chunked prefill 的 DeepSpeed-MII。SLO 达标率目标为 90%。

应用 模型 TTFT SLO TPOT SLO 数据集（平均输入 / 输出 token）
Chatbot OPT-13B 0.25 s 0.1 s ShareGPT（755.5 / 200.3）
Chatbot OPT-66B 2.5 s 0.15 s ShareGPT
Chatbot OPT-175B 4.0 s 0.2 s ShareGPT
Code Completion OPT-66B 0.125 s 0.2 s HumanEval（171.3 / 98.2）
Summarization OPT-66B 15 s 0.15 s LongBench（1738.3 / 90.7）

图 9：左两幅为代码补全（HumanEval），右两幅为摘要（LongBench）。

应用 对比 vLLM：速率 / SLO 对比 DeepSpeed-MII：速率 / SLO
Chatbot 2.0×–4.6× / 1.8×–3.2× 1.6×–7.4× / 1.7×–1.8×
Code Completion 5.7× / 1.4× 1.6× / 1.4×
Summarization 4.3× / 12.6× 1.8× / 2.6×

三类应用的瓶颈不同，收益的来源也不同：

  • Chatbot：vLLM 大部分请求能满足 TTFT，但 Decode 被 Prefill 拖慢，大量请求违反 TPOT。DistServe 为 OPT-175B 找到的方案是 Prefill 实例 inter-op = 3、intra-op = 3，Decode 实例 inter-op = 3、intra-op = 4，这种配置很难手工找到。
  • 代码补全：TTFT 要求最严，各系统都受 TTFT 限制。DistServe 去掉了 Decode 的干扰，搜索算法又自动给 Prefill 实例加大 intra-op 并行。
  • 摘要：输入很长、TTFT 宽松、TPOT 严格。vLLM 的 Decode 被长 Prefill 严重拖慢，所以这里 SLO 的差距最大（12.6×）。

DeepSpeed-MII 在大模型上表现好于 vLLM，但 chunked prefill 本身比完整 Prefill 慢，它是用 TTFT 换 TPOT。

4.2 传输开销

图 10：左为 OPT-175B 在 ShareGPT 上的延迟分解，右为三个模型的 KV Cache 传输时间 CDF。

即使是 OPT-175B，KV Cache 传输也只占总延迟的 不到 0.1%，超过 95% 的请求传输延迟小于 30 ms。这是在跨节点只有 25 Gbps 的集群上得到的，依靠的是算法 2 把传输限制在节点内 NVLink 上。

4.3 消融与算法开销

  • 模拟器与真实系统的 SLO 达标率误差在所有情况下小于 2%。
  • vLLM++（枚举并行策略取最优）与 vLLM 性能相同；DistServe-High（算法 1）优于 DistServe-Low（算法 2），因为没有“同 stage 同节点”的约束。
  • 搜索算法在最大规模设置下运行时间不超过 1.3 分钟，且与模型大小无关。

5. 局限

论文在 Discussion 中明确了适用范围：

  • 吞吐优先的离线场景：对延迟不敏感时，chunked prefill 能把每个 batch 填到 compute-bound，GPU 利用率更高。
  • 资源受限场景：只有几张甚至一张 GPU 时，分离没有可调整的空间，混部更简单。
  • 容错：一个 Decode 实例对应多个 Prefill 实例，Decode 实例故障会波及多个 Prefill 实例。论文未实现抢占和容错。
  • 长上下文：KV Cache 随 prompt 长度线性增长，Prefill 计算量按平方增长，传输的相对占比反而下降，同时两阶段的干扰更严重。作者据此认为 PD 分离在长上下文下仍然适用。

此外，实验中 Prefill 和 Decode 用的是同一种 GPU，没有涉及异构硬件；模拟器假设负载在小时级别上可预测。

6. 总结与思考

1. 优化目标决定架构。 continuous batching 对总吞吐是最优的，对 goodput 则不是。DistServe 的贡献首先在于把目标从 throughput 换成带 SLO 约束的 per-GPU goodput，PD 分离是这个目标下的自然结果。反过来，离线场景下目标变回吞吐，混部加 chunked prefill 仍然更合适。

2. 分离的收益主要来自解耦。 消除干扰只是第一层；更重要的是两个阶段可以独立选择 GPU 数量、batch 策略和并行方式。vLLM++ 与 vLLM 性能相同，说明混部时这部分调优空间是被干扰锁死的。

3. 传输开销可以靠部署方式消除。 PD 分离最常被质疑的是 KV Cache 传输。论文的处理方式是利用“KV Cache 只在对应层之间传输”这一结构，把传输限制在节点内 NVLink，而不依赖高速跨节点网络。新的注意力结构（GQA、MQA）会进一步缩小 KV Cache。

4. 分离后问题变成了配比与调度。 Prefill 与 Decode 实例的比例取决于输入输出长度分布和 SLO，负载变化后需要重新规划。DistServe 用离线模拟加周期性重规划来处理，这也是后续工作和生产系统（弹性配比、异构硬件、前缀缓存与 PD 分离的配合）继续展开的方向。
