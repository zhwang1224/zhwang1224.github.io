KVCache 传输与计算方式的演进：从整体传输到逐层载入与写回

发表于 2026-11-27 分类于 人工智能系统 阅读时长 ≈ 16 分钟
用 7 张图梳理 PD 分离推理中 KVCache 的传输与计算方式：从共置执行、整体传输（DistServe）、逐层传输（Splitwise）到逐层载入与写回（Mooncake），再把 vLLM、SGLang、LMCache、NVIDIA Dynamo、NIXL 与 Mooncake 的开源实现归纳为四类方法。

Prefill 与 Decode 分离（PD 分离）之后，KV Cache 不再“在哪算就在哪用”：Prefill 算出的 KV 要搬到 Decode；前缀缓存普及后，命中的历史 KV 还要从 CPU 内存、SSD 甚至别的节点搬回 Prefill。KV 传输从一项附带开销，变成了推理系统的核心设计问题。

本文按技术形态把这条演进线分为四代（第 0–3 代），每代配一张图，说明它怎样安排计算与传输、解决了什么、又留下了什么；最后把 vLLM、SGLang、LMCache、NVIDIA Dynamo、NIXL 与 Mooncake 的开源实现归纳为四类方法。论文部分的细节均对照原文核实，开源部分依据 2025–2026 年的官方文档、源码与技术报告。

KVCache 传输与计算方式的演进

工作 出处 本文用到的内容
DistServe OSDI 2024 整体传输、按 stage 放置、Decode 拉取
Splitwise ISCA 2024 逐层传输、串行与逐层的切换
Mooncake FAST 2025（arXiv 版含 §5.2） 逐层载入与写回、分布式 KVCache 池
vLLM、SGLang、LMCache、Dynamo、NIXL、Mooncake 官方文档、源码、LMCache 技术报告 开源系统中的实际做法

1. 总览

先看 KV 有多大。DistServe 给出的例子是：OPT-66B 上，一个 512 token 请求的 KV 约 1.13 GB。Mooncake 仓库给出的量级是：LLaMA3-70B 上，128k token 对应约 40 GB KVCache。搬这些数据的时间如果不能藏进计算里，就会直接加到延迟上。

图 1：第 0–3 代的时序示意与要点，底部为开源工程实现的四类方法。

这条演进线有两条主线：

  • 传输粒度越来越细，以便与计算重叠。 从整个请求（第 1 代），到每一层（第 2 代），再到“载入、计算、写回”三条流并行（第 3 代）。开源系统里还有按 prefill chunk 传输的中间粒度。
  • 要搬的 KV 从“刚算出的”扩展到“命中的历史 KV”。 第 1、2 代只关心 Prefill → Decode 的新 KV；有了前缀缓存，Prefill 要先把命中的 KV 读进来（第 3 代）。命中率越高，prefill 越受载入带宽限制，这也是开源实现在多级缓存、预取和 I/O kernel 上持续优化的原因。

分代依据的是技术形态，不严格按发表时间：Splitwise 的 arXiv 版（2023 年 11 月）早于 DistServe（2024 年 1 月），而 Splitwise 的串行传输基线就是第 1 代的做法。

2. 第 0 代 → 第 1 代：PD 分离与整体传输

共置执行（Orca、vLLM 等早期系统，也是 DistServe 和 Splitwise 的基线）中，Prefill 与 Decode 在同一张 GPU 上批处理，KV 在本卡 HBM 中产生并直接使用，不需要传输。问题在于两阶段的计算特征完全不同：prefill 计算密集，decode 访存密集，新请求的 prefill 插进来会拖慢正在 decode 的请求；两阶段还只能共用一套资源分配和并行策略。

PD 分离把两阶段放到不同实例上，代价是必须把 KV 从 Prefill 实例搬到 Decode 实例。最直接的做法是 整体传输：prefill 全部算完、得到首 token 之后，把整个请求的 KV 一次性交出去。

图 2：(a) 一个请求的时序；(b) 带宽需求的估算；(c) 跨节点带宽有限时的放置方式。

DistServe 没有试图把传输藏进计算，而是从两方面降低它的影响：

  • 拉取而非推送。 Decode 实例按自己的节奏拉取 KV，Prefill 实例把 KV 留在显存里继续处理别的 prefill，显存充当排队缓冲。突发流量时，Decode 显存不会被大量同时涌入的 KV 压垮。
  • 用放置把传输限制在 NVLink 上。 按 10 rps 计算，OPT-66B 需要约 90 Gbps 才能让传输开销不可见。有 InfiniBand 时可以忽略；跨节点带宽有限时，DistServe 利用一个观察：KV 只在 Prefill 与 Decode 实例的 对应层 之间传输。于是用 inter-op（流水线）并行把模型按层切成 stage，同一 stage 的 Prefill 段和 Decode 段放在同一节点，KV 就只走节点内 NVLink。在跨节点仅 25 Gbps 的测试床上，OPT-175B 的 KV 传输只占总延迟的不到 0.1%。

整体传输的根本问题是传输时间随 prompt 长度线性增长，并且完全暴露在首个 decode 步之前。Splitwise 的串行基线把这一点说得更直接：首 token 生成后才开始传，传完才能生成下一个 token。

3. 第 2 代：逐层传输

Splitwise 注意到，prefill 是逐层计算的，第 i 层算完时这一层的 KV 就已经完整了，不必等到最后一层。

图 3：(a) 串行传输；(b) 逐层传输；(c) 设计要点与实测开销。

  • 做法。 每算完一层，就异步发出这一层的 KV，同时继续算下一层。实现上用 MSCCL++ 的零拷贝单边 put，KV 一就绪就经 InfiniBand 写到 token 机器，接收方不用发起 receive；全部层 put 完后置位一个 semaphore，token 机器据此开始生成。
  • 前提。 集群调度器在调度请求时就同时选定 prompt 机器和 token 机器，传输目标事先已知，计算过程中才能开始发送。
  • 折中。 逐层传输要求每层细粒度同步，可能干扰计算、增加 TTFT。短 prompt 的 KV 本来就小，不需要靠重叠来隐藏。Splitwise 在计算开始前根据 batch 的 token 数做选择：短 prompt（H100 上少于 512 token）用串行传输，长 prompt 用逐层传输。
  • 效果。 串行传输的可见延迟随 prompt 长度线性增长；逐层传输未被重叠的部分基本恒定，A100（200 Gbps）约 8 ms，H100（400 Gbps）约 5 ms，相对 prompt 计算时间不到 7%。coding trace 上，串行传输最多增加 3% 的端到端延迟，Splitwise 的混合策略只增加 0.8%。

逐层传输解决了“传出去”的问题，但每个请求仍从头 prefill，不涉及跨请求复用 KV。

4. 第 3 代：逐层载入与逐层写回

前缀缓存让 prefill 只需计算未命中的 token，但命中的 KV 必须先进入 HBM。Mooncake 把 KV 放进由集群 CPU 内存（以及 SSD）组成的分布式 KVCache 池，并把“载入命中的 KV”和“写出新 KV”都改成逐层进行。

图 4：(a) 一个请求的数据通路，编号对应论文图 3 的 s1–s4；(b) Prefill 内部载入、计算、写回三条流的时序；(c) 调度与传输引擎。

数据通路（图 4a）。

  1. KVCache 复用：命中的前缀 KV 从 CPU DRAM 逐层载入 HBM。前缀在别的节点时，经 RDMA 取回。
  2. 增量 prefill：只计算未命中的 token；未命中 token 超过阈值（通常大于 1000）时切成多个 chunk，在多个 Prefill 节点上流水执行（CPP）。新 KV 逐层写回 CPU DRAM。
  3. KVCache 传输：前缀与增量 KV 按层流式发往 Decode 节点的 CPU DRAM，与第 2 步重叠，由 Transfer Engine 经 RDMA 完成（每节点最高 8 × 400 Gbps）。
  4. Decode：KV 收齐后异步载入 HBM，与其他请求的 decode 并行，然后加入 continuous batching。

Prefill 内部的三条流（图 4b，arXiv 版 §5.2）。 每层 attention 开始前，等待这一层的 KV 载入完成，并发起下一层的异步载入；attention 结束后，发起这一层 KV 的异步写回；所有层算完后，等待全部写回完成。载入和计算由不同硬件并行完成，prefill 的执行时间约为 max（KV 载入时间，标准 prefill 计算时间）而不是两者之和，取哪一个由前缀占输入的比例决定。

对显存的影响。 Mooncake 把 KV 占用显存的代价看作“大小 × 占用时长”，逐层载入与写回缩短了占用时长，所以只要显存能装下单个请求，prefill 调度就不必考虑剩余显存，只看 KV 分布和 DRAM 容量。

调度（图 4c）。 Conductor 按前缀命中长度和排队时间估算各 Prefill 实例的 TTFT，选最短者；请求没有被调度到前缀最长的实例时，新实例从持有者取回 KV 并存到本地，热点块由此在多个节点上有副本。

这一代留下的问题是：命中率越高，prefill 的时间越由载入带宽决定。开源实现里的预取策略、GPU 辅助 I/O kernel 和 chunk 聚合，针对的都是这一点。

5. 开源工程实现

5.1 四类方法

第 1–3 代的思路在开源系统里已经拆成了几类可复用的组件：

方法 要解决的问题 做法 代表实现
① PD 间传输 把 Prefill 的 KV 送到 Decode 请求级拉取，或 chunk 级推送；经 RDMA / NVLink 在显存之间直接传输 vLLM NixlConnector、SGLang PD、LMCache PD
② 逐层载入与写回 隐藏载入和写回时间，限制显存占用 在每层 attention 前后挂钩子，用独立 CUDA 流或 DMA 搬运 vLLM KV Connector、SGLang HiCache、LMCache
③ 多级 KV 缓存 显存放不下历史 KV，跨实例复用 HBM → 主机 DRAM → 存储后端；按 page 或 chunk 组织数据，配合预取与写回策略 SGLang HiCache、LMCache、Mooncake Store
④ 传输库与编排 屏蔽 NVLink、RDMA、GDS 等通路差异，按 KV 位置调度 插件式传输后端，多网卡聚合与拓扑感知选路，KV 感知路由 NIXL、Mooncake Transfer Engine、NVIDIA Dynamo

其中 ① 对应第 1、2 代，并多出 chunk 这一中间粒度；② 和 ③ 对应第 3 代；④ 是它们共同的底座。下面分别展开。

5.2 Prefill → Decode 的传输

图 5：(a) vLLM NixlConnector；(b) SGLang PD；(c) LMCache PD；(d) NVIDIA Dynamo 的编排流程。

三种实现在粒度和发起方上各不相同：

  • vLLM NixlConnector：请求级、Decode 拉取。 Prefill 算完后，KV 块留在 Prefill 显存中，租约默认 30 秒，Decode 排队时用心跳续租；Decode 通过 NIXL 读取 KV 块，读完通知 Prefill 释放。NIXL 默认后端为 UCX，同机走 cuda_ipc，跨机走 RDMA。多轮对话可以开启双向模式，由 Prefill 先从 Decode 拉取上一轮已有的 KV 块，只计算新 token。vLLM 文档也明确指出，PD 分离用于分别调优 TTFT 与 ITL、控制尾部 ITL，并不提升吞吐。
  • SGLang PD：chunk 级、Prefill 推送。 默认由 Decode 在 prefill 完成前预留目标 KV 槽位；Prefill 每完成一个 chunk 就调用 send_kv_chunk，经 Mooncake Transfer Engine 或 NIXL 用 RDMA 写入 Decode 显存，传输与后续 chunk 的计算重叠。可选的 prefill_complete 策略把预留推迟到 prefill 完成之后，减少 Decode 槽位的占用，代价是分块 prefill 与传输不再重叠。
  • LMCache PD：chunk 先拷入连续缓冲区。 每个 chunk 的 KV 先拷到 Prefill 侧一块连续的 GPU 缓冲区，整块传到 Decode 侧缓冲区，再拆回 Decode 的分页显存。技术报告指出，vLLM 原生 PD 按页地址直接拷贝，分页 KV 分散在显存中时逐页传输，带宽利用不足；在 8K 输入、200 输出、P/D 经 NVLink 相连的设置下，LMCache 的平均 TTFT 降低 1.53–1.84×。
  • NVIDIA Dynamo：编排层。 PrefillRouter 按缓存重叠度和负载选择 Prefill worker；Prefill 返回传输元数据后，请求被路由到 Decode worker，后者与 Prefill worker 协调，经 NIXL 直接完成显存到显存的非阻塞传输，传输期间 GPU 继续为其他请求做前向。传输元数据随后端而异：vLLM 为块 ID，SGLang 为 bootstrap 连接，TensorRT-LLM 为 opaque state。

5.3 多级缓存与逐层载入

图 6：(a) SGLang HiCache 的三级缓存与工作流程；(b) LMCache 的逐层流水；(c) vLLM KV Connector 在 worker 侧的逐层钩子。

  • SGLang HiCache 把 GPU 显存、主机内存和存储后端组织成 L1 / L2 / L3。L1、L2 是实例私有的，跨实例复用只能经过 L3（mooncake、hf3fs、nixl、aibrix 等后端）。请求到达时先在 HiRadixTree 上匹配 L1、L2，未命中部分在 L3 命中超过 256 token（默认）才预取到 L2；prefill 时一边计算第 N 层，一边载入第 N+1 层的 KV。GPU 按层组织数据（layer_first），主机内存可以按 page 组织（page_first、page_first_direct），便于零拷贝交给 L3。
  • LMCache 为计算和数据搬运分配独立的 CUDA 流：先把第 1 层 KV 取进 GPU 缓冲区并拆成分页格式，计算第 1 层时异步取第 2 层。第 2 层要等第 1 层放进分页显存后才开始取，因此只需要一层 KV 大小的固定缓冲区。存取以 256 token 的 chunk 为单位（vLLM 的一页只有 16 token、单层），避免大量小 I/O。
  • vLLM KV Connector 把逐层载入和保存做成了引擎接口：worker 侧有 start_load_kv、wait_for_layer_load、save_kv_layer、wait_for_save 四个钩子，调度器侧有 get_num_new_matched_tokens 和 request_finished。NixlConnector、MooncakeConnector、LMCacheConnectorV1、OffloadingConnector 等都建立在这一接口之上。

6. 对比

方案 传输粒度 发起方 与本请求计算重叠 数据通路 主要代价
共置执行 — — — 本卡 HBM prefill 与 decode 相互干扰
DistServe 请求 Decode 拉取 否 Prefill HBM → Decode HBM（优先 NVLink） 传输暴露在首个 decode 步之前

7. 总结与思考

1. 粒度越细，越依赖提前知道目的地。 逐层或分块传输要在计算过程中就把数据发出去，前提是目的地已经确定：Splitwise 在调度时同时选定两台机器，Mooncake 的 Conductor 同时选出 P/D 对，SGLang 默认让 Decode 先预留槽位。vLLM NixlConnector 选择由 Decode 事后拉取，Prefill 不必等待 Decode 分配显存，代价是传输无法与本请求的 prefill 重叠。SGLang 的 prefill_complete 策略把这个取舍摆得很清楚：推迟预留，就失去重叠。

2. 瓶颈从“传出去”转向“读进来”。 第 1、2 代优化的是 Prefill → Decode 的新 KV；前缀命中率升高后，要搬的主要是历史 KV。Mooncake 的 prefill 时间约为 max（载入，计算），命中率越高越偏向载入。开源实现的优化也集中在“读进来”这一侧：HiCache 用 best_effort、wait_complete、timeout 三种预取策略在命中率和延迟之间取舍，GPU 辅助 I/O kernel 比 cudaMemcpyAsync 最高快 3×；LMCache 报告从 CPU 内存载入 KV 可达 400 Gbps，vLLM 原生 CPU offloading 为 88 Gbps。vLLM 的双向模式则让 Prefill 直接从 Decode 拉取上一轮的 KV，少读一次存储。

3. 数据布局是计算与 I/O 之间的翻译层。 计算天然按层进行，存储和网络则偏好大块连续的数据。Mooncake 的 block 大小（16–512 token）按模型规模和最优网络传输大小选取；HiCache 的 page_first_direct 把一个 page 内同一层的 token 放在一起；LMCache 用 256 token 的 chunk 和单层缓冲区。它们解决的是同一个问题：既能逐层供给计算，又不让传输退化成大量小 I/O。

4. KV 是网络里的大流，拓扑和路径都要管。 DistServe 用放置约束把 KV 限制在 NVLink 上；Mooncake 的 Transfer Engine 按拓扑矩阵优先选本 NUMA、本 PCIe switch 的网卡，避开 UPI 和 PCIe switch 的带宽瓶颈，调度器还靠增加热点块的副本缓解拥塞。跨节点时，PD 间的 KV 传输是持续数百毫秒到数秒的大象流，本站的 ARK 笔记讨论的就是这类流在 ECMP 下的哈希冲突。

5. 工程栈在收敛，但取舍还没有统一。 引擎提供逐层钩子（vLLM KV Connector），传输交给 NIXL 或 Mooncake Transfer Engine，缓存交给 HiCache、LMCache 或 Mooncake Store，分层已经比较清楚。但拉取还是推送、按请求、按 chunk 还是按层传，不同系统仍有不同选择，背后是显存占用、重叠程度和实现复杂度之间的权衡。
