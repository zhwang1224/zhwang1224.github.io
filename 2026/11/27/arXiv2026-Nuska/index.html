Nuska：按松弛度调度分离式 LLM 推理的多阶段通信

发表于 2026-11-27 分类于 人工智能系统 阅读时长 ≈ 17 分钟
arXiv 2026 论文 Nuska 阅读笔记。PD 分离推理的 Prefill 阶段同时存在 KV-Cache 复用拉取、EP/SP 集合通信和 P2D 传输三类流，它们在共享链路上相互争抢，而 SJF、EDF 等阶段无关的调度恰好把带宽让给了最能等的流。Nuska 观察到请求的 TTFT deadline 会随 Prefill 推进逐步落实到每条流上，用反向多级队列实现“延后—提升”，在不知道精确松弛度的情况下近似最小松弛度优先（LLF）。测试床上平均 TTFT 降低 20.7%–32.3%，仿真中 TTFT SLO 达标率提升 1.2×–2.4×。

Nuska（arXiv 2026，香港科技大学 iSING Lab、上海交通大学、中国科学技术大学）研究 PD 分离推理中 Prefill 阶段的网络争抢。生成首个 token 要经过三类通信：从远端 Prefill 单元拉取可复用的 KV-Cache、EP/SP 的集合通信、把 KV-Cache 交给 Decode 的 P2D 传输。三者在同一批链路上相互重叠：在 16 GPU 的测试床上，争抢让 TTFT 拉长近 50%，All-to-All 的完成时间变为原来的 1.8×。SJF、EDF 这类按单条流优化的调度，并不知道哪条流挡在计算的关键路径上。

Nuska 的出发点是：请求的 TTFT deadline 会随 Prefill 逐层推进，逐步落实到每条流上。P2D 流的 deadline 明确，可以延后到“刚好赶上”；集合通信直接阻塞下一层计算，必须优先；KV 复用流介于两者之间。Nuska 用 反向多级队列（RMLQ） 实现“延后—提升”（Defer-and-Promote）：流从低优先级起步，随松弛度减小逐级提升，从而在不知道精确松弛度的情况下近似 最小松弛度优先（LLF）。测试床上平均 TTFT 降低 20.7%–32.3%，大规模仿真中 TTFT SLO 达标率提升 1.2×–2.4×。

Nuska：按松弛度调度分离式 LLM 推理的多阶段通信

项目 内容
标题 Nuska: Stage-Aware Communication Scheduling for Disaggregated LLM Serving
作者 Yijun Sun、Xudong Liao、Songrun Xie、Hao Chen、Han Tian、Wenxue Li、Yiming Zhang、Kai Chen
机构 香港科技大学 iSING Lab、上海交通大学、中国科学技术大学
会议 arXiv 预印本（v2，2026 年 9 月）
原文 arXiv:2603.17456

术语：松弛度（laxity）指流或请求在违约前还剩的余量；CCT 为集合通信完成时间；earliness（提前量）为请求完成时刻距 deadline 的余量，正值表示提前完成，负值表示违约；P2D 为 Prefill 到 Decode 的 KV-Cache 传输。

1. 背景：Prefill 中的三阶段通信

TTFT 是交互应用和 Agent 流水线最看重的 SLO：首 token 迟到会触发重试或切换服务商，论文引用的微软生产事故研究中，首 token 延迟约占服务故障的 40%。现代推理系统把 PD 分离、KV-Cache 复用和多种并行（TP、EP、SP 等）组合在一起，Prefill 的每一层都会产生通信。Nuska 把单个 Prefill 请求每一层的通信抽象为一个 多阶段流（MsFlow）：

阶段 内容 与计算的关系 deadline
Stage 1 初始化 从远端 Prefill 单元拉取可复用的 KV 块 可与前一层计算重叠 隐式，取决于何时被用到
Stage 2 执行 EP 的 All-to-All、SP 的集合通信 严格阻塞下一层计算 隐式，越早越好
Stage 3 完成 P2D 传输 不阻塞 Prefill 计算 明确，即请求的 TTFT deadline

Stage 3 的 deadline 之所以明确，是因为 Dynamo、SGLang、vLLM 等主流框架把 P2D 时延计入 TTFT。同一请求的所有 MsFlow 共享一个 TTFT deadline，并受层间依赖约束：第 l 层的 Stage 2 完成后，才能开始计算第 l+1 层。

图 4：左为请求内争抢，同一请求不同层的 KV 复用、EP 与 P2D 流在时间上重叠；右为请求间争抢，同一实例的请求 R1、R2 与另一实例的请求 R3 争抢同一条链路。

请求间争抢还有一种来自 KV 块热度倾斜的情形：多个 Prefill 单元同时向同一个“victim”单元拉取热点 KV 块，victim 单元的本地集合通信与远端的 KV 拉取在它的网卡上相互争抢。

2. 动机

争抢真实存在。 论文在 16 GPU 的 Prefill 集群上测量（每 GPU 50 Gbps，两个服务实例，TP=1、EP=8），负载为 QwenB-agent（平均 1k token，65% 提示词复用，每 GPU 1 req/s）。

图 5：有无争抢时 (a) 归一化 TTFT 的分布与 (b) All-to-All 完成时间的 CDF。

争抢让整体 TTFT 拉长近 50%，主要原因是关键路径上 All-to-All 的 CCT 接近翻倍（1.8×）。

阶段无关的调度会误判紧迫度。 公平共享、SJF、EDF 以及 coflow 调度优化的是单条流或单个 coflow 的指标，而 TTFT 由多个相互依赖阶段的流共同决定。SJF 偏向流更小的 KV 复用流；EDF 只看得到 P2D 的明确 deadline，会过早服务它，对隐式 deadline 的流则退化为公平共享。两者都可能把带宽交给不在关键路径上的流。只优化单一阶段的工作（集合通信算法合成、KV 预取、块合并等）大多靠提高通信并发来隐藏时延，各自之间没有协调，叠加起来反而放大争抢。

关键观察：deadline 随 Prefill 推进逐步落实到流上。 早期阶段（Stage 1、2）的流级 deadline 是隐式的，由 TTFT 和下游计算时长共同决定；到了 Stage 3，TTFT 直接成为流的上界。不同阶段的松弛度不同，于是可以把松弛度确定且较大的 Stage 3 往后放，把带宽让给更急的早期阶段流。

表 1、表 2：三条流争抢一条瓶颈链路，Remain time 为流传完后请求还需的后续时间（图中灰色条），红色竖线为各请求的 deadline；(a)–(d) 依次为公平共享、SJF、EDF 和 Defer-and-Promote。

按“松弛度 = deadline − 后续时间 − 流大小”计算（单位带宽），A、B、C 的松弛度分别为 7、2、4。公平共享让请求 2、3、4 都违约，SJF 和 EDF 让请求 2、3 违约。Defer-and-Promote 先传 B，把 C 延后到时刻 7 刚好完成，最后传 A，三组请求全部达标，次序 B → C → A 正是按松弛度从小到大。请求内争抢的例子（论文图 6、图 7）也一样：入口方向延后 KV 复用、出口方向延后 P2D，先保集合通信，第 2 层的开始时刻从 T=3 提前到 T=2（−33%），完成时刻从 T=4 提前到 T=3（−25%）。

问题在于 LLF 需要知道每条流的精确松弛度，而早期阶段流的松弛度取决于后续计算和调度，事先无法得知；交换机也只有少量优先级队列。

3. 设计

3.1 反向多级队列

图 8：通信库发出的流分为隐式 deadline（Stage 1、2）与显式 deadline（Stage 3）两类，在主机侧进入不同优先级的软件队列，报文按优先级打标后进入交换机端口对应的硬件队列。

RMLQ 把经典 MLFQ 反过来：MLFQ 让流随发送量增加而降级，RMLQ 让流从低优先级起步，随松弛度减小而提升。它要解决两个问题：

  • C-1：明确 deadline 的流何时从延后切换为提升。太早浪费瓶颈带宽，太晚错过 deadline。
  • C-2：隐式 deadline 的流松弛度不准。低估会错误延后 Stage 2，GPU 立刻空转；高估则造成优先级反转，饿死真正紧迫的请求。

仲裁规则：最高优先级留给最紧迫的 Stage 3 流；其余档位中，早期阶段流优先于 Stage 3 流；RLI 相同的早期阶段流，按请求间排序裁决。

3.2 明确 deadline：MLU 与几何阈值

Stage 3 流用 最小链路利用率（MLU） 衡量紧迫度：

其中 S(t) 为剩余数据量，T(t) 为距 deadline 的剩余时间，B(1−ρ) 为计入负载 ρ 后的有效带宽。MLU 即满足 deadline 至少需要的剩余链路份额：大于 1 表示已不可行，接近 1 表示需要独占链路，越小越可以延后。

  • 阈值：把连续的 MLU 映射到 K 个队列时，为使最坏情况下的相对量化误差最小，阈值应成几何级数。实际取第 i 级阈值为 （），默认 E=4、U=0.5。
  • 提升方式：只在层边界提升，保证同一消息的报文落在同一队列，避免乱序；只升不降，防止优先级振荡。模型层数远多于队列数（如 L=64、K=8/16），按层提升的粒度足够。请求计算结束后，改为按固定间隔更新。

3.3 隐式 deadline：RLI 与稳健的请求间排序

请求内：相对层下标（RLI）。 精确松弛度拿不到，但同一请求内的相对次序是确定的：阻塞当前计算的流，比为后续层预取的流更急。Nuska 定义 RLI = L_target − L_curr（数据被消费的层减去当前执行的层），严格优先 RLI 最小的流。集合通信服务当前层，RLI 为 0，直接进入高优先级；KV 复用流按 RLI 初始化，随计算推进逐层提升，近的层先于远的层。论文用交换论证证明，在理想计算模型（无抢占开销）下，这一规则使 Prefill 完工时间最短：在计算停顿期间传 RLI 大于 0 的流，等于浪费了它与后续计算重叠的机会。

请求间：RED 与过载剪除。 RLI 相近、又同时威胁执行的跨请求流需要裁决。批处理会把一次误判扩散到同批的所有请求，论文给出两种陷阱及对策：

  • 搭便车效应：批次中少数极紧的请求抬高整批的优先级，同批的宽松请求跟着抢占其他更急的批次。Nuska 在 deadline 间隔最大处把批次切成紧、松两个子批，定义 稳健有效 deadline ，其中 、 为两个子批各自的最小 deadline，f 为紧请求的占比。紧请求很少时，RED 偏向宽松子批的 deadline。
  • 黑洞效应：临近 deadline 不等于还来得及。过载时优先一个注定失败的批次，只会拖垮其他可行的批次。Nuska 按最坏情况（批次间无重叠）累加估计的计算与通信时延做可行性检查，迭代剪除对瓶颈端口负载贡献最大的请求。被剪除的请求降入 Scavenger 队列，只在网络空闲或实际时延低于估计时传输，并不直接丢弃。

请求间排序只在批次到达和离开时重新计算，不逐层更新，以免对负载估计的瞬时抖动过度反应。

3.4 实现

Nuska 约 10,000 行代码，作为可插拔模块接入 NCCL 和 Mooncake，并集成进 vLLM。每个节点运行一个本地守护进程，经共享内存上的无锁 MPSC 队列与运行时通信；Nuska 拦截 RDMA Verbs 等底层原语，把通信库代理线程的工作请求转交守护进程，通过 submit（带元数据注册任务）、permit（授予优先级并放行发送）、completion（收到硬件完成信号后更新状态）三个原语控制发送。集中式协调器按请求粒度汇总各节点的统计，做跨节点裁决。

商用交换机的优先级队列有限（K ≪ L）。集合通信通常留在一个服务单元内，KV-Cache 流量则跨机架，因此 Nuska 在主机侧用软件队列执行上述严格优先级，在网络中用 DSCP 硬件优先级隔离 KV-Cache 流量：Stage 3 按 MLU 阈值打 DSCP 标记，早期阶段流把 RLI 截断到 K−1 后映射到 [0, K−1] 号队列。

4. 实验结果

设置。

  • 测试床：8 台服务器，每台 4 张 RTX 3090（PCIe Gen 3.0）、2 块 ConnectX-5 100 Gbps 网卡，经 NVIDIA SN2700 以太网交换机互连；16 张 GPU 组成 Prefill 集群，Decode 单独部署，输出长度限为 1 个 token。模型为 Mixtral 8x7B（FP16，top-2，TP=1、EP=8）。负载来自 Qwen 生产 trace：QwenA-Conv（对话，平均 2k token，50% 复用）与 QwenB-agent（Agent，平均 1k token，65% 复用）。
  • 仿真：基于 Vidur 与流级仿真器 flowsim，默认 256 台服务器，P:D = 1:1，由类似 Dynamo 的 KV-Cache 感知调度器分配请求；每台 8 张 GPU（NVSwitch 900 GB/s）、8 块网卡，1:1 fat-tree，链路 200 Gbps，时延按 A100 校准。MoE 模型部署在 32 GPU 实例上：Mixtral 8x22B、Grok-2（TP=4、EP=8），DBRX（TP=2、EP=16），Qwen3-Coder（TP=1、EP=32）。稠密模型为 Llama3-8B（1M 上下文，16 GPU，TP=4、SP=4），使用 Mooncake trace（对话、Agent 的复用率约 40%、65%，上下文约 15k、9k token）。
  • 指标与基线：SLO 阈值为低负载下 TTFT 的 3 倍。基线为公平共享（FS）、SJF、EDF 和 Karuna（为有 deadline 的流分配按时完成所需的最小带宽，其余流按 SJF 调度）。

4.1 测试床

图 9：(a) 归一化平均 TTFT 与 (b) 归一化 All-to-All CCT，均以 QwenA-Conv 的 Baseline 为 1。

vLLM 配置 8192 个 batched token，每 GPU 1 req/s。平均 TTFT 在 QwenA-Conv 上降低 20.7%（1.26×），在 QwenB-agent 上降低 32.3%（1.48×）；Stage 2 的 CCT 分别缩短 31.9%（1.47×）和 43.1%（1.76×）。TTFT 的改善主要来自阻塞计算的集合通信更快完成。论文没有说明图中 Baseline 具体采用哪种策略。

Karuna 是最强的基线。对话负载中少量尾部请求需要搬运大量 KV-Cache，高负载下三个阶段都会争抢，Karuna 恰好延后了不急的 Stage 3 流量，缓解了一部分。Agent 负载的提示词更短、复用率更高，多个并发请求共享相同前缀，多个 worker 同时拉取同一份缓存，形成发送端的一对多争抢，集中在 Stage 1、2。此时 Stage 3 不再主导争抢，Karuna 对早期阶段流退化为 SJF，与其他基线的差距随之缩小。

4.3 收益来源

图 13：DBRX（QwenA，每 GPU 0.7 req/s）上 (a) 专家并行归一化 CCT 与 (b) 请求归一化 earliness 的 CDF。

该配置下 Nuska 的 SLO 达标率提升 2.2×，收益有两个来源：

  • 缩短不可重叠的通信：专家并行的平均 CCT 降低 52%，Prefill 完工时间随之缩短。
  • 调节提前量：与 FS、SJF、EDF 相比，非负 earliness 部分降低 42%，不必要的提前完成少了，省下的带宽留给真正紧迫的请求。Karuna 的非负 earliness 最小，但它按接近最低的速率分配带宽，没有用上空闲带宽，违约比例高。

Llama3-8B（SP）上的拆解（论文图 14）呈现同样的趋势。

5. 总结与思考

1. 紧迫度由流在计算图中的位置决定。 三类流里只有 Stage 2 在关键路径上，Stage 1 有一层计算可以重叠，Stage 3 只受 TTFT 约束。SJF 看流大小，偏向较小的 KV 复用流；EDF 看明确的 deadline，偏向 P2D；两者恰好都把带宽交给了最能等的流。图 13 中 CCT 降低 52% 是最主要的收益，说明很大一部分 SLO 违约来自集合通信被 KV 流量拖慢，而这一点单看任何一条流的指标都看不出来。

2. 拿不到精确松弛度时，把能算准的和算不准的分开处理。 表 1 的例子里按松弛度排序就是最优解，难点在于早期阶段的松弛度事先无法得知。Nuska 分三层处理：P2D 的 deadline 明确，用 MLU 精确刻画；早期阶段放弃绝对值，只用结构上确定的相对次序 RLI；跨请求的估计误差无法消除，就用 RED 和可行性剪除让决策对误差不敏感。这与 PIAS 在不知道流大小时用 MLFQ 近似 SJF 是同一思路，RMLQ 相当于 MLFQ 的镜像。PIAS、Karuna 和 Nuska 都出自港科大 Kai Chen 团队，Karuna 为 deadline 流分配最小带宽，正是 Nuska 对 Stage 3 的处理方式，所以它是最强基线并不意外；Nuska 新增的是借 LLM 的层结构为没有 deadline 的流排出次序。Agent 负载下 Stage 3 不再主导争抢，Karuna 就与其他基线拉不开差距。

3. 与 DualPath 对照。 DualPath 把 KV-Cache 流量引入计算网络后，用 InfiniBand VL 把推理集合通信放在高优先级、KV-Cache 放在低优先级，否则 DeepEP dispatch 时延会变为原来的 6.7 倍。这相当于 Nuska“集合通信优先”的静态版本。两篇论文都说明，KV-Cache 流量与集合通信共用同一张网络已是常态，优先级隔离是第一步；Nuska 更进一步，在 KV 流量内部按松弛度区分，并让 P2D 在快要赶不上时抢到最高优先级。

4. 评估还缺几块。

  • 基线都是阶段无关的策略，没有“集合通信 > KV 复用 > P2D”这类静态阶段优先级的基线（DualPath 的做法即属此类），看不出 MLU、RLI、RED 这套机制在静态隔离之外还贡献多少；也没有各组件的消融，以及协调器决策和拦截 Verbs 的开销数据。
  • 测试床是 RTX 3090、PCIe Gen 3.0、100 Gbps 网卡和单台交换机，只测了 Mixtral 8x7B，图 9 的 Baseline 未注明具体策略；大规模结论全部来自按 A100 校准的仿真。
  • 争抢的前提是 EP/SP 集合通信跨节点，与 KV 流量共用 scale-out 网络。在 NVL72 这类大 scale-up 域内，EP 通信留在 NVLink 上，scale-out 网络上主要剩下 KV 流量（Stage 1、3）之间的争抢，论文在讨论多模型混部时也提到了这一点。论文认为思路可以借助虚拟通道或流量类别推广到 scale-up 网络，但没有验证。
