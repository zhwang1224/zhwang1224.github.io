Mooncake：以 KVCache 为中心的分离式推理架构

发表于 2026-11-24 分类于 人工智能系统 阅读时长 ≈ 15 分钟
FAST 2025 论文 Mooncake 阅读笔记。Mooncake 是 Kimi 的推理服务平台，在 Prefill/Decode 分离的基础上，把 GPU 集群中闲置的 CPU、DRAM、SSD 和 RDMA 网卡组织成分布式 KVCache 池，并围绕 KVCache 的分布做全局调度，以更多的存储换取更少的 Prefill 计算。

Mooncake（FAST 2025，月之暗面与清华大学）是 Kimi 的线上推理服务平台。DistServe 和 Splitwise 论证了 Prefill 与 Decode 应当分离；Mooncake 在此基础上再向前一步，把 KVCache 本身也从 GPU 节点中分离出来，组织成一个跨节点共享的缓存池。

论文的出发点是：用更多的存储换更少的计算。长上下文、多轮对话的负载中有大量可复用的前缀，复用 KVCache 可以直接省去对应的 Prefill 计算。但单节点的缓存容量只能达到理论命中率的一半左右，所以缓存必须是全局的，调度也必须感知缓存的分布。在真实 trace 上，Mooncake 相对基线把满足 SLO 的有效请求容量提高了 59%–498%。

Mooncake：以 KVCache 为中心的分离式推理架构

项目 内容
标题 Mooncake: Trading More Storage for Less Computation — A KVCache-centric Architecture for Serving LLM Chatbot
作者 Ruoyu Qin、Zheming Li、Weiran He、Jialei Cui、Feng Ren、Mingxing Zhang、Yongwei Wu、Weimin Zheng、Xinran Xu
机构 Moonshot AI、清华大学
会议 FAST 2025
原文 USENIX FAST '25

1. 背景：GPU 节点上闲置的资源

作为 MaaS 提供方，Kimi 的优化目标是在满足 TTFT 和 TBT 两类 SLO 的前提下最大化有效吞吐。文章背景 GPU 供给紧张，集群无法弹性扩容，所以系统会主动拒绝预计无法满足 SLO 的请求。

GPU 服务器以高度集成的整机形式交付（DGX/HGX），除了 GPU 之外，每个节点还带有 CPU、大容量 DRAM、SSD 和多块 RDMA 网卡。在推理服务中这些资源大部分时间是闲置的。Mooncake 的思路是把它们重新组织成几个分离的资源池：Prefill 池、Decode 池，以及由 CPU、DRAM、SSD、RDMA 构成的 KVCache 池。

2.2 本地缓存容量不足

现有的前缀缓存方案把缓存限制在本地的 HBM 和 DRAM 中。LLaMA3-70B 每个 token 的 KVCache 为 320 KB，即使为缓存预留约 1 TB 的 DRAM，也只能存放约 300 万个 token。

图 9：虚线为 3M token 的本地缓存容量，标注为该容量下的命中率占理论最大命中率的比例。

本地缓存在多数场景下达不到理论最大命中率的 50%。要接近理论最大值需要约 5000 万 token 的容量，相当于至少 20 个节点的 DRAM。因此缓存必须跨节点共享。

3. 设计

3.1 总体架构

图 2：左侧为全局调度器 Conductor，右侧为 Prefill 池、Mooncake Store 和 Decode 池，以及两个阶段各自的优化目标和约束。

各部分的职责：

  • Prefill 池：目标是尽可能复用缓存，约束为 TTFT SLO、MFU（Model FLOPs Utilization）下限和 DRAM 容量。
  • Decode 池：目标是最大化吞吐，约束为 TBT SLO 和显存容量。
  • Mooncake Store：部署在每个节点上，负责 KVCache 的存储和传输。
  • Conductor：全局调度器，根据 KVCache 的分布和负载为每个请求选择一对 Prefill 实例和 Decode 实例。

图 3：一个请求经过的四个步骤。

  1. KVCache 复用：Prefill 节点把可复用的前缀缓存从（可能是远端的）CPU 内存加载到 GPU。
  2. 增量 Prefill：只计算未命中的部分，新生成的 KVCache 写回 CPU 内存。未缓存的 token 超过阈值（通常大于 1000）时分成多个 chunk 执行。
  3. KVCache 传输：与增量 Prefill 重叠进行，逐层把 KVCache 流式传输到 Decode 节点的 CPU 内存。
  4. Decode：KVCache 全部到达后，请求加入 Decode 节点的 continuous batching。

3.2 Mooncake Store

缓存管理。KVCache 以分页的 block 存储，每个 block 包含 16–512 个 token。block 的哈希键由自身内容和前缀共同决定，用于去重。同一个键可以在多个节点上有副本，以分散热点缓存的访问。缓存池写满后按 LRU 淘汰。

传输引擎。每个节点有多块 RDMA 网卡，聚合带宽最高可达 8 × 400 Gbps，与内存带宽相当，现有库难以充分利用。NCCL 无法处理节点或网卡增减带来的拓扑变化，也不支持 DRAM 到 DRAM 的路径。Mooncake 的传输引擎为此做了三件事：

  • 拓扑感知的路径选择：每台服务器生成拓扑矩阵并广播到集群，把网卡按内存类型（各 CPU socket 的 DRAM、各 GPU 的显存）划分为首选和次选。正常情况下只使用首选网卡，使传输限制在本地 NUMA 或本地 PCIe switch 内，避免受 UPI 或 PCIe switch 带宽限制。一次传输被切成 16 KB 的分片，不同分片可以经过不同路径。
  • 端点池化：连接按需建立，用 SIEVE 算法淘汰端点，限制活跃连接数。
  • 故障处理：某块网卡暂时不可用时，自动选择其他可达路径重新提交。

3.3 Prefill 池与分块流水线并行

有了 chunked prefill 之后是否还需要单独的 Prefill 池，论文给出两个理由：

  • 在线服务的 SLO 更严格，chunked prefill 很难同时做到 Prefill 阶段的高 MFU 和 Decode 阶段的 TBT 达标。
  • 长上下文（128k 甚至 100 万 token）请求的输入是输出的 10–100 倍，需要跨节点并行来降低 TTFT，而 Prefill 节点需要与 Decode 节点不同的并行配置。

跨节点并行的已有方案各有问题：张量并行（TP）跨节点时每层需要两次基于 RDMA 的 all-reduce，MFU 明显下降；序列并行（SP）对短请求的 MFU 低于单节点 TP，并且频繁的跨节点通信会与 KVCache 传输竞争网络。

Mooncake 采用 分块流水线并行（CPP）：把每 X 个 Prefill 节点组成一个流水线组，请求的输入切成若干 chunk，不同 chunk 由不同节点同时处理。只在流水线各阶段的边界处有跨节点通信，可以与计算重叠；它对长短请求都适用，不需要频繁调整节点分组。

缓存负载均衡。缓存的访问频率差别很大：系统提示词几乎被所有请求访问，某个用户上传的长文档可能只被一个用户使用。由于负载变化快，论文认为无法准确预测缓存的未来使用情况，因此采用启发式的 热点自动迁移：

  • 命中前缀最长的实例负载过高时，Conductor 把请求转给其他实例；如果传输缓存比重新计算更快，该实例主动从持有者拉取 KVCache 并保存在本地。
  • 如果远端的最佳前缀命中长度不超过本地命中长度乘以一个阈值，则直接本地计算。

这两条规则在缩短 Prefill 时间的同时，使热点缓存自然地在多个实例上形成副本。

4. 实验结果

设置。为保护商业信息，可复现的实验使用与 LLaMA3-70B 结构相同的 dummy 模型。每个节点 8 张 A800-80GB、4 块 200 Gbps RDMA 网卡，KVCache block 大小为 256 token。TTFT 阈值 30 s，TBT 阈值分别取 100 ms、200 ms、300 ms，TBT 取每个请求最长的 10% token 间隔的平均值。TTFT 和 TBT 都达标的请求称为有效请求。基线为 vLLM（v0.5.1）及其前缀缓存、chunked prefill 两个特性，后两者分别测试。

4.1 有效请求容量

图 1：16 个 8×A800 节点，横轴为 TBT，纵轴为 TBT 不超过该值的请求比例。三条竖线对应 100 ms、200 ms、300 ms 三个阈值。

负载 100 ms 200 ms 300 ms
Conversation +498% +157% +59%
Tool&Agent +64% +42% +22%
Synthetic +62% +40% +28%
  • Conversation：输入长度变化大、输出较长，vLLM 的 TBT 因长上下文 Prefill 而大幅波动。chunked prefill 能减少对 Decode 的干扰，但仍难以兼顾 Prefill 的 MFU 和 TBT 约束。SLO 越严格，分离的优势越大。
  • Tool&Agent：前缀缓存比例高、输出短，vLLM 的前缀缓存版本是最强的基线。Mooncake 在 200 ms 阈值下比它高 42%。
  • Synthetic：输入最长、缓存热点分散。Mooncake 大部分请求的 TBT 在 100 ms 以内，vLLM 约 20% 的请求超过 300 ms；200 ms 阈值下 Mooncake 比 vLLM 高 40%。

线上部署的历史统计显示，相对之前基于 vLLM 的系统，Mooncake 使 Kimi 在 A800 和 H800 集群上分别多处理 115% 和 107% 的请求。平台目前运行在数千个节点上，每天处理超过 1000 亿 token。

4.2 Prefill GPU 时间

图 8：柱上的倍数为各基线相对 Mooncake 的比值。

相对 vLLM，Mooncake 在三种负载下把 Prefill GPU 时间分别减少 36%、53%、64%。vLLM 的前缀缓存只使用 HBM 上的本地缓存，在 conversation 和 tool&agent 负载下是 Mooncake 的 1.43× 和 1.40×；在热点分散的 synthetic 负载下几乎没有效果，为 Mooncake 的 2.59×。chunked prefill 为了保证 TBT 牺牲了 Prefill 效率，GPU 时间最长，分别为 1.90×、2.68×、3.33×。

4.3 全局缓存与本地缓存

图 10：10 个 Prefill 节点，每个节点 3M token 的缓存容量。本地缓存设置下节点只能访问自己的缓存；全局缓存设置下节点之间可以共享并主动迁移缓存。

全局缓存的命中率是本地缓存的 2.22×、1.38×、2.36×，Prefill GPU 时间为本地缓存的 0.76×、0.74×、0.52×，即命中率最高提升 136%，计算时间最多减少 48%。副本统计显示，conversation 和 tool&agent 负载中访问量最高的约 100 个缓存键在系统稳定后几乎在每个 Prefill 实例上都有副本。

4.4 传输性能与带宽需求

传输引擎：传输 40 GB 数据（LLaMA3-70B 上 128k token 的 KVCache）时，在 4 × 200 Gbps 和 8 × 400 Gbps 配置下带宽分别达到 87 GB/s 和 190 GB/s，约为 TCP 的 2.4× 和 4.6×。
带宽需求：

图 13：左为平均 TTFT，红色虚线为重新计算的 TTFT；右为理论与实际的传输时间。

总带宽超过 100 Gbps 时，平均 TTFT 保持在 2 s 以下，明显低于重新计算。低于 100 Gbps 时出现网络拥塞，实际传输时间远高于理论值，TTFT 急剧上升。论文建议网络带宽不低于 100 Gbps。

延迟分解：输入长度为 128k token、前缀缓存比例为 95% 时，Prefill 时间减少 92%；计入调度、传输、加载缓存的开销后，TTFT 仍减少 86%。这些开销可以与模型推理异步进行，不影响吞吐。

4.5 P/D 配比

图 15：16 个节点，synthetic 负载，TTFT 阈值 10 s、TBT 阈值 100 ms。左为有效请求比例，右为平均 TTFT 和 TBT。

增加 Prefill 节点降低 TTFT、提高 TBT，反之亦然。P/D 比例约为 1:1 时有效请求容量最高。论文指出线上流量的统计特征总体稳定，因此实际部署中固定 P/D 比例，只在负载明显波动时切换节点角色。

5. 总结与思考

1. 分离之后，KVCache 成为调度的中心对象。 DistServe 和 Splitwise 把 KVCache 当作分离带来的传输开销，目标是把它隐藏掉。Mooncake 把 KVCache 当作可以跨请求复用的资产：请求调度到哪个节点，取决于缓存在哪里、搬运缓存和重新计算哪个更快。调度问题从“负载均衡”变成了“缓存位置与负载的联合优化”。

2. 存储换计算成立的前提是带宽。 2.1 节的不等式说明，复用缓存是否划算取决于加载带宽与 GPU 算力之比。GPU 越快，对带宽的要求越高（A800 需要 6 GB/s，H800 需要 19 GB/s）。这也解释了为什么论文花大量篇幅在传输引擎上：缓存池的容量来自多节点的 DRAM，而它的可用性来自 RDMA 网卡的聚合带宽。

3. 全局缓存的价值来自容量，而不只是共享。 图 9 表明命中率随容量增长有明显的拐点，单节点 3M token 的容量处在拐点之前。全局池把容量提高一个数量级后，命中率才接近理论上限。热点分散的负载（synthetic）从全局缓存中获益最大，而本地前缀缓存在这种负载下几乎无效。

4. 用简单的启发式应对不可预测的负载。 Prefill 时间可以准确预测，缓存的未来访问则不能。Mooncake 没有尝试预测热点，而是让调度决策的副作用（负载过高时转移请求并拉取缓存）自然形成热点副本。这种做法实现简单，并且随负载变化自动调整。

5. 三篇论文对分离的论证逐步推进。 DistServe 说明分离消除了干扰、解耦了并行策略；Splitwise 说明两个阶段可以使用不同的硬件；Mooncake 说明分离后的 Prefill 池可以独立地为长上下文做跨节点并行，并且节点上闲置的 CPU、内存和网卡可以再组成一个缓存池。这也是一篇存储会议的论文：它处理的核心问题是一个 PB 级分布式缓存的容量、副本、淘汰和传输。
