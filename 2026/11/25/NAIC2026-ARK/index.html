ARK：在主机侧预留路径，避开 KV Cache 大流的 ECMP 冲突

发表于 2026-11-25 分类于 人工智能系统 阅读时长 ≈ 11 分钟
NAIC 2026（SIGCOMM 2026 Workshop）论文 ARK 阅读笔记。PD 分离推理中的 KV Cache 传输是持续数百毫秒到数秒的巨型大象流，ECMP 哈希冲突会让部分 spine 过载而其他 spine 空闲。ARK 利用“KV 流在准入时即已知、寿命足以摊销协调”这两点，让每台主机维护一份复制的 spine 预留表，通过选择源端口让 ECMP 把并发流哈希到不同 spine，不改交换机、不引入乱序。分组级仿真中平均 / P95 FCT 最多降低 27.3% / 34.0%，平均 TTFT 最多降低 12.9%。

ARK（NAIC 2026，即 SIGCOMM 2026 的 Networks for AI Computing Workshop，佐治亚理工学院）研究 PD 分离推理中 KV Cache 传输的 网内选路 问题。Prefill 节点生成的 KV Cache 要经数据中心网络送到 Decode 节点，单个请求就是几百 MB 到几 GB 的流，持续数百毫秒到数秒。ECMP 按五元组哈希选路、不看流的大小，两条这样的流一旦哈希到同一个 spine，就会在整个传输期间平分带宽，旁边的 spine 却可能空着。

ARK 的出发点是：KV 流的目的地、字节数和开始时刻在 Prefill 结束时就已确定，寿命也长到足以摊销一次协调。于是每台主机维护一份复制的 spine 预留表，新流到达时选一个未被占用的 spine，用预先算好的 源端口 让 ECMP 哈希恰好落在它上面，再把预留广播给其他主机。交换机不用改，每条流仍走单一路径，接收端无需重排序。在 16 GPU 的分组级仿真中，平均 / P95 FCT 最多降低 27.3% / 34.0%，平均 TTFT 最多降低 12.9%。

ARK：在主机侧预留路径，避开 KV Cache 大流的 ECMP 冲突

项目 内容
标题 ARK: Avoiding Routing Collisions for KV Cache Transfer in Disaggregated LLM Inference
作者 Hung-Chun Lin、Ting-Wei Hsu、Chung-En Ho、Ahmed Saeed
机构 佐治亚理工学院（Georgia Tech）
会议 NAIC 2026（ACM SIGCOMM 2026 Workshop on Networks for AI Computing）
原文 DOI: 10.1145/3789240.3828750，arXiv:2610.41160

1. 背景

KV Cache 流是一种新的流量形态。 PD 分离（DistServe、Splitwise）把计算受限的 prefill 和访存受限的 decode 放到不同的 GPU 池，代价是每个请求的 KV Cache 都要经网络从 prefill GPU 搬到 decode GPU。vLLM、SGLang、Dynamo、llm-d 都已支持这一模式，Kimi（Mooncake）和 DeepSeek-V3 的 SGLang 参考部署也采用了它。论文给的对比是：传统数据中心“大象流”的峰值在几十 MB 量级，而 LLaMA-3.1-405B 一个 100K token 请求的 KV Cache 约 48 GB（每 token 504 KB），单条流就能让一条 400 Gbps 链路饱和 960 ms。这段传输位于请求的关键路径上，FCT 的增加会直接计入 TTFT。

AI 网络仍以 ECMP 为基线。 ECMP 对五元组（源 / 目的 IP、源 / 目的端口、协议）做哈希来选下一跳，同一条流固定走一条路径。Meta 的训练 RoCE 网络和阿里 HPN 都保留了商用 ECMP，只是分别用“丰富哈希输入 + 集中式流量工程”和“双平面、双 ToR”来规避它的弱点。哈希不感知流大小，两条 KV 大流哈希到同一 spine 就会在数秒内平分带宽；AI 集群的 leaf–spine 层通常还有超售，冲突造成的排队更快填满缓冲区。

2. 动机

现有的网内负载均衡方案都不划算或不适用：

方案 代价 / 问题
CONGA 需要在全网部署定制的拥塞感知 leaf ASIC
ConWeave 需要可编程 ToR 和逐流重排序缓冲
LetFlow 需要交换机级的 flowlet 检测
逐包喷洒 乱序到达，KV 巨流在接收端重组的 CPU 开销大
PLB（主机侧） 被动式：连续 M 个 ECN 标记的往返后才重选路，且只在连接空闲时进行；RDMA 按硬件节奏发送，KV 流生命周期内几乎没有空闲间隙

KV 流本身提供了协调的机会：

  • 寿命足以摊销协调。 平均 1.6 GB 的 KV 传输至少独占一条 100 Gbps spine 链路 128 ms，比 flowlet 方案针对的毫秒级流高三到四个数量级，毫秒级的准入协调只占流寿命的 1% 以下。
  • 流的身份在准入时已知。 Prefill 引擎生成 KV Cache 时，目的 GPU、字节数和开始时间都已确定，不需要像 Hedera 那样在运行时检测大象流；等价路径也能在主机端枚举。

因此可以在第一个字节发出之前就把路径定下来，不依赖拥塞反馈，也不需要等待空闲间隙。

3. 设计

图 1：(a) 两级 spine-leaf 拓扑；(b) 路径预留控制器的流程；(c) 控制平面广播预留、数据平面传输 KV 流的分离部署。

问题模型。 两级 spine-leaf 网络中每个 leaf 连接全部 N_S 个 spine，跨 leaf 的主机对之间有 K = N_S 条等价路径，每条恰好经过一个 spine，ECMP 按 k = H(五元组) mod K 选路。

关键观察：源端口是主机自己能控制的哈希输入。 KV 传输使用统一的目的端口，对一对主机而言源 / 目的 IP、目的端口和协议都是固定的，只有源端口可变。只要知道交换机的哈希函数 H，主机就能枚举源端口，算出每个源端口会被哈希到哪个 spine。

每台主机上运行一个用户态的 路径预留控制器：

  1. 启动时预计算：对每个对端枚举 δ = 0 … 2^16 个源端口，按 H(q) mod K 分桶，得到“spine k → 可用源端口”的映射表。
  2. 流到达：扫描本地预留表 R，选编号最小的未预留 spine，从对应桶中取一个源端口创建 RDMA QP 发送 KV Cache，同时向所有对端广播 RESERVE。
  3. 流完成：从 R 中删除该 spine，广播 RELEASE。
  4. 全部占满：|R| = K 时退回普通 ECMP，随机选一个 spine。

控制面与数据面分离。 RESERVE / RELEASE 消息很小但对时延敏感：广播时延决定了两台主机争抢同一 spine 的竞争窗口。ARK 把它们放在低带宽网络或现有管理信道上，避免排在大象流后面；KV 流本身走普通 RDMA 网络，交换机照常做 ECMP。

竞争处理。 R 是异步更新的副本，两台主机可能在一个广播时延内预留同一 spine。每条 RESERVE 携带 (时间戳, 主机 id)，较小者胜出，失败者换一个 spine 重新哈希。这要求主机时钟同步精度在广播时延（几微秒）以内，PTP 即可满足。

论文把 ARK 定位为调度设计空间中最轻的一端：Fastpass、Flowtune 用中心仲裁器按包或 flowlet 调度，ARK 不需要仲裁器和流量矩阵，每条流只在准入时做一次 spine 选择。

4. 实验结果

设置。 平台为 SimAI：计算由 Vidur 建模（用 H100 上实测的 LLaMA-3-8B 逐层数据训练回归器，预测 prefill / decode 时延），KV 传输在 AstraSim 基于 ECMP 的 NS-3 后端上做分组级仿真，ARK 实现为主机侧应用。拓扑为两台 8 GPU 服务器（Server 1 做 prefill，Server 2 做 decode）、2 个 leaf、4 个 spine，所有链路 100 Gbps，每个 leaf 800 Gbps 入口对 400 Gbps 上行，超售比 2:1。提示长度服从 α = 0.7 的 Zipf 分布，均值约 13,300 token，按每 token 128 KB 计，KV 流为 125 MB–6.7 GB（均值 1.6 GB）。泊松到达，每组 1000 个请求，基线为 ECMP。

4.1 FCT 与 spine 负载

图 2：泊松到达下 QPS 从 1 扫到 30，蓝色标注为 ARK 相对 ECMP 的 FCT 降幅。

  • QPS = 1 时流很少重叠，平均 FCT 只降 1.9%，P95 降 1.2%。
  • 负载上升后收益扩大，正文报告在 QPS = 25 达到峰值：平均 −27.3%，P95 −34.0%。图中 QPS = 20 处标注的平均降幅为 28.9%，略高于正文给出的峰值。
  • QPS = 30 时 leaf–spine 接近饱和，收益收窄到平均 13.8% / P95 12.4%。

图 3：ECMP 下 Spine 2、3 长时间承载多达 18 条并发流，Spine 1、4 间歇空闲；ARK 把四个 spine 的峰值都压在约 8 条以内。

4.2 TTFT

TTFT 按 T_prefill + T_KV + T_decode-1 计算：T_KV 取 NS-3 仿真的 FCT，其余两项由 Vidur 预测。

图 4：与图 2 相同的 QPS 扫描，蓝色标注为 ARK 相对 ECMP 的 TTFT 降幅。

平均 TTFT 的降幅从 QPS = 5 的 2.2% 增长到 QPS = 25 的 12.9%；P95 的降幅在 QPS = 30 时最大，为 11.5%。Prefill（约 840 ms）和首个 decode 步（约 10 ms）是固定偏移，所以 TTFT 的相对收益小于 FCT；TPOT 由 GPU 本地的 decode 决定，不受选路影响。

4.3 控制器开销

操作（Intel i9，单线程单核） 时间
哈希计算（每次） 4.10 μs
预留表查找（每次） 0.87 μs
启动时初始化（每个对端，2^16 个源端口） ~326 ms
每条流的准入（最坏情况），K = 4 / K = 1000 ≤ 3.48 μs / ≤ 870 μs
参照：100 Gbps 下传输 1.6 GB KV Cache ~137 ms

K = 4 时，预留开销约为一次 KV 传输时间的 0.0025%。

5. 总结与思考

1. 把负载均衡从“事后发现”改成“准入时安排”。 CONGA、LetFlow、PLB、Hedera 处理的是同一个难题：网络不知道哪条流大、什么时候来，只能检测或对拥塞做出反应。KV 传输正好相反，大小、目的地和开始时间在 prefill 结束时全部已知，负载均衡变成了一次性的放置决策。ARK 的主要价值在于指出这一点，机制本身（复制预留表 + 广播）相当朴素。

2. 源端口是主机控制路径的“后门”。 主机能改的哈希输入只有源端口，ARK 借它反解 ECMP，用纯软件实现了类似源路由的效果。代价是对交换机行为的强依赖：主机要知道哈希函数 H，而且 mod K 的映射要保持不变。多层 Clos 需要在每个 ECMP 决策点分别反解；链路故障改变 ECMP 组成员后，启动时算好的映射表就会失效，论文没有讨论故障场景。

3. 二值预留在高负载下很快用完。 预留表中每个 spine 只记一条流，占满后新流回到随机 ECMP。按 Little 定律粗算，QPS = 25 时 ARK 的平均 FCT 约 0.55 s，同时在传的流约有 14 条（25/s × 0.55 s），远多于 K = 4；图 3 中 ARK 下每个 spine 也同时承载多条流。也就是说，收益最大的负载区间里，多数流是在预留表已满后随机下发的。论文没有给出预留流与回退流的比例，收益有多少来自预留本身并不清楚。此外，论文强调流大小在准入时已知，选路却只看 spine 是否被占用；按剩余字节数选最轻的 spine，是更自然的推广。

4. TTFT 收益建立在串行传输模型上。 按图读数，QPS = 25 时平均 FCT 从约 755 ms 降到约 550 ms，平均 TTFT 从约 1600 ms 降到约 1395 ms，两者的绝对降幅都在 200 ms 左右，说明串行模型里网络省下的时间原样计入了 TTFT。但 Splitwise、Mooncake 都把 KV 传输按层与 prefill 计算重叠，Splitwise 报告在 H100、400 Gbps 下未被重叠的传输时间只有约 5 ms。在这类系统中，12.9% 更接近上界；而且逐层发送可能让一条 KV 流出现层间间隙，论文用来排除 PLB、flowlet 方案的“流内没有空闲间隙”这一前提也会随之变弱。

5. 评估还停留在概念验证规模。 一台 prefill 服务器、一台 decode 服务器、4 个 spine，只有一个 8B 模型；基线只有 ECMP，没有与逐包喷洒、自适应路由或集中式调度对比，也没有考虑与集合通信等其他流量共存。作为 workshop 论文，它提出的视角（把 KV 流当成可预知的大流来调度）比具体机制更有价值。
