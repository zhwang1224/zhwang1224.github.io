阿里 xMaaS 生产 Trace 解读

发表于 2026-11-20 分类于 人工智能系统 阅读时长 ≈ 25 分钟
SIGOPS ATC 2026 Best Paper 阅读笔记。基于阿里 xMaaS 平台六个月、101,499 张 GPU、30 种 GPU 型号的生产 LLM 推理 trace，从集群、应用、模型三层回答 GPU 如何被供给、分配、占用和使用，并归纳显存超额预留、异构资源管理、PD 分离适用性三个开放问题。

生产环境的 MaaS（Model-as-a-Service）平台非常复杂：几十种 GPU、近 30 万个应用、7 万个模型变体。SIGOPS ATC 2026 Best Paper《Model-as-a-Service in the Wild》分析了阿里 xMaaS 平台六个月的生产 trace，覆盖 101,499 张 GPU。以往的 trace 研究多看请求，这篇论文从资源侧回答：这些 GPU 是怎么被供给、分配、占用和实际使用的。

最突出的结论是在实际生产环境中 GPU 被长期占用，但可能并没有被有效利用。在线负载 60% 的 GPU Time 的 SM 利用率在 15% 以下，显存却长期保持在 80%–95%。一个 4B 模型的应用在约 500 张 96 GB GPU 上把显存占到接近 99%，KV Cache 占用率大部分时间只有个位数。此外，资源消耗高度偏斜，冷门模型的问题在于长期驻留显存。

1. 从资源侧看推理

KV Cache 管理、请求调度、PD 分离、模型扩缩容等推理优化，收益都取决于部署条件：实时 KV Cache 需求、驻留的模型变体、资源类型和负载模式。论文认为，已有的 characterization 恰好缺这一块：

  • 通用 ML 平台（MLaaS，NSDI ‘22）和 LLM 训练集群（Acme，NSDI ‘24）的研究，与推理服务的需求和行为不同；
  • BurstGPT、ServeGen 等请求级 trace 记录了到达模式、突发性和 token 长度，适合负载建模，但不暴露资源使用和集群部署信息。

2. xMaaS 与 trace

平台组织

图 1 xMaaS 总体架构：用户请求进入在线/离线应用，应用以实例部署到多集群、多机房、多 ASW 域的异构 GPU 上；基础模型经后训练产生模型变体。

  • 资源层级：地域 → 集群 → 机房 → ASW（接入交换机）域 → 机架 → GPU 服务器。同一 ASW 下的机架使用同一种 GPU，同一机房内的不同 ASW 域可以是不同型号，所以异构性出现在机房和集群粒度。
  • 应用与实例：应用是部署单元，在线、离线都有；实例是调度和执行单元，在整个生命周期内持有固定的 GPU 分配。
  • 基础模型与变体：基础模型是一个训练好的模型（如 DeepSeek-V4），变体是经后训练或业务定制得到的可部署版本。一个实例同一时刻只服务一个变体，同一变体可以部署在多个应用中。
  • 服务引擎：使用自研引擎或 SGLang 等开源引擎，启动时通常预分配 KV Cache 池。支持 PD 合并（collocated）和 PD 分离（disaggregated）两种模式。
  • 扩缩容：由用户选择模型、GPU 型号、实例数和服务配置。平台支持在预定时间释放资源的定时缩容，以及按 SM 利用率加实例的阈值扩容。在线服务会为流量突发预留余量，并固定在合适的 GPU 型号上；离线服务的 batching 更激进，也能更灵活地使用各集群、各型号的空闲容量。

论文明确指出，这些配置直接决定了 trace 呈现的资源行为：KV Cache 预分配使显存保持预留状态，在线余量和扩缩容策略影响 SM 利用率和分配变化。

3. Insight 1

全局：显存占用但 SM 利用率不高

图 5 全集群资源动态：左为选定的一周，右为六个月总览（阴影为选定周）；四行依次为 SM 利用率、GPU 显存利用率、CPU 核数和主机内存。

  • SM 利用率：选定的一周内，在线负载呈明显的昼夜规律，低谷 10%–15%，峰值 25%–30%；离线负载更高，通常在 40%–60%，周期性较弱。六个月尺度上，在线 SM 利用率大多在 10%–25%。
  • 显存利用率：在线通常保持在 80%–95%，只在低流量时段出现规律性低谷；离线在 80%–90%，波动更大。论文认为这与常驻的模型权重、运行时缓冲区和预分配的 KV Cache 池相符。
  • 主机侧几乎不紧张：选定周内在线实例通常只用约 1.5–3 个 CPU 核、5–10 GB 主机内存，离线约 2.5–5 核、25–50 GB。

按 GPU Time 加权的分布更直观（图 11(d)）：在线 60% 的 GPU Time SM 利用率低于 15%，离线为 30%；SM 利用率超过 50% 的部分在在线 GPU Time 中不到 10%，在离线中超过 40%。

跨型号：在线占比越高，利用率越低

图 4 GPU Time 排名前五的 GPU 型号的 SM 利用率：(a) 按 GPU Time 加权的分布；(b) 每个点代表某型号在某集群的部署，横轴为在线 GPU Time 占比，纵轴为 SM 利用率中位数，点的大小表示 GPU Time。

前五种型号的 SM 利用率中位数从约 20% 到 40% 以上不等，四分位距也差别很大。同一型号部署在不同集群时，中位利用率也可能相差悬殊。总体趋势是在线占比越高，利用率越低，这与在线预留余量、离线激进 batching 的部署策略一致。

单应用：99% 的显存，个位数的 KV 占用

图 9 一个高 GPU Time 的在线应用（4B 模型）在选定周内的表现：(a) GPU 显存利用率与 KV Cache 占用率（双纵轴）；(b) SM 利用率。

一个服务 4B 模型的在线应用，部署在约 500 张 96 GB 显存的 GPU 上。整周显存利用率都接近 99%，KV Cache 占用率大部分时间只有个位数；SM 利用率仍有明显的昼夜周期，峰值超过 30%。

原因是模型规模与显存容量不匹配：4B 模型的权重只占 96 GB 中的一小部分，运行时把剩余显存预分配给 KV Cache 池，而这个池大部分时间空着。只看物理显存遥测，会以为这些 GPU 已经满载，只有结合应用级的 KV Cache 指标才能看出差别（Observation 6）。

4. Insight 2：极度偏斜，头部决定效率，长尾决定复杂度

偏斜几乎出现在每一个维度上：

GPU 型号（30 种） 后一半 仅 3.5%，但仍有 12.9M GPU 小时

模型变体的数量结构值得单独看：

  • 在线负载有 1,158 个基础模型、10.8K 个变体，平均每个基础模型 9.3 个；离线只有 638 个基础模型，变体却多达 59.8K 个，平均 93.7 个。
  • 离线的变体数约为在线的 5.5×，GPU Time 却只有在线的 1.5×。
  • 约 55% 的基础模型只有一个变体；约 85% 的在线基础模型变体数少于 10 个（离线为 75%）；变体最多的基础模型超过 5K 个变体。论文提醒，按基础模型聚合会掩盖可部署变体的多样性。

推论：前 10% 的应用和变体覆盖了绝大部分 GPU Time，对它们逐个调优、专门安排放置是划算的；长尾数量巨大，逐个调优不现实，只能依靠共享、换入换出、自动扩缩容等通用机制。

在线部署紧凑，离线部署分散，这与离线负载放置更灵活一致。真正值得注意的是下面这张图：

图 11 在线与离线负载的模型级资源画像（均按 GPU Time 加权）：(a) GPU 峰值算力；(b) GPU 显存容量；(c) 模型规模；(d) SM 利用率。

  • 两类负载约 80% 的 GPU Time 都跑在峰值算力低于 200 TFLOPS 的 GPU 上；约 60% 跑在显存低于 100 GB 的 GPU 上。
  • 8B 以下的模型在两类负载中都约占 40% 的 GPU Time，到 32B 时都累计到约 75%。差别只在最大的几档：离线在 235B 处有明显跳变，在线在 235B 以上拖着更长的尾巴。

硬件相同、模型规模相同，利用率却差一大截，说明差距主要来自服务目标和部署策略（在线要预留余量、离线可以激进 batching），而非硬件或模型本身（Observation 8）。

6. Insight 4：需求在变，分配不变，缩容比扩容难

图 8 两个在线应用在选定周内的表现，按 GPU 型号着色：从左到右依次为归一化 QPS、分配的 GPU 数、每小时平均输入/输出长度的 CDF、TTFT 和 TPOT。

App2 是使用至少三种 GPU 型号的在线应用中 GPU Time 最高的一个，App1 与它共用 GPU-A 和 GPU-B，因此可以在相同硬件上做应用内和跨应用的对比。

  • App1：QPS 每天都有清晰的周期，GPU 分配几乎是一条直线。
  • App2：QPS 连续数天处于低位，GPU 分配却几乎不变；仅有的几次调整集中在 GPU-D 上，也不跟随对应的 QPS 曲线。

论文的解释是这一时期的容量调整很保守（Observation 5）。第 7.1 节给出了深层原因：释放容量可能丢掉已加载的热模型状态，削弱应对突发的能力。已有工作主要在加速模型加载和扩容（ServerlessLLM、DeepServe、BlitzScale）以及分层自动扩缩容（Chiron），这份 trace 揭示的则是互补的另一面：安全缩容在生产中同样关键。生产级 autoscaler 必须能回收空闲的显存和算力，同时在流量突然回升时不损害性能。

7. Insight 5：冷门模型的问题是驻留，而不是生命周期短

论文在每类负载内按六个月 GPU Time 给变体排名，前 10% 为热变体，其余 90% 为冷变体，分类只依据 GPU Time 贡献。

生命周期（原文图 13(a)）：

  • 在线热变体与冷变体实例的生命周期分布几乎一样：约一半实例运行不到 1 小时，最长的超过 1,000 小时。在线变体冷门，并不意味着生命周期短。
  • 离线则不同：约 95% 的冷变体实例运行不到 1 小时，热变体约为 70%。

模型规模（原文图 13(b)）：冷变体的 GPU Time 主要累积在 3B–8B 区间，离线尤其明显。在线冷变体到 32B 时已累积约 90% 的 GPU Time，热变体约为 75%；热变体在 32B 以上保留更多 GPU Time，在线热变体延伸到最大的模型规模。

图 14 热/冷模型变体的资源利用率（CDF 均按 GPU Time 加权）：(a) SM 利用率；(b) 零利用率时间占比；(c) GPU 显存利用率；(d) 不同 SM/显存阈值组合下的显存空闲 GPU Time 占比。

  • SM 利用率：同样取 75% 的 GPU Time，在线冷变体的 SM 利用率不到 10%，在线热变体接近 30%。
  • 零利用率：以 50% 的零利用率时间占比为阈值，两类负载中都有约 40% 的冷变体 GPU Time 超过阈值，热变体不到 20%；超过 20% 的在线冷变体 GPU Time，零利用率占比接近 100%。也就是说，这些变体有大段时间完全不做计算，而不只是平均利用率低。
  • 显存空闲：论文把 SM 利用率低、显存利用率高的区间定义为显存空闲（memory-idle），即 GPU 保留着权重、运行时缓冲和预留的 KV 容量，却几乎不做计算。两类热变体和在线冷变体都有超过 80% 的 GPU Time 处于显存利用率 80% 以上。在四组 SM/显存阈值下，在线冷变体的显存空闲比例最高，约占 GPU Time 的 50%–65%；在线热变体约 20%–30%，两类离线变体都低于约 15%。

论文的原话是：冷门在线变体是 a residency problem rather than merely a low-compute tail，它们的问题是长期驻留显存，而不只是计算量少的长尾（Observation 10）。

这一点与 serverless 推理的常见假设不同。冷启动优化通常假定冷门模型来得快、走得也快；这里的冷门在线变体却可能运行上千小时、占满显存、几乎不做计算。可行的方向之一是让同一基础模型的变体共享权重（Punica、S-LoRA、Chameleon 等 adapter serving 系统），但论文指出，生产中还要求推理框架、显存布局、通信库和量化格式彼此兼容，需要兼容性感知的分组和跨运行时支持。

8. Insight 6：异构不可避免，最好的 GPU 并不存在

集群内部本身就是异构的：56 个集群中只有 14 个是单一 GPU 型号，好几个集群包含 8–10 种型号。论文认为，到 O(100K) GPU 的规模，硬件异构是必然的，未来还会加入更多 GPU 代际和专用加速器。

“最好的 GPU”因应用、因指标而异（图 8 右侧两列）：

最低 TTFT 最低 TPOT
App1 GPU-B，25 ms GPU-C，2.8 ms
App2 GPU-D，65 ms GPU-A，6.9 ms

在两个应用共用的 GPU-A 和 GPU-B 上，GPU-B 的 TTFT 在两个应用中都更低，差距从 App1 的约 2 倍缩小到 App2 的 1.4×；TPOT 的排序却反过来了（App1 中 GPU-B 更低，App2 中 GPU-A 更低，但差距只有几个百分点）。同一应用在不同型号上的每小时平均 token 长度很接近，所以这些差异无法用长度来解释。

部署矩阵很稀疏：

图 18 前 30 个模型在各 GPU 型号上的部署覆盖：行为按 GPU Time 排序的模型，列为按 GPU Time 排序的 GPU 型号，着色格表示 trace 中出现过该组合的部署。

前 30 个模型与 GPU 型号的组合中，只有 53.4% 在 trace 中出现过。矩阵左密右疏：GPU Time 越高的型号承载的模型越多。论文认为这在一定程度上反映了运行时支持不完整，例如某些型号缺少相应的 kernel、量化支持或通信后端。反过来看，这是很大的优化空间：只要扩展运行时支持，不换硬件就能让许多此前不可行的模型–硬件组合变得可行，从而扩大调度空间。论文提到的方向包括基于 LLM/agent 的 kernel 生成与调优（CuTeGen、Xe-Forge、Astra、AccelOpt）。

换句话说，在异构集群里，软件覆盖率本身就是容量。Mélange、Helix、Hetis、Coral 等异构推理系统通常假定一组固定的候选硬件或特定负载，而生产环境需要的是能随新 GPU、新负载持续扩展的放置机制。

9. Insight 7：PD 分离是可选项

模式 应用 实例 基础模型 模型变体 GPU Time（GPU 小时）
PD 合并 9.4K 1.6M 1,148 10.7K 133.6M
PD 分离 477 69.0K 146 384 14.4M

表 3 在线负载按 PD 服务模式划分的规模。

按应用、实例和变体数量计，PD 分离都是少数。按 GPU Time 推算，它约占在线 GPU Time 的 9.7%（14.4M / 148.0M，本文计算），但绝对量仍有 1,440 万 GPU 小时。

用在哪里（原文图 15）：PD 分离的 GPU Time 中，32B 以下的模型只占约 30%，一半以上来自 235B 以上的模型；PD 合并的 GPU Time 中，235B 以上的模型不到 10%。硬件上，PD 分离集中在峰值算力和显存容量都更高的 GPU 型号，与算力的关联更强。

图 16 PD 合并实例与 PD 分离的 prefill/decode 实例的资源画像（按 GPU Time 加权）：(a) SM 利用率；(b) 单实例显存分配；(c) 单实例 GPU 数；(d) PD 分离部署的 prefill/decode GPU Time 比。

  • 反直觉的 SM 利用率：decode 实例的 SM 利用率高于 prefill，两者都高于 PD 合并实例。prefill 一般是计算密集型阶段，但为了吸收 prompt 突发、保护 TTFT 而预留的 prefill 容量，会拉低其平均利用率。观测到的利用率由部署层面的容量配置和阶段特性共同决定。
  • 更大的实例：单 GPU 实例占 PD 合并 GPU Time 的 60% 以上，在 PD 分离中却不到 10%；PD 分离以 4 卡和 8 卡实例为主。xMaaS 中的 PD 分离部署限制在单个 ASW 内，两个阶段使用同一种 GPU。
  • P/D 配比极其分散：prefill 与 decode 的 GPU Time 之比从 1:10（极端偏 decode）到 10:1（极端偏 prefill）不等，1:1 只占约 20%，一半以上来自偏 prefill 的部署。P/D 平衡因此是按模型、按应用决定的配置问题，不存在固定比例。

图 10 GPU Time 最高的 PD 分离在线应用：(a) prefill 与 decode 的 KV Cache 占用率；(b) prefill 时延和 KV Cache 传输时延随归一化 QPS 的变化。

  • KV 占用两极分化：decode 的 KV 占用率在 30%–60% 之间波动，prefill 一直很低，峰值约 7%，prefill 池留有大量闲置的 KV 容量。
  • KV 传输与 prefill 重叠：KV 传输时延与 prefill 时延量级相当，都随 QPS 上升。

**为什么生产中只有选择性地采用 PD 分离？**论文给出三点（§7.3）：

  1. **硬件组织限制了异构 PD 的收益。**把 prefill 和 decode 放到不同类型的硬件上（Splitwise 的核心思路，见本站《Splitwise》）可以提升效率，但生产中的高速互连域通常是同构的，比如 xMaaS 中同一 ASW 下都是同一种 GPU。数据中心扩建按 GPU 代际和部署批次进行，同构的局部域也简化了兼容性、容量规划和多负载支持。于是异构 PD 往往要跨越局部硬件域，KV Cache 传输开销可能抵消甚至吃掉阶段专用化带来的收益。Prefill-as-a-Service 这类软件方案跨部署共享 prefill 容量，部分缓解了这个问题，但仍要处理局部性、调度和 KV 传输开销。
  2. **收益取决于负载和服务要求。**32B 及以下的模型约占在线 GPU Time 的四分之三，PD 分离则集中在大模型上。如果 PD 合并已经能满足时延和吞吐要求，PD 分离只会带来额外的传输和管理成本。
  3. **运维复杂度更高。**需要独立的资源池、跨实例 KV 传输、协调扩缩容，以及更复杂的监控和故障处理。

对确实需要 PD 分离的负载，下一个难题是弹性 P/D 伸缩：资源分配要同时考虑 prefill/decode 需求和 TTFT/TPOT 目标；在 P/D 池之间迁移请求会带来 KV 传输开销和局部性约束，因此伸缩决策要同时考虑 prefill 算力和可用的 KV 传输带宽，并保证服务可用性。

10. Insight 8：MoE 以少量模型占用四分之一的 GPU

架构 应用 实例 基础模型 模型变体 GPU Time（GPU 小时）
Dense 260.4K 118.4M 1,169 68.8K 270.3M
MoE 38.3K 15.9M 155 1.4K 95.6M

表 4 Dense 与 MoE 负载的规模（在线和离线合计）。

  • MoE 的基础模型、变体和应用都远少于 Dense，却占合计 GPU Time 的约 26%，而且这一比例在六个月内保持稳定。每个 MoE 变体的 GPU Time 约为 Dense 的 18×，这与 MoE 更多采用多卡部署相符。
  • MoE 的 GPU Time 集中在约 30B、235B 和 700B 三档，仅 235B 一档就约占一半；Dense 模型中 32B 以上的不到 10%。也就是说，这份 trace 中超大模型的 GPU Time 主要来自 MoE。
  • 单实例显存分配：MoE 中超过 400 GB 的约占 60% 的 GPU Time，超过 800 GB 的占 10% 以上；Dense 约 90% 的 GPU Time 单实例不超过 200 GB。单 GPU 实例约占 Dense GPU Time 的 80%，在 MoE 中不到 20%；MoE 以 4 卡（约一半）和 8 卡（约 20%）实例为主。

11. 三个开放问题

论文第 7 节把以上观察收敛为三个开放问题：

生产证据 方向 落地约束
OP1 显存超额预留 KV 池按峰值预留（图 9）；冷门在线变体长期驻留（图 14）；保守缩容（图 8） 动态 KV 显存池；冷变体间共享显存；安全的弹性缩容 要能跨 30 种 GPU 移植（很多现有机制依赖厂商或运行时专有的显存 API）；共享会削弱故障隔离，而在线实例可能运行 1,000 小时以上；需要跨多个运行时兼容
OP2 异构资源管理 30 种 GPU 型号；同一应用的最优 GPU 随指标而变（图 8）；部署覆盖率仅 53.4%（图 18） 可扩展的放置策略；扩展运行时支持（kernel 自动调优、跨平台移植） 新 GPU 代际、专用加速器和新负载会持续进入生产；现有方案多假定固定的候选硬件
OP3 弹性 PD 分离 PD 分离只占少数，集中在大模型上；P/D 比从 1:10 到 10:1（图 16） 在不中断服务的前提下弹性调整 P/D 资源 同时满足 prefill/decode 需求与 TTFT/TPOT 目标；KV 传输开销与局部性；可用性与可靠性
  • OP1：生产 MaaS 系统如何 (i) 在多种 GPU 上弹性回收按峰值预留、实际用得很少的 KV Cache 显存，(ii) 在运行时各异的冷门模型变体之间共享显存，(iii) 在不影响性能的前提下安全缩减空闲的在线容量？
  • OP2：如何构建可扩展的异构资源管理机制，适应多样的负载、不断演进的 GPU 型号和不均匀的运行时支持？
  • OP3：如何让 PD 分离具备弹性，在负载变化时调整 P/D 资源，同时保持服务可用性和可靠性？

总结

这篇论文没有提出新系统，但给出了一份难得的生产资源账本。可以浓缩成三句话：**显存是被锁死的资源，算力被闲置在显存已满的 GPU 上；偏斜和异构是常态，头部与长尾、在线与离线需要不同的机制；PD 分离、显存共享、弹性伸缩这些成熟思路，在生产中都要过可移植性、故障隔离和运维复杂度这几关。**对做推理系统的人来说，它最大的价值也许是指出了几个仍然缺少答案的方向：安全缩容、冷模型驻留和弹性 P/D。
