集合通信入门：从一次梯度同步说起

网上讲集合通信的文章，要么停在”broadcast 就是广播、all_reduce 就是全归约”这种同义反复，要么一上来就是复杂度推导。这篇想走中间路线：从一个能手算的最小例子出发，把每个原语的语义、它们之间的关系、以及在真实训练框架里的样子讲清楚，尽量不引入用不上的公式。

一、先看一个最小的例子

假设我们用两张卡训练一个只有一个参数的”模型” $y = w \cdot x$，损失是平方误差，初始 $w = 2.0$，学习率 0.1。两张卡拿到不同的数据：

rank 0 1 1 2 2(2−1)(1) = +2
rank 1 2 6 4 2(4−6)(2) = −8

二、通信发生在训练的什么位置

两个容易混淆的概念在这里先分清楚：

  • 控制面（control plane）：进程之间交换”我是谁、我在哪、我们有几个人”这类元信息。PyTorch 里由 init_process_group 的 store（TCP/文件/环境变量）完成，走的是普通 socket。
  • 数据面（data plane）：真正搬运张量。走的是 NVLink、RDMA 这些高速路径。

排障时先判断问题出在哪个面，能省掉大量时间：卡在初始化多半是控制面（地址、网卡、防火墙），跑起来之后变慢或 hang 多半是数据面。

三、十个原语，一次讲清

在逐个看之前，先建立一个总的认识：这些原语并不是十种彼此独立的能力，而是少数几个底层动作的固定组合方式。底层动作只有五个：

底层动作 作用
send / receive 把一段数据从一个进程搬到另一个进程
copy 在本地复制数据（含跨设备的显存拷贝）
reduce 算子 对两份数据做按元素运算（求和、取最大等）
barrier 让所有进程在某一点对齐
signal / wait 成对的事件通知，保证”数据到了”这件事被对端确知

所谓通信原语，就是把这五个动作按特定模式编排出来的模板。理解这一点有两个好处：一是不用死记十个定义，二是当某个库缺少你想要的原语时，你知道可以用 send/recv 自己拼出来（性能另说）。

集合通信真正的难点也不在语义——语义都很简单——而在于如何把这些模板高效地映射到具体的硬件拓扑上。同一个 AllReduce，在 4 卡全互连的机内、在 8 机 64 卡的 fat-tree 上，最优的编排方式完全不同。这也是为什么会有 NCCL 这类库存在。

3.1 点对点通信

send / recv 是一对一的，严格说不算”集合”通信，但它是所有集合操作的基础构件，也是流水线并行唯一用到的通信方式。

要点：send 和 recv 必须配对。落单的一方会一直等下去，这是最容易写出的死锁。

3.2 一对多：broadcast 与 scatter

两者都是”root 发给大家”，区别在于发的是不是同一份数据。

broadcast——所有人拿到 root 的同一份数据：

典型用途：训练开始时把 rank 0 的初始参数同步给所有卡；把随机种子、配置广播出去。

scatter——root 手里有 4 份数据，每人分一份不同的：

典型用途：把一个大张量按 rank 切分下发。实践中更常见的做法是各卡直接读自己那份数据，所以 scatter 的使用频率低于 broadcast。

3.3 多对一：gather 与 reduce

这两个是上一组的逆向，数据从大家汇聚到 root，区别在于汇聚时是拼接还是运算。

gather——拼接，root 拿到所有人的数据首尾相连：

reduce——按元素运算，root 拿到运算结果：

注意 gather 的结果长度是输入的 4 倍，而 reduce 的结果长度和输入相同——一个是拼接，一个是叠加，这是区分二者最快的方式。

关于归约算子。 MPI 标准定义了一整套算子，但各家 GPU 通信库支持的只是其中一个子集，这一点在移植代码时经常被绊到：

算子 含义 MPI NCCL PyTorch (dist.ReduceOp)
SUM 求和 ✅ ✅ ✅
PROD 求积 ✅ ✅ ✅ PRODUCT
MAX / MIN 最大 / 最小 ✅ ✅ ✅
AVG 求平均 — ✅（2.10+） ✅（需 NCCL 后端）
LAND / LOR / LXOR 逻辑与 / 或 / 异或 ✅ ❌ ❌
BAND / BOR / BXOR 按位与 / 或 / 异或 ✅ ❌ ⚠️ 仅 Gloo
MAXLOC / MINLOC 极值及其所在位置 ✅ ❌ ❌

三点实践提示：

  • NCCL 只支持算术类算子，逻辑与按位运算一概不支持。需要这些的话得走 Gloo 后端或自己用 all_gather 拼。
  • AVG 值得优先用。手写 all_reduce(SUM) 再除以 world_size 要多走一遍显存；NCCL 的 ncclAvg 把除法融进了归约过程。
  • MAXLOC/MINLOC 返回的是”值 + 位置”的二元组，用于”哪张卡上出现了最大 loss / 第一个 NaN”这类问题。NCCL 没有，通常的替代做法是先 all_reduce 求 MAX，再各卡比对本地值是否等于全局最大。

归约算子必须由加速卡的算子库真正支持才能生效——这不是纯粹的通信问题。低精度类型（BF16/FP8）下某些算子的支持情况会更不完整，用之前值得实测确认。

all_gather = gather + broadcast，每个人都拿到拼接结果：

all_reduce = reduce + broadcast，每个人都拿到归约结果：

典型用途：FSDP 在反向传播后，把梯度归约的同时就地切分，每张卡只保留自己负责更新的那一段。

3.5 全交换：all_to_all

每张卡把自己的第 j 块发给 rank j，同时从每个人那里收一块。用矩阵的语言说，这就是一次分布式转置。沿用上面的数据：

对照 3.4 的 reduce_scatter 看：同样的输入，reduce_scatter 是”按列求和”，all_to_all 是”整体转置”。前者有归约、结果变小；后者只搬运、总量不变。

和 all_gather 的区别也值得单独点出来，因为两者都是”多对多、只搬不算”，很容易混：

all_gather 中，每个节点发给所有人的是同一份数据；all_to_all 中，发给每个人的是不同的数据。

换句话说，all_gather 是 all_to_all 的一个特例——把每张卡要发出的 n 块内容设成完全相同，all_to_all 就退化成了 all_gather。这也解释了为什么 all_to_all 更”贵”：all_gather 的数据在传输过程中可以被复用和聚合（一份数据发给多个人，树形结构能派上用场），而 all_to_all 的每一块都有唯一的目的地，没有任何复用余地。

典型用途：MoE 模型的 token 路由。每张卡上的 token 要被送到它所选专家所在的卡上算，算完再送回来——正好是两次 all_to_all。变体 all_to_all_v 允许每对收发的长度不同，因为路由结果是数据相关的、天然不等长。

这也是最”吃”网络的原语：它没有任何数据复用，n 张卡之间要传 n(n−1) 个互不相同的块，且每块只传一次。AllReduce 起码还能靠树形结构聚合，all_to_all 没有这个余地。

3.6 同步：barrier、signal 与 wait

barrier 不搬数据，只保证”所有人都到齐了才继续”。

常用于计时打点、确保某个 rank 写完文件后其他 rank 再读。不要在训练主循环里随手加 barrier——它会把所有卡拉齐到最慢的那张，抹掉本来可以重叠的时间。

signal / wait 则是 barrier 的”点对点版本”，也是所有数据传输背后真正在起作用的同步机制。它是一对记录型信号量：

为什么必须有它？因为**”数据写完了”和”对端知道数据写完了”是两件事**。网络和内存系统都可能重排写入顺序，接收方看到缓冲区里有内容，不代表内容是完整的。必须有一个明确的、保证在数据之后到达的信号，接收方才敢读。

这个抽象在真实系统里有很具体的对应物：

  • CUDA 层面：cudaEventRecord / cudaStreamWaitEvent 就是一对 signal/wait，用来在流之间建立依赖；
  • NCCL 内部：小消息用的 LL 协议把 4 字节数据和 4 字节标志位打包进同一个 8 字节原子写——标志位本身就是那个 signal，接收方轮询标志位即可确认数据有效，省掉了一次昂贵的内存屏障；
  • 应用层面：torch.cuda.Event 暴露的就是这套机制。

平时写训练代码不会直接调用 signal/wait，但理解它的存在能解释一类困惑：为什么通信 API 返回了、数据却还不能读（返回只代表”已入队”，signal 还没发生）；为什么第十节强调”同步完成前不能释放缓冲区”（wait 还没返回，数据可能还在途中）。

四、原语之间的关系

这十个原语不是十件互不相干的事，它们之间有很清晰的结构。看懂了下面这几条，记忆量会大幅下降。

第一组关系：加不加 All 前缀。

第二组关系：互为逆操作。

第三组关系：可以互相组合。 AllReduce 有两种分解方式，它们的对比很能说明问题：

分解 ① 最符合直觉：所有人把数据发给 rank 0，rank 0 算出结果再广播回去。但它有个致命问题——rank 0 的网卡要承受 n 倍的进出流量，其余所有链路都闲着。卡越多，root 越是瓶颈，完全不随规模扩展。

分解 ② 则让每张卡只负责结果的 1/n：先通过 reduce_scatter 各自把自己那段算完，再通过 all_gather 互相补齐。每张卡的收发量相同、所有链路同时工作，没有任何一点成为瓶颈。

用第 3.4 节的数据验证分解 ②：reduce_scatter 之后四张卡分别持有 1111 / 2222 / 3333 / 4444，再做一次 all_gather，每张卡都得到 [1111, 2222, 3333, 4444]——正是对原始矩阵做 all_reduce 的结果。

现代通信库走的都是分解 ②，第五节的 Ring AllReduce 就是它的一个具体实现。分解 ① 只在极小规模或特殊拓扑下才可能划算。顺带一提，Parameter Server 架构本质上就是分解 ① 的工程化版本（worker 把梯度 reduce 到 server，server 更新后再 broadcast 回去），它的扩展性瓶颈和这里是同一个——这也是大规模训练最终转向 AllReduce 范式的原因。

这条恒等式有两个非常实际的推论：

  1. 它是 Ring AllReduce 的实现基础（下一节展开）；
  2. 它解释了 ZeRO/FSDP 为什么”看起来换了通信方式，其实通信量没变”。ZeRO-1/2 把 DDP 的一次 all_reduce 拆成 reduce_scatter + all_gather，总搬运量相同，但中间状态只需要保存 1/n，省的是显存。

五、AllReduce 内部到底怎么做

用户看到的是一次 all_reduce 调用，通信库内部要把它变成一系列点对点收发。最经典的实现是 Ring AllReduce：把所有卡排成一个环，数据切成 n 块，转两圈。

沿用第 3.4 节的数据，4 张卡排成环 0 → 1 → 2 → 3 → 0。

第一圈：reduce_scatter（3 步）。 每一步，每张卡向右邻发一块、从左邻收一块并累加：

步 rank0 rank1 rank2 rank3
初始 1, 2, 3, 4 10, 20, 30, 40 100, 200, 300, 400 1000, 2000, 3000, 4000
步 1 收到 4000
→ 块3 = 4004		 收到 1
→ 块0 = 11		 收到 20
→ 块1 = 220		 收到 300
→ 块2 = 3300
步 2 收到 3300
→ 块2 = 3303		 收到 4004
→ 块3 = 4044		 收到 11
→ 块0 = 111		 收到 220
→ 块1 = 2220
步 3 收到 2220
→ 块1 = 2222 ✓		 收到 3303
→ 块2 = 3333 ✓		 收到 4044
→ 块3 = 4444 ✓		 收到 111
→ 块0 = 1111 ✓

3 步之后，每张卡都完整地拥有了一块归约结果（rank0 拥有块1、rank1 拥有块2、rank2 拥有块3、rank3 拥有块0）。这正是 reduce_scatter 的状态。

第二圈：all_gather（3 步）。 同样沿环传递，但收到后不再累加而是直接写入。3 步后每张卡都集齐了 4 块。

为什么要这么绕？ 一个直觉上更简单的做法是”所有卡把数据发给 rank 0，rank 0 算完再广播回去”。问题在于 rank 0 的网卡要承受 n 倍流量，成为瓶颈，且完全不随卡数扩展。而 Ring 方案中：

  • 每张卡在每一步只收发一块（约 1/n 的数据），所有链路同时工作、负载均衡；
  • 每张卡总共收发约 2 倍于数据量的字节，这个量与卡数无关——64 卡和 1024 卡的每卡通信量几乎一样。

代价是要走 2(n−1) 步，卡多了之后步数带来的固定开销会变得显著。所以通信库对大规模场景会改用树形结构（步数降到 log n 量级），对小消息还有专门的低延迟协议。具体用哪种由库自动选择，这也正是使用集合通信库而非手写点对点的价值：你只需要表达”我要做一次 AllReduce”，怎么做交给库。

六、绕不开的几个术语

读任何一份分布式训练代码或日志，都会遇到这几个词。

术语 含义 怎么拿到
rank 进程在通信组里的全局编号，0 到 world_size−1 dist.get_rank()
world_size 通信组里的进程总数 dist.get_world_size()
local_rank 进程在本机内的编号，用来决定绑哪张卡 环境变量 LOCAL_RANK
process group 一组共同参与集合操作的进程；可以有多个、可以嵌套 dist.new_group([0,1])
backend 底层通信库实现，如 nccl / gloo / mpi init_process_group(backend=...)
communicator 后端内部的通信上下文，对应 PyTorch 的 process group NCCL 的 ncclComm_t
stream CUDA 流；通信操作被放进流里异步执行 torch.cuda.Stream()

几个新手常见的误解：

  • rank ≠ GPU 编号。一个进程可以管多张卡，多个进程也可能在同一台机器上。绑卡要用 local_rank，不是 rank。
  • process group 可以有多个。3D 并行中，同一个进程会同时属于 TP 组、PP 组、DP 组，每组各有自己的 rank 编号。dist.new_group() 创建的子组是理解 Megatron 类代码的关键。
  • 集合操作是按调用顺序匹配的，不看名字也不看 tag。这一条会在第十节反复出现。

7.3 后端全景

深度学习框架从不直接操作底层网络。框架只说”我要做一次 AllReduce”，剩下的全部交给通信库——由它去判断该走 NVLink 还是 RDMA、该用环还是树、该切成几块。

这一层抽象的价值在于：原语的语义与物理介质是解耦的。同一句 all_reduce，底下可能跑在 NVLink、PCIe、CXL 这类板内/机内互联上，也可能跑在 InfiniBand、RoCEv2、以太网这类网络上，应用代码一行都不用改。各家硬件厂商因此都提供自己的实现，统称 xCCL：

后端 适用硬件 说明
NCCL NVIDIA GPU GPU 训练的默认选择，PyTorch 里 backend="nccl"
Gloo CPU 为主 不依赖 GPU，实现简洁，支持按位算子，适合调试和 CPU 场景
MPI CPU / HPC 传统 HPC 标准，算子集最全；需自行编译 PyTorch 才能启用
RCCL AMD GPU NCCL 的 API 兼容移植
oneCCL Intel GPU/CPU 与 oneAPI 集成
HCCL 华为昇腾 NPU 昇腾平台的对应实现，同样提供类似 nccl-tests 的基准工具

此外还有两类容易和上表混淆的东西，用途不同：

  • CUDA-aware MPI：让 MPI 直接收发显存指针而不必先拷回主机内存。它仍是 MPI，只是打通了 GPU 路径；
  • NVSHMEM：不是集合通信库，而是 GPU 上的分区全局地址空间（PGAS）——允许 kernel 内部直接读写远端 GPU 的显存。粒度比集合通信细得多，适合通信与计算深度交织的场景（如 MoE 的细粒度 token 路由）。

各家 xCCL 的 API 名字和语义高度相似，因为它们共同的祖先都是 MPI 标准里 collective 那一章。学会一套，迁移成本很低——真正的差异不在 API，而在底层拓扑感知与算法选择的实现质量。

九、并行策略与原语的对应关系

把前面的内容串起来，就得到了这张对照表。看懂它，基本就能读懂主流训练框架的通信部分。

并行策略 用到的原语 在什么时候 特点
DDP（数据并行） all_reduce 反向传播中，梯度就绪即发 频率低、可与计算重叠
ZeRO-1/2 reduce_scatter + all_gather 梯度归约 + 参数同步 通信量同 DDP，省显存
FSDP / ZeRO-3 all_gather ×2 + reduce_scatter 前向、反向各凑一次参数 通信量约 DDP 的 1.5 倍
TP（张量并行） all_reduce 每层前向、反向各若干次 频率极高，一般只在机内做
SP（序列并行） reduce_scatter + all_gather 替代 TP 的 all_reduce 总量不变，省激活显存
PP（流水并行） send / recv stage 边界 量小但延迟敏感
EP（专家并行） all_to_all_v ×2 MoE 层的 dispatch 与 combine 最难优化

一条贯穿始终的工程原则：通信越频繁、消息越大的并行维度，越要放在带宽越高的位置。所以 TP 和 EP 通常限制在单机的 NVLink 域内，而 DP 因为一步只通信一次、又能和反向计算重叠，放到跨机去。

NCCL_DEBUG=INFO 是排障第一步，它会打印拓扑发现、算法选择、传输方式的完整决策链路。

定位 hang 的通用方法：集合通信 hang 的本质永远是”部分 rank 到了、部分没到”。所以第一件事是确认每个 rank 卡在哪一次集合操作上——

  • 如果所有 rank 卡在同一个操作，问题在网络或硬件；
  • 如果卡在不同操作，问题在应用层的控制流分歧（回到坑 1）。

PyTorch 的 Flight Recorder（设置 TORCH_NCCL_TRACE_BUFFER_SIZE）会记录每个 rank 最近的集合操作，正是为这个判断准备的。
