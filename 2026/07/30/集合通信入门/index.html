集合通信

集合通信（Collective Communication）是由一个通信域（Communicator）中的一组进程或设备共同参与的通信操作。通信域中的每个参与者都拥有唯一的编号，称为秩（Rank）；某些集合操作还会指定一个根秩（Root Rank），作为数据的源端或目的端。

这里的“所有参与者”是指通信域内的全部 Rank，而不一定是作业中的全部进程。各 Rank 必须以一致的顺序调用相匹配的集合操作，并保证数据类型、元素数量、根秩等参数符合接口约定，否则可能造成阻塞、数据错误甚至程序崩溃。

集合通信是分布式训练的核心基础设施。数据并行中的梯度同步、张量并行中的激活值聚合、ZeRO/FSDP 中的参数分片，以及 MoE 中的 Token 路由，都依赖不同的集合通信模式。

1. 基本概念

集合通信的基础操作包括发送（Send）、接收（Receive）、复制（Copy）、组内进程的栅障同步（Barrier），以及节点间的进程同步（Signal + Wait）等。

这些基础操作通过不同方式组合，形成了一系列标准的集合通信原语，主要包括：一对多的广播（Broadcast）、多对一的收集（Gather）、多对多的全收集（All-Gather）、一对多的分发（Scatter）、多对一的规约（Reduce）、多对多的全规约（All-Reduce）、规约与分发相结合的规约分发（Reduce-Scatter），以及多对多的全交换（All-to-All）等。这些通信原语通过相应的集合通信算子实现。

集合通信的核心挑战在于提升通信效率，并针对不同的网络硬件及其连接拓扑，选择和设计与之相匹配的通信算法，从而充分利用网络带宽、降低通信延迟。

从接口语义上看，Send 和 Receive 属于点对点通信（Point-to-Point Communication），Barrier、Broadcast、Gather、Reduce 等才属于集合操作。Copy、Signal 和 Wait 通常是通信库或设备运行时在实现集合算法时使用的本地数据搬运与同步机制，并不是跨平台统一定义的集合通信原语。

集合通信库通常在这些基础机制之上，根据消息规模和硬件拓扑选择具体算法。例如，一次 AllReduce 在语义上可以分解为 Reduce + Broadcast，也可以分解为 ReduceScatter + AllGather；但高性能实现通常不会真的先把所有数据集中到某个 Rank，再从该 Rank 重新发送，而是采用环、树或分层算法，让通信与规约计算并行执行。

以一台包含 4 张加速卡的服务器为例，可将 4 张卡抽象为 Rank 0～Rank 3。逻辑 Rank 与物理设备编号不是同一个概念，通信库还需要建立从 Rank 到设备及网络端点的映射。服务器内的互连通常包括 PCIe、NVLink/NVSwitch 等；跨服务器通信则常使用 InfiniBand、RoCE 或以太网。实际系统不一定是全连接拓扑，即使逻辑上任意两个 Rank 都可以通信，数据也可能需要经过交换芯片、网卡或其他设备转发。

常见集合通信操作可分为三类：

  • 数据搬运：Broadcast、Scatter、Gather、AllGather、AllGatherV、AllToAll 和 AllToAllV；
  • 搬运与计算：Reduce、AllReduce、ReduceScatter 和 ReduceScatterV；
  • 全局同步：Barrier。

2. 常见通信原语

设通信域中共有 个 Rank，Rank 0 为示例中的根秩。各原语的核心语义如下：

原语 数据流向 操作结果
Broadcast 一对多 根 Rank 的同一份数据复制到所有 Rank
Scatter 一对多 根 Rank 的数据被划分后分发到各 Rank
Gather 多对一 各 Rank 的数据按 Rank 顺序收集到根 Rank
AllGather 多对多 每个 Rank 都获得所有 Rank 数据的拼接结果
AllGatherV 多对多 每个 Rank 获得各 Rank 变长数据的拼接结果
Reduce 多对一 各 Rank 的数据按元素规约，结果保存在根 Rank
AllReduce 多对多 各 Rank 的数据按元素规约，完整结果保存在每个 Rank
ReduceScatter 多对多 先按元素规约，再将规约结果分片到各 Rank
ReduceScatterV 多对多 先按元素规约，再按不同长度分配结果块
AllToAll 多对多 每个 Rank 向每个目标 Rank 发送不同的数据分片
AllToAllV 多对多 每对 Rank 之间可以交换不同数量的数据

Broadcast

Broadcast（广播）将根 Rank 上的一份数据复制到通信域内的所有 Rank。操作完成后，每个 Rank 都拥有内容相同的数据。

Broadcast 的逻辑语义：广播完成后，每个 Rank 的输出都等于根 Rank 的输入。

典型应用包括：

  • 在数据并行训练开始前同步模型参数或随机种子等初始化状态；
  • 分发配置、元数据或控制信息；
  • 作为某些 AllReduce 算法中的一个逻辑阶段。

Broadcast 强调的是“复制同一份数据”。如果根 Rank 向不同 Rank 发送不同分片，则对应的是 Scatter，而不是 Broadcast。

Scatter

Scatter（散发或分发）把根 Rank 上的输入缓冲区划分为 个数据块，并将第 个数据块发送给 Rank 。每个 Rank 只接收属于自己的那一部分数据。

Scatter 的逻辑语义：根 Rank 持有完整输入，每个 Rank 最终只获得与自身编号对应的数据分片。

Scatter 常用于从中心化数据布局转换为分片布局，例如分发输入数据、模型参数或计算任务。它与 Gather 的数据流向相反，但二者并不意味着对任意程序状态都构成严格的数学逆操作。

Gather

Gather（收集）把每个 Rank 的本地数据收集到根 Rank，并通常按照 Rank 编号依次写入根 Rank 的接收缓冲区。除根 Rank 外，其他 Rank 不会获得完整的收集结果。

Gather 的逻辑语义：各 Rank 提供本地分片，仅根 Rank 获得按 Rank 顺序拼接的完整结果。

Gather 适合汇总推理结果、日志、指标或检查点数据。如果所有 Rank 都需要获得完整结果，应使用 AllGather。

AllGather

AllGather（全收集）使每个 Rank 都获得所有 Rank 本地数据的拼接结果。若每个 Rank 提供 个元素，则操作完成后，每个 Rank 通常得到按 Rank 顺序排列的 个元素。

AllGather 的逻辑语义：每个 Rank 最终都获得所有本地输入按 Rank 顺序拼接后的结果。

从通信语义上看，AllGather 可以理解为 Gather + Broadcast，但实际实现通常没有固定根 Rank，也不会先将全部数据集中到单个 Rank。环形 AllGather 会让数据分片沿环逐步转发，从而均衡链路流量并避免根节点瓶颈。

典型应用包括：

  • 在 ZeRO/FSDP 中临时聚合分片参数；
  • 在张量并行或序列并行中聚合分片张量；
  • 作为基于 ReduceScatter + AllGather 的 AllReduce 算法的第二阶段。

AllGatherV（变长全收集）

AllGatherV 是 AllGather 的变长版本：不同 Rank 可以提供不同数量的元素，操作完成后，每个 Rank 都获得所有输入的完整集合。以 MPI 的 MPI_Allgatherv 为例，recvcounts[r] 描述从 Rank 接收的元素数量，displs[r] 描述该数据在接收缓冲区中的起始位置。

AllGatherV 的逻辑语义：各 Rank 的本地输入长度可以不同，但每个 Rank 最终都获得同一组变长数据。图中块高表示元素数量。

对于每个源 Rank ，发送端提供的数据类型签名必须与所有接收端为其配置的接收类型签名匹配。displs 允许数据块在接收缓冲区中具有不同的放置位置，因此结果不一定必须紧密连续；工程实践中通常使用按 Rank 顺序排列且互不重叠的布局。

AllGatherV 常用于聚合长度不一致的序列、Token、稀疏索引或不均匀数据分片。由于各 Rank 的发送量可能相差较大，整体性能往往受最大数据块和链路负载不均衡影响。

Reduce

Reduce（规约）对各 Rank 输入缓冲区中相同位置的元素执行规约运算，并只将结果写入根 Rank。例如，4 个 Rank 分别提供标量 5、6、7、8，使用求和操作后，根 Rank 得到 26。

Reduce 的逻辑语义：对各 Rank 的对应元素执行规约，并仅在根 Rank 上保存完整结果。图中采用 Sum 操作，结果为 26。

常见规约运算包括求和（Sum）、乘积（Product）、最大值（Max）和最小值（Min）。MPI 还定义了逻辑运算、位运算、MaxLoc、MinLoc 及用户自定义规约操作；具体通信库支持哪些运算，应以其接口和数据类型约束为准。为了便于并行化，规约运算通常应满足结合律；算法是否可以任意调整运算顺序，还取决于操作是否满足交换律。实数加法在数学上满足结合律，但浮点加法受舍入误差影响并不严格满足结合律，因此不同规约顺序可能产生细微的数值差异。

Reduce 常用于只需要在一个 Rank 上获取全局统计量或聚合结果的场景。如果每个 Rank 都需要规约结果，则应使用 AllReduce。

ReduceScatter

ReduceScatter（规约散发）先对所有 Rank 的输入数据按元素执行规约，再将规约后的结果划分为 个数据块，使 Rank 只获得第 个结果块。

ReduceScatter 的逻辑语义：每个 Rank 提供相同分块布局的输入，Rank 最终获得第 个数据块的规约结果。

例如，每个 Rank 都提供由 A、B、C、D 四个分片组成的输入。执行求和 ReduceScatter 后，Rank 0 获得所有 A 分片的和，Rank 1 获得所有 B 分片的和，以此类推。它描述的是一个整体集合操作，并不要求实现先把完整规约结果集中到某个 Rank，再执行 Scatter。

ReduceScatter 常用于：

  • 数据并行中的分片梯度同步；
  • ZeRO/FSDP 中将规约后的梯度直接保留在对应的参数分片持有者上；
  • 环形 AllReduce 的规约阶段。

AllGather 与 ReduceScatter 在数据布局和通信量上具有互补关系，但 ReduceScatter 包含会丢失信息的规约运算，因此二者通常不能称为严格的“正向与反向操作”。

ReduceScatterV（变长规约散发）

ReduceScatterV 是结果分片长度不必相等的规约散发。设 recvcounts[i] 为 Rank 接收的元素数量，则每个 Rank 的输入向量长度都应为 。通信库先对这些等长输入向量执行逐元素规约，再把长度为 recvcounts[i] 的第 个结果块交给 Rank 。

ReduceScatterV 的逻辑语义：所有 Rank 使用相同的结果分块描述，但不同目标 Rank 的结果块长度可以不同。图中 recvcounts = [1, 2, 3, 4]。

命名需要特别注意：MPI 将变长接口命名为 MPI_Reduce_scatter，并要求所有参与 Rank 提供相同的 recvcounts 数组；对应的等长接口称为 MPI_Reduce_scatter_block。部分加速器通信库则把二者称为 ReduceScatterV 和 ReduceScatter。

ReduceScatterV 适合不均匀参数分片、稀疏梯度分区或各 Rank 目标负载不同的场景。它仍然是一个整体集合操作，并不意味着实现必须先在某个根 Rank 上形成完整结果。

AllReduce

AllReduce（全规约）对所有 Rank 的输入按元素执行规约，并把完整结果发送到每个 Rank。数据并行训练通常使用 Sum 或 Average AllReduce 同步梯度，使各个模型副本基于一致的聚合梯度更新参数。

AllReduce 的逻辑语义：对所有 Rank 的对应元素执行规约，并将完整规约结果写入每个 Rank。图中采用 Sum 操作，结果为 26。

AllToAll

AllToAll（全交换）要求每个 Rank 将输入划分为 个分片，其中发往 Rank 的分片只发送给 Rank ；与此同时，每个 Rank 都会从其他所有 Rank 接收相应分片。它可以视为一种完整交换（Complete Exchange）。

AllToAll 的逻辑语义： 表示从源 Rank 发往目标 Rank 的数据，Rank 最终汇集来自所有源 Rank 的相应分片。

AllGather 向所有目标复制相同的本地数据，而 AllToAll 向不同目标发送不同的数据，因此 AllToAll 通常具有更复杂的流量模式。AllToAllV 进一步允许发往不同 Rank 的数据量不同，更适合负载不均衡的场景。

典型应用包括：

  • MoE 专家并行中的 Token 分发与结果回传；
  • 张量布局变换和并行维度重分片；
  • 分布式矩阵转置或数据重排。

AllToAll 可以实现某些分布式矩阵转置，但其本质是按目标 Rank 进行数据交换，不能笼统地等同于矩阵转置。

AllToAllV（变长全交换）

AllToAllV 是 AllToAll 的变长版本。对 Rank 而言，sendcounts[j] 和 sdispls[j] 分别描述发往 Rank 的元素数量及其在发送缓冲区中的位置；recvcounts[j] 和 rdispls[j] 则描述从 Rank 接收的数据量及其在接收缓冲区中的放置位置。

Barrier

Barrier（栅障）是一种不携带用户数据的集合同步操作。调用 Barrier 的 Rank 会等待，直到通信域内所有 Rank 都进入同一个 Barrier，随后各 Rank 才能继续执行。

Barrier 的逻辑语义：任何 Rank 从 Barrier 返回之前，通信域内的所有 Rank 都必须已经进入该 Barrier。

Barrier 适合阶段性同步和调试，但不应被无条件插入性能关键路径。许多集合操作只保证自身的数据依赖与完成语义，并不等价于一次全局 Barrier；额外同步会破坏计算与通信重叠，增加等待时间。

3. 点对点通信与底层同步

Send 与 Receive

Send/Receive 在两个 Rank 之间直接传输数据，是构造集合通信算法的重要基础。例如，环形 AllReduce 会在相邻 Rank 之间重复执行分片的发送、接收和本地规约。不过，对应用层而言，应优先使用能准确表达需求的集合接口，让通信库统一进行拓扑感知和调度优化。

Signal 与 Wait

Signal/Wait 通常指设备运行时、共享内存或网络传输层中的事件同步机制：生产者在数据就绪后发出信号，消费者等待相应事件后再读取或复用缓冲区。其事件格式、确认方式和内存可见性规则由具体硬件及 SDK 决定，不能假定所有通信库都采用相同的握手协议。它们更适合被视为集合通信实现细节，而不是与 Broadcast、AllReduce 并列的标准集合原语。

4. 常见集合通信算法

集合原语规定“结果是什么”，集合算法决定“数据怎样传”。同一个 AllReduce 可以有多种正确实现，性能差异主要来自启动延迟、通信数据量、链路并行度、规约计算开销和拓扑匹配程度。

常见算法包括：

  • 环形算法（Ring）：将数据切分并沿逻辑环流水传输。对于大消息，Ring AllReduce 通常可以获得较高的带宽利用率；但其通信轮数随 Rank 数量线性增长，小消息或超大规模场景可能受延迟限制。
  • 树形算法（Tree）：通过二项树、二叉树或双二叉树逐层传播和规约，通信轮数通常为 ，更适合延迟敏感的小消息。树的构造方式会影响负载均衡和可用带宽。
  • 递归倍增（Recursive Doubling）：每轮与距离成倍增长的伙伴交换数据，常用于 Rank 数为 2 的幂时的小型或中型 AllGather、AllReduce。
  • 分层算法（Hierarchical）：先利用 NVLink/NVSwitch 或 PCIe 完成节点内通信，再通过 InfiniBand/RoCE 完成节点间通信，最后在节点内分发结果，以避免让慢速跨节点链路承载不必要的重复流量。

其中， 是通信轮数， 表示单次消息的启动延迟； 是传输字节数， 表示单位字节的传输时间，即有效带宽的倒数； 是参与规约的元素数量， 表示单位元素的本地计算成本。实际性能还会受到链路竞争、交换机超卖、PCIe/NIC 亲和性、NUMA、协议头开销和流量调度的影响。

优化集合通信时通常需要关注：

  • 消息规模：小消息更关注启动延迟，大消息更关注带宽利用率；
  • 拓扑感知：根据 GPU、CPU、NIC 和交换机的连接关系构造环或树；
  • 分片与流水：将大消息切分为多个 Chunk，使传输、规约和转发重叠；
  • 操作融合：合并多个小张量，减少内核启动和网络消息数量；
  • 计算通信重叠：在依赖允许时异步发起通信，并与前向或反向计算并行；
  • 多轨与多网卡：合理使用多条独立链路，同时避免流量集中到同一 PCIe Root Complex 或交换机端口；
  • 分层和网内规约：在硬件支持时使用节点内/节点间分层算法，或利用交换网络的规约卸载能力。

因此，集合通信不存在对所有场景都最优的固定算法。高性能通信库必须综合考虑操作类型、数据规模、Rank 数量、物理拓扑和运行时负载，动态选择协议与算法。

6. 通信库与软件栈

深度学习框架通常不会直接操作网卡或设备互连，而是通过通信后端调用专业通信库。例如：

  • MPI 面向通用分布式并行计算，定义了丰富的点对点和集合通信接口；
  • NCCL 面向 NVIDIA GPU，提供拓扑感知的 GPU 集合通信和点对点通信；
  • RCCL、oneCCL、HCCL 等库分别服务于不同的加速器或软件生态；
  • CUDA-aware MPI 可以直接识别设备缓冲区，减少应用显式搬运数据的工作。

框架、通信库、设备运行时和网络传输层共同构成集合通信软件栈。上层关注 Rank、通信域和张量语义，底层负责设备内存访问、链路选择、数据分片、同步和错误处理，从而屏蔽硬件差异。

小结

集合通信原语定义了分布式程序中常见的数据交换与规约模式，集合通信算法则负责将这些语义高效映射到真实网络。理解 Broadcast、Scatter、Gather、AllGather、AllGatherV、Reduce、ReduceScatter、ReduceScatterV、AllReduce、AllToAll 和 AllToAllV 的准确语义，是进一步分析 Ring、Tree、分层 AllReduce 以及大模型并行通信开销的基础。
